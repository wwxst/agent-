# Agent Kernel 重构前的执行合同实验｜2026-10-31

> 研究分支：`research/agent-kernel-contract-spike-20261031`。本报告是自研最小模型的 **Fixture 结果**，并非四个参考产品动态跑分，也非旧 `agent-` Kernel 的恢复方案。

## 目标

验证在 `agent-cil` 迁移/破坏性重构之前，哪些执行合同应成为新内核的硬约束，并对比两种工具结果写入策略：
- **事实即时记录 + 模型投影稳定排序**（本研究候选）
- **等待前序槽位才按模型顺序提交结果**（参考 DeepSeek Harness 的 `commitReady` 思路）

## 实验环境和命令

- 日期：2026-10-31
- Node：v22.16.0；npm：10.9.2
- 环境：隔离的本地 Node 进程，纯内存 EventJournal + FakeToolHost；没有真实 Provider 凭证、外部网络或 shell 副作用
- 执行：`node --test experiments/kernel-contract-spike/*.test.mjs`（本地相同源码所在目录执行 `node --test *.test.mjs`）

## 对源码设计的直接判断

1. Pi 的 `runAgentLoop` 异步 EventSink 是低层适配候选；外部安全屏障不能只靠未 await 的 UI 事件流，且不能在一条并行结果事件写入失败时释放执行权。
2. DeepSeek Harness 的 `commitReady` 保持结果的模型顺序，但可能产生“副作用已完成、结果尚等待前序槽位”的观测窗口。是否需要 Host 侧独立执行收据需实测。
3. Codex 的 StepContext 快照是必须补充验证的执行输入一致性设计，不意味着直接采用其 Rust Core。
4. Claude 2.1.304 的静态分析显示流式工具分发、权限和宿主/子智能体机制，但当前未做真实 Claude CLI 运行对照。

**阶段性建议（仅候选）**：新 Agent Kernel 采用最小 Loop + 独立执行协调器；工具意图批次在启动前持久化；Host 已确认的执行事实立即提交；模型上下文按 ToolCall ID 投影；持续运行的工作由独立 Host/监督器终止并结算；未知结果停止普通循环而不是自动重试。
