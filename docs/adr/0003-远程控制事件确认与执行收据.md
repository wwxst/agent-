# ADR 0003 · 将网络收件确认、持久接受、执行开始和工具结果分离

- 状态：**提议**（待维护者确认；不代表已实现）
- 日期：2026-10-24
- 研究触发：[Claude Code 远程 Bridge 源码追踪](../research/claude-code/18-远程Bridge事件确认与恢复.md)
- 适用范围：Client API、Agent Kernel、EventStore、Remote Worker、Tool Host

## 背景

Agent 的远程控制既要处理网络重连，又要防止重复执行副作用。Claude Code 2.1.88 的 `replBridgeTransport.ts` 有清晰的工程取舍：为了避免重连反复派发相同命令导致提示重复，在 Bridge 接收到消息时同时确认 `received` 与 `processed`。源码注释承认：如果子进程在真正持久接收前崩溃，会出现丢消息窗口。

这个例子提醒我们：**传输层收到数据不是业务已接受，业务已接受不是工具已开始，工具已开始也不是操作已成功。**

## 决策提议

### 1. 区分四种确认

- `TransportReceived`：某个网络连接看到消息，允许重放，不改变业务事实；
- `CommandAccepted`：命令在可信存储中通过幂等键提交，Session/Turn 确认接收；
- `ExecutionStarted`：可信 Worker/ToolHost 持有有效 Lease/Epoch、记录意图后开始；
- `ExecutionTerminal`：获得可验证结果、失败或 `OutcomeUnknown`。

客户端只能从 CommandAccepted 推导“任务已提交”，只能从 ExecutionTerminal 推导“本次执行有最终结果”。

### 2. Command Inbox 和 Event Journal

- 命令带不可重复的 `commandId`、`idempotencyKey`、Session ID 和所期望 Turn/状态版本。
- CommandAccepted 与状态变更需要一个可信事务边界。
- 在事务提交前，不能通过网络发出“已接受”的最终确认。
- 服务端至少一次投递客户端事件；客户端按 `sessionId + sequence` 去重。
- 事件日志与 Snapshot 分离，旧事件丢失时必须明确要求重新取快照。

### 3. Tool Invocation 意图和执行收据

- 有副作用操作需先持久化 ToolCallPrepared、参数指纹、授权 ID、Host/Epoch，再允许执行。
- Host 以 `toolCallId` + `hostId` + `epoch` 记录接收与执行状态，拒绝明显重复或过期请求。
- Host 不能确认是否已完成时，返回 `OutcomeUnknown`；Kernel 不盲目重复执行 Shell、消息发送、外部 API 等非幂等调用。
- 即使各层做了幂等，**也不宣称外部世界的任意副作用能无条件 exactly-once**。
- Task 恢复时先核对收据/后置条件，不能仅凭消息上下文推测已经执行。

### 4. Worker Epoch 与权限

- 同一 Agent Host 的 Lease 在换 Worker 时提高 Epoch；旧 Epoch 不应能够开始新的操作。
- Epoch 用于 fencing，不是用户/会话授权令牌；必须与 Scope、Capability、密钥认证结合。
- 远程 Worker 不可自动降级为本地执行以规避故障。
- 重连之后，已批准的 ToolCall 必须继续绑定原有参数摘要和工具实现版本。

### 5. 事件展示与持久状态区分

- 模型 Token、实时进度和临时 UI 变化可以走非持久流；
- 审批、工具意图、关键状态转换和任务终态必须先持久提交再广播；
- 当广播失败但已提交成功时，允许从 EventStore 重放同一个 eventId；
- 当写入失败时，不能向客户端广播代表持久成功的终态。

## 备选方案

| 方案 | 优势 | 拒绝原因 |
| --- | --- | --- |
| 收到消息就回复 processed | 时延低，实现简单 | 崩溃窗口内可能确认后丢失，语义混淆 |
| 直到工具结束再回复收到 | 业务语义直观 | 执行太久，重连易重复入队；客户端无法感知已排队 |
| 四阶段事实 + Event Journal + Worker Receipt（提议） | 可追溯、可恢复、避免无声丢失/重复 | 需要更多状态和持久化测试 |
| 尝试外部 exactly-once | 表面 API 简单 | 对任意不受控外部系统无法普遍保证 |

## 验收门槛

1. 网络重发已接受命令：仍只有一个 Turn。
2. 收到消息但未提交时进程崩溃：重试能够提交，不存在虚假的已接受 ACK。
3. 持久接受后广播失败：重连回放相同事件 ID。
4. 工具可能已经执行而回执丢失：非幂等操作禁止自动重试。
5. 重建 Worker 后旧 Epoch 的新 ToolCall 被拒绝。
6. 同一 ToolCall 的拒绝/批准/取消顺序符合版本化状态机，不被迟到控制响应覆盖。
7. 事务异常和快照损坏可由事件恢复或明确报告故障，不把不完整历史报告为成功。
8. 客户端 UI 区分“收到”“排队”“运行中”“已完成”“结果未知”。

## 决策与实施状态

该 ADR 为提议；具体 EventStore/数据库、Worker Lease、跨进程协议仍需实现前通过其他 ADR 确认。研究本身不能替代故障注入、跨进程与操作系统级测试。
