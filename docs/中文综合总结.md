# Agent 内核技术文档综合总结

> 本总结依据仓库已有设计、阶段性实现记录、架构决策记录及四套内核研究整理。**本仓库当前为纯文档归档，不含运行源码。** 所有历史实现和测试陈述仅适用于当时对应的源码版本，不构成当前仓库的功能承诺。

## 一、项目在研究什么

项目目标是建立一个独立的 Agent 执行内核：让模型生成操作意图，由可信运行时控制状态机、工具执行、权限审批、事件存储与故障恢复，并允许以后从 CLI 扩展到桌面、Web 或远程服务。

研究并比较 Pi Agent、OpenAI Codex、Claude Code 和 DeepSeek Harness，是为了选择可验证的设计机制，而不是简单复制其中任意一种产品。设计重点始终是**状态一致性、执行安全、可审计性和故障时的保守处理**。

## 二、总体架构：六个核心层次

| 层次 | 主要责任 | 关键边界 |
| --- | --- | --- |
| 内核与状态机 | Session、Turn、Step、Agent Loop、终态、取消 | 不依赖具体模型厂商和操作系统工具 |
| 模型适配 | 流式响应、工具调用声明、用量、上下文格式 | Provider 不直接执行工具或修改权威事件 |
| 工具调度 | 工具注册、参数预检、风险类别、并发屏障 | 调度通过不等于工具获得执行授权 |
| 可信工具宿主 | 执行入口、身份与权限复核、资源/文件/网络隔离 | Host 独立校验，拒绝不满足安全条件的执行 |
| 持久化与恢复 | 事件日志、Writer Lease、Fencing、Intent/Receipt、Checkpoint | 不确定的外部副作用不得自动重放 |
| 控制与扩展 | 命令接收、Steering、控制面授权、后续 Skills/MCP/Subagents | 插件与客户端不能提升权限或覆盖内核事实 |

详见：[总体架构](01-总体架构.md)、[执行循环](02-执行循环与状态机.md)、[模块地图](模块地图.md)。

## 三、最重要的设计结论

### 1. 状态机与事件日志应当成为事实基础

模型输出和客户端显示只是某个阶段的观察结果。Session、Turn、工具意图与执行收据必须有稳定标识和可核验的事件顺序；Snapshot/Checkpoint 是可重建的投影，不能代替不可变事件事实。

### 2. “收到命令”和“执行成功”必须分开

网络 ACK、命令持久接受、Turn 入场、工具开始和工具执行结束是五类不同事件。重复网络请求应由幂等键和持久绑定处理，不可借重放历史消息重做外部操作。

### 3. Tool Intent/Receipt 是可靠性边界

工具执行前要有可信的意图记录，执行后要有执行宿主可核验的收据。对于“可能执行了但没有拿到结果”的情况，应保留结果未知状态（Outcome Unknown），走对账与人工审核，不得默默重试。

### 4. 取消和租约不等于外部副作用被撤销

AbortSignal、Writer Lease 与 Fencing Token 可以阻断后续动作或拒绝旧执行者，但不能证明已经发生的网络调用、文件写入或外部副作用已撤回。因此取消、超时、租约丢失和结果未知必须被区别处理。

### 5. 工具权限要由可信宿主独立强制

模型、插件、项目文档或客户端给出的能力声明不能作为授权根。工具宿主必须复核调用身份、参数、租约、权限和运行环境；Linux namespace、cgroup、seccomp 分别解决不同威胁，缺一项不能声称达到完整沙箱。

### 6. 模型上下文与审计事实需要分开

给模型的历史内容可能经过摘要、裁剪或格式转换，但不能因此改写权威 Tool Outcome 或抹除原始证据。上下文压缩失败应保持保守语义，不应触发未知副作用重放。

## 四、四套参考内核的主要借鉴方向

| 参考系统 | 核心研究价值 | 自研方案需要保留的边界 |
| --- | --- | --- |
| Pi Agent | 简洁的执行循环、模型流、工具并发与 Steering | 外部事件持久化屏障、并行执行排空、截断与结果未知处理不能退化 |
| OpenAI Codex | Turn/Step 控制、工具路由、审批、沙箱和持久事件 | 明确状态机、授权优先级和终态的事实来源 |
| Claude Code | 权限链、Hooks、Skills、子任务、压缩与客户端协议 | 区分 SDK/静态分析与实际执行；避免把界面取消当成 OS 强制终止 |
| DeepSeek Harness | Scope、组合能力、工具管线、能力生命周期 | 插件不得接管可信宿主、授权根和权威日志 |

跨内核研究最终提出 TypeScript、SQLite WAL、独立 Tool Host 和保守并发调度作为重要候选基线；后续重评又讨论直接采用 Pi Core 等替代方案，**尚不能把所有候选视为已被最终接受**。详见：[正式架构评审](research/comparative/14-自研内核架构取舍正式评审稿.md)、[架构重评](research/comparative/26-架构重评第一轮-2026-10-29.md)、[Pi Core 适配审查](research/comparative/28-Pi-Agent-Core适配边界审查-2026-10-29.md)。

## 五、历史阶段记录应该如何理解

- **M0：** 内核合同、基础 Agent Loop、内存事件存储与确定性测试的历史起点。
- **M1：** 安全重开、SQLite WAL、Writer Lease/Fencing、托管会话、Intent/Receipt、双账本和人工审核记录的增量演进。
- **M2：** 命令幂等、Steering、上下文 Checkpoint、Command Dispatcher、身份凭据和执行期间授权重检。
- **M3：** Linux Bubblewrap、cgroup、Worker 身份验证、seccomp 与挂载目录准入的部分安全实现和验证记录。

这些是**清理前代码仓库的时间线**；当前目录没有上述模块的可执行实现，也没有 CI 可用于重跑记录中的测试。

## 六、尚未解决或仍需验证的关键问题

1. 真正独立 Worker cgroup 的受控 Linux 环境正向验证，以及可移植的系统调用与资源隔离方案。
2. SQLite 权限隔离、宿主身份核验、跨进程与外部副作用的一致性边界。
3. 生产鉴权、高风险审批、人工审核者身份及受控恢复操作。
4. 多模型真实端到端测试、令牌预算和流式异常处理。
5. Skills、MCP、Subagents、远程 Worker 与客户端协议的完整生产设计。
6. “继续自研循环”与“采用现成 Agent Core 并加可信适配层”的成本/安全对比。
7. 历史研究中未实测或仅静态推导的机制，仍需要同条件动态实验。

## 八、总结

这些文档的共同结论并不是“Agent Loop 应当如何调用模型”这么简单，而是：**一个可托付实际操作的 Agent 内核，必须以可核验状态、持久证据、权限边界和失败语义为基础**。今后重新开展代码实现时，应先确定要保留的安全不变量，再选择自研或复用哪些执行部件，避免单纯因为某个框架更短或功能更多而放弃可靠性要求。
