# 25 · M2 持久身份权威、密钥轮换/撤销与授权决策审计

> 交付范围：**受信本机管理的静态 Principal 凭据生命周期**，服务内执行时每次从 SQLite 事务读取最新权限并提交授权决策记录。本轮仅保护 Loopback Command 控制面，不开放远程管理端点，也不等于生产级 IdP、通用 RBAC、加密日志、防篡改日志或 OS 沙箱。

## 设计原则

- 原有 `ControlKeyring` 保留为明确的**临时内存模式**；新的 `SqliteControlAuthority` 是部署方可显式启用的**持久模式**。`startLoopbackControlServer` 必须二选一传入 `principals` 或 `authority`，同时传入或都不传均拒绝启动。
- 由可信宿主代码首次调用 `authority.bootstrap([...])`；必须提交至少一个高强度 32-byte Base64url Bearer 凭据，明确 `principalId`、Session 白名单和 `command.accept / command.inspect / command.dispatch` 能力。数据库中已存在任何历史信任根时拒绝重复 Bootstrap，**不能重启后偷偷重建已被撤销的密钥**。
- **Bearer 原文不落 SQLite**；仅 SHA-256(高随机度 Base64url Token) 十六进制摘要入库。读库时逐个候选使用等长 Buffer `timingSafeEqual` 校验（不可防同 OS 用户窥取正在运行的宿主进程内存或 HTTP 网络接口上的明文 Token）。
- 一切管理操作 **只提供受信进程 API**：`rotate(principalId,expectedVersion,newToken)`、`revoke(principalId,expectedVersion)`。不通过普通 Bearer HTTP 开放自我授权、密钥替换、复活或其他管理员能力。
- Rotation 保留原始 Session 白名单和权限、不扩权；每次需要 CAS `expectedVersion`，同一 Principal 只存在一个有效摘要。撤销永久冻结该 Principal ID。历史令牌摘要由 `control_credential_history` 记录，**旧 Token 永不允许重用**。
- 授权每次用 `BEGIN IMMEDIATE` 读取实时 `control_credentials`，并在同一事务内写入 `control_authorization_audit`；成功与 `401/403` 拒绝的身份结果均先持久提交（SQL/WAL/FULL）才返回。审计写入失败时整个授权拒绝，无“日志写不进去但先执行”的降级模式。

## SQLite 数据结构

| 表 | 含义 |
| --- | --- |
| `control_credentials` | Principal ID、凭据摘要、JSON Session/Permission allowlist、单调 `credential_version`、revoked |
| `control_credential_history` | 全部历史摘要，拒绝轮换回旧凭据，不包含凭据明文 |
| `control_authorization_audit` | 自动递增 `audit_seq`、action、decision、principalId、sessionId、permission、credentialVersion、数据库时间戳 |

`action` 包括 bootstrap / rotate / revoke / authorize。授权结果限于 allowed、unauthenticated、forbidden。未知 Token 的主体为 null；从不存储原始 Token、Authorization 头、命令 Payload、模型输出或响应消息。SQL Audit 没有跨 DB 防篡改签名：拥有数据库写权限的攻击者可伪造/删除审计；本地文件权限/备份/安全隔离仍由部署方负责。

## 使用示例

```ts
import {randomBytes} from 'node:crypto';
import {SqliteControlAuthority} from './packages/control-plane/src/authority.js';
import {startLoopbackControlServer} from './packages/control-plane/src/index.js';

const authority = new SqliteControlAuthority('./agent.sqlite');
const first = randomBytes(32).toString('base64url');

// 只在首次安装时、受信的本地管理流程中调用；不能每次启动执行。
authority.bootstrap([{
  principalId:'operator_1',
  bearerToken:first,
  sessionIds:['session_1'],
  permissions:['command.accept','command.inspect','command.dispatch'],
}]);

// 后续启动直接使用已存在的 authority，不能尝试 bootstrap。
const http = await startLoopbackControlServer({
  databasePath:'./agent.sqlite',
  runner,           // 由可信宿主配置的 ManagedSessionRunner
  authority,        // 与 principals（旧内存配置）严格互斥
});

// 本机管理进程的可信操作，绝不通过公开 HTTP Endpoint 调用：
const second = randomBytes(32).toString('base64url');
authority.rotate('operator_1',1,second);
// 旧 first 从此对新 HTTP 请求一律 401。
authority.revoke('operator_1',2);
// 新 second 同样被拒，且 operator_1 不得被复活。
await http.close();
authority.close();
```

示例中的 Token 必须由部署方的机密渠道交付；**不要打印、提交或存储原文到明文配置/CI 输出**。实际部署必须可靠保存新的 Token，否则当前接口不支持找回。

## 故障与竞争语义

- 两个宿主进程同时轮换同一版本：SQLite `BEGIN IMMEDIATE` 序列化，其中一个 CAS 成功，另一个收到 ConflictError；不会让两份历史令牌都同时生效。
- 轮换/撤销事务与授权竞争：授权结论依据数据库序列化顺序，旧令牌仅可能在撤销事务 **此前** 获得授权；撤销 COMMIT 后的 **新** 请求必须拒绝。
- **重要限制：**授权成功、写入决策审计后，与后续 `ManagedSessionRunner` 接受/分发不是同一事务。因此**已经通过认证并启动的长运行 Turn 不会被本轮撤销操作同步抢占**；需要后续带认证版本号的执行期间重新校验（及对应强制隔离），不能宣称本阶段提供即时终止能力。
- 授权审计触发器拒绝 / SQLITE I/O 出错：没有可信授权结果可返回（HTTP 为通用错误），不触发 `runner`；任何管理过程中间写入异常，Digest/版本/历史凭据/管理日志全部回滚。
- 进程在 revoke COMMIT 后被 SIGKILL：下次打开相同 SQLite 时旧 Token 仍不可用；未决 Turn / ToolCall 始终受原有 Host/Fencing/Receipt 边界阻断。
- 新增持久模式只由受信宿主明确选用；旧内存模式不提供持久授权审计、轮换、撤销的语义，应避免在需要审计的部署中继续使用。

- 真实用户/企业 IdP、密钥硬件存储、安全发放/销毁、可审计的权限增删、跨应用身份传播、密钥保管服务。
