# 03 · 数据模型、事件与持久化

> 状态：v0.1 数据合同草案；生产存储选型尚未决定。

## 一、核心实体

| 实体 | 必备字段（概念） | 说明 |
| --- | --- | --- |
| Session | id、ownerId、createdAt、configVersion、lastSequence | 真实会话归属与配置 |
| Turn | id、sessionId、state、createdAt、endedAt、requestId | 单次任务生命周期 |
| Step | id、turnId、kind、state、attempt | 单个模型或工具阶段 |
| ToolCall | id、turnId、toolName、argsHash、status、approvalId | 工具调用身份与幂等约束 |
| Approval | id、toolCallId、decision、decider、expiresAt | 明确的授权凭据 |
| Event | sessionId、sequence、eventId、turnId、type、payload、occurredAt | 可追踪、可回放的规范变化 |
| Snapshot | sessionId、lastSequence、schemaVersion、stateDigest | 提升恢复效率 |

所有 ID 由服务端生成；客户端请求幂等键不是权限证明。事件载荷必须带 Schema Version，序列号在 Session 内严格递增。

## 二、推荐事件种类

- SessionCreated / SessionConfigured / SessionClosed
- TurnQueued / TurnStarted / TurnCompleted / TurnCancelled / TurnFailed / TurnInterrupted
- UserMessageAccepted / SteeringAccepted / SteeringRejected
- ModelRequestStarted / ModelDelta / ModelMessageCompleted / ModelRequestFailed
- ToolCallProposed / ToolCallPrepared / ToolCallStarted / ToolCallSucceeded / ToolCallFailed / ToolCallOutcomeUnknown
- ApprovalRequested / ApprovalGranted / ApprovalDenied / ApprovalExpired
- ContextCompactionStarted / ContextCompactionCompleted / ContextCompactionFailed
- BudgetExceeded / CancelRequested

事件名字在落地前需要冻结到统一 JSON Schema 或等价类型定义；示例只是候选集合，不代表所有事件必须单独保存完整模型分片。

## 三、事件日志不变量

1. 事件写入是 Session 状态变化的可追溯来源；快照是派生缓存。
2. 对同一 Session，序号唯一且单调递增；游标重放不能乱序或跳号宣称完整。
3. 对客户端至少一次交付，因此消费端按 eventId 或 (sessionId, sequence) 去重。
4. 消息显示可以合并流式文本，但终态事件与工具副作用状态不可随意丢失。
5. Event Journal 和副作用状态的关系需有事务或可恢复 outbox，避免只发命令不留痕。
6. 外部工具结果、用户文件和凭据应限制保留、大小和访问权限；敏感信息不得进入普通日志。

## 四、副作用与恢复

**关键原则：不能宣称跨进程外部副作用做到任意情况下 exactly-once。**

高风险工具的推荐状态：

```text
proposed -> prepared -> started -> succeeded / failed / unknown
                         |
                     cancellation requested
```

- prepared：持久化参数、指纹、授权和执行意图。
- started：Tool Host 确认接手请求，可携带宿主侧幂等键。
- succeeded/failed：明确收到执行结果；进程死亡导致无回执应先标记 unknown。
- unknown：可能已执行或部分执行，禁止盲目重试；请求 Host 查询、使用事务型执行器协调，或请用户人工确认。

Read 等纯读工具可以按照明确策略重试；Write/Edit 在安全前提下可利用版本标签和宿主检查实现条件执行；Shell、网络发送、视频导出等默认视为非幂等。

## 五、存储抽象

推荐接口：

```ts
interface EventStore {
  append(sessionId: string, expectedSequence: number, events: KernelEvent[]): Promise<number>;
  read(sessionId: string, afterSequence: number, limit: number): Promise<KernelEvent[]>;
  loadSnapshot(sessionId: string): Promise<SessionSnapshot | null>;
  writeSnapshot(snapshot: SessionSnapshot): Promise<void>;
}
```

append 必须具备并发冲突检查，避免多实例同时推进同一个 Turn。实现前评估 SQLite/PostgreSQL 的不同并发与部署条件，不要先承诺两者完全等价。

## 六、协议演进与回放

- 事件结构用显式版本；新字段优先可选，删除旧字段要有迁移路径。
- 快照的 Schema Version 必须能迁移；重建失败时仍能从完整事件还原或给出明确错误。
- EventStore 的测试要覆盖异常断电、重复 append、存储损坏、旧版本迁移、快照与真实日志不一致。
- 客户端订阅传入 afterSequence，返回比该游标大的事件；保留窗口已过期时返回 SnapshotRequired，而不是默默跳到最新。

## 七、安全与保留

- 凭据由 SecretStore 独立托管，事件中只保存不可逆凭据引用或脱敏信息。
- 工具输出设大小上限，二进制产物存储在 Artifact Store，日志只存不可伪造的引用。
- 设定按工作区/租户隔离的读写边界和可配置数据保留策略。
