# 05 · 模型 Provider 与上下文管理

> 状态：设计草案。不同模型支持能力存在差异，不能用一套提示词假装消除协议差异。

## 一、Provider 接口

Provider Adapter 负责：

1. 列举或配置模型及可用能力（工具调用、图像、推理强度、上下文窗口等）。
2. 将 Kernel 的规范化消息转换为厂商请求。
3. 将增量响应转换为 TextDelta、ToolCallDelta、ModelCompleted、Usage、ProviderError 等内部事件。
4. 处理网络重试、限流和取消信号，维护稳定的错误分类。
5. 不允许自行执行本地工具、不管理 Session 持久化。

建议的概念接口：

```ts
interface ModelProvider {
  id: string;
  capabilities(modelId: string): Promise<ModelCapabilities>;
  stream(request: ModelRequest, signal: AbortSignal): AsyncIterable<ModelEvent>;
}
```

不要假设不同 Provider 的 ToolCall ID、消息顺序、推理消息、Usage 统计或流中断行为完全相同。Adapter 应在入口处归一化，并通过兼容性测试记录差异。

## 二、消息与工具调用规范化

模型内容区分 system、developer、user、assistant、tool；真实 Provider 没有某种角色时按明确适配策略处理，不能悄悄删除安全约束。

ToolCall 需要稳定的 ID、名称、最终结构化参数和生成来源。流式片段不得直接转发到 Tool Host；只有完整解析、参数验证与策略审批后才进入执行。

模型返回多个工具调用时，Kernel 而非 Provider 决定是否允许并行以及如何呈现执行顺序。

## 三、上下文构建

按明确顺序构建：

1. 系统与内核不可变安全规则；
2. Session/项目级可信指令；
3. 工具声明与权限提示；
4. 有效的 Skills（作为带来源标签的资源）；
5. 近期用户消息、模型消息、工具回显；
6. 经过明确协议存储的压缩摘要与任务状态。

所有外部文本都标记来源和可信度。文件中的“忽略之前指令”等内容不得上升为 system 权限。

## 四、Token 预算

需要同时限制：

- 当前请求最大上下文占用；
- 预留模型输出预算；
- Turn 累计请求与响应 Token；
- 工具输出转换为上下文的最大字节数；
- 摘要请求自身成本；
- 额外步骤数、任务时长和外部费用预算。

计算方式优先使用模型真实元数据与实际 Usage；估算值必须有安全余量。在能力信息缺失时保守拒绝超预算请求，不伪造精确 Token 数。

## 五、上下文压缩

借鉴 Codex 的重点是**在确定性边界进行压缩并保留任务有效状态**，不是照搬某个固定提示词。

建议策略：

- 在新模型请求之前检查窗口与余量，避免在 ToolCall 进行中破坏上下文。
- 需要摘要时构建显式的压缩请求；保留近期关键用户要求、当前任务和审批/工具状态。
- 摘要是可观察、可版本化的状态转换，记入 ContextCompaction* 事件。
- 原始事实、工具返回和压缩摘要应可追溯；摘要不能无条件成为覆盖用户指令的新权限。
- 压缩失败可选择缩减非关键结果或停机解释，不要跨越上下文硬上限继续发送。

## 六、错误与退化

| 错误 | 策略 |
| --- | --- |
| 网络超时且未执行工具 | 允许在重试预算内进行 Provider 重试 |
| 流式响应中断 | 明确记录不完整消息，禁止将碎片 ToolCall 执行 |
| Provider 限流 | 退避并将等待状态报告给客户端 |
| 模型不支持 ToolCall | 返回能力不匹配或显式采用有限功能模式 |
| 窗口不足 | 压缩、裁剪可裁剪项或停止并请求人工处理 |
| 用量未知 | 不宣称预算精确，采用保守上限 |

## 七、MVP 测试

- 两种 Provider 适配器契约测试（至少一种可在离线 Mock 中重放）。
- 交错 ToolCall 片段、非法 JSON、未知工具、流中断与中途取消。
- 模型/上下文预算触顶。
- 压缩后仍保留用户目标、审批结果和已完成工具事实。
- 模型生成恶意文本不能直接更改权限或系统角色。
