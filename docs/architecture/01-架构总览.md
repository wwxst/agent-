# Agent 内核：架构总览

> **状态：推荐架构草案（待评审）**。本文不宣称当前仓库已有可运行源码。

## 一、目标

构建能支持 CLI、桌面、Web 与自动化客户端的 Agent 内核。内核负责**决定什么时候调用模型或工具**、记录状态、限制资源和处理故障；模型厂商、存储、工具执行宿主和 UI 都通过清晰接口接入。

优先目标是可靠、可审计、安全和可维护；支持多个模型和客户端是设计条件，而非必须同时交付所有扩展的承诺。

## 二、逻辑结构

```text
          CLI / Web / Desktop / Automation
                      |
             Command API / Events
                      |
      Identity / Authorization / Idempotency
                      |
                Session Runtime
                 +---------+
                 | Kernel  | <---- Context Projection
                 |  Loop   | <---- Model Provider Adapter
                 +----+----+
                      |
          Tool Scheduler / Admission
                      |
          Trusted Tool Host / Sandbox
                      |
                  Tool Outcome
                      |
         Event Journal + Host Evidence
                      |
       Reconciliation / Human Review
```

上图是**逻辑分层**，不是部署实例图。某些组件可以在同一机器上，但权限和证据的信任边界不能因此消失。

## 三、七项架构不变量

1. **唯一事实源：** Session/Turn 的状态转移以版本化事件与可信记录为准，UI 和模型上下文是投影。
2. **完整调用入场：** 工具调用必须完成参数合并、Schema 验证、预算与策略检查，且在副作用前持久保存必要意图。
3. **独立授权：** 模型、插件、上下文文档及客户端不能授予工具权限；Host 重新验证请求身份和能力。
4. **副作用证据：** 工具开始和结束要可对账，失去可信收据时标记 UNKNOWN 而非默认失败或重试。
5. **执行互斥：** 共享可变 Session 必须有单写者/版本竞争约束；旧租约失效后不允许新动作入场。
6. **保守终止：** 取消、超时和进程终止不是副作用撤回的证明；未决调用必须保留证据。
7. **扩展减权：** Skills、MCP、Hooks 和 Subagents 不能绕过 Kernel/Host 的安全合同。

## 四、组件和依赖方向

| 组件 | 职责 | 不拥有的权力 |
| --- | --- | --- |
| Kernel | Turn 状态机、模型步骤、工具意图协调、预算 | 不直接读取模型密钥或执行文件/网络副作用 |
| Provider | 厂商请求、流解析、响应规范化 | 不写权威日志、不执行工具 |
| Context | 安全裁剪、摘要、Checkpoint | 不改写事件事实和授权结论 |
| Event Store | 追加、读取、并发控制、恢复证据 | 不推断外部副作用成功 |
| Tool Scheduler | 工具快照、预检、独占屏障、调用排序 | 不绕过 Host 授权 |
| Tool Host | 独立执行授权、隔离、收据、取消/清理 | 不决定 Agent 的下一步推理 |
| Control Plane | 用户身份、命令幂等、授权与审计 | 不允许未验证客户端直接写数据库 |

接口合同应依赖方向单一：**高层 Kernel 依赖抽象，具体 Provider/SQLite/Linux 适配器不反向定义状态机**。共享合同可独立维护；部署时由组合根注入实现。

## 五、两种顺序

并行 ToolCall 的**实际完成顺序**可以不同于模型提出的**调用顺序**。可信事件要及时记录真实完成事实；下一轮模型可见 ToolResult 推荐按原始 ToolCall 顺序投影。两者不可在日志里偷换，也不能为追求有序投影拖延关键执行收据。

这是历史研究第 27 号报告支持的候选原则，最终实现须用反序完成与崩溃测试确认。

## 六、部署与演进

- 起始阶段：单机、单写者、少量受限工具，真实代码与测试再行恢复建设。
- 接入高风险工具前：验证授权、Host 隔离、收据与 UNKNOWN 阻断。
- 引入多 Agent 或远程 Worker 前：定义身份继承、执行位置、预算和旧 Epoch 失效语义。
- 技术栈采用 TypeScript/SQLite 或复用 Pi Core，均需要独立基准和许可证审查；目前没有最终裁决。
