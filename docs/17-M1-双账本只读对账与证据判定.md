# 17 · M1 双账本只读对账：Kernel Intent/Receipt × Host Execution Ledger

> 状态：**已实现只读、单 SQLite 快照、逐 ToolCall 的双账本证据归类**。没有自动修复、ToolCall 重放、Turn 恢复、人工审批接口、外部副作用幂等或 OS 沙箱。**任何对账结论都不能直接视为执行授权。**

## 一、为什么需要双账本

上一阶段 Host 在自己的 SQLite 表 `host_tool_executions` 中记录 `started / succeeded / failed`，Kernel 在 `kernel_events` 中记录完整 `tool.intent / tool.receipt / tool.result`。

即使两个表在同一 SQLite 文件，它们也不是单一原子执行操作：Host STARTED 到工具执行、Host FINISHED 到 Kernel Receipt 分别可能发生进程终止、IPC 失联、Token 过期。**没有 Receipt 不表示没有执行；Host 完成也不等于 Kernel 已确认结果。**

本轮新增 `packages/tool-reconciliation/src/index.ts`：

```ts
import { SqliteToolReconciler } from './packages/tool-reconciliation/src/index.js';

const observer = new SqliteToolReconciler('./agent.sqlite');
try {
  const report = observer.inspect('session-1');
  // report.calls: [{turnId, callId, name, intentSeq,
  //                 receiptSeq?, hostFenceToken?, kernelOutcome,
  //                 hostState, status, requiresManualReview}]
  // report.pendingTurnId / report.requiresManualReview / report.fullyVerified
} finally {
  observer.close();
}
```

`SqliteToolReconciler` 使用 `DatabaseSync(path, {readOnly: true})` + `PRAGMA query_only=ON`，在同一次 `BEGIN` 读取 Kernel 事件、Host 台账，并用同一次 SQLite 快照进行对账。这避免顺序读取两条不同连接的时间竞争。**不调用模型、工具或 Host，也不 acquire/release/renew Writer Lease，不写入新 Receipt。**

数据库中可能存在 M0/M1 旧会话却没有 `host_tool_executions` 表：观察者通过 `sqlite_master` 检查 schema，缺失按**没有 Host 证明**处理，不偷偷建表，不推断可以重试。如果连 `kernel_events` 都不存在，返回 `UNKNOWN_SESSION`。所有事件的 Session、Seq、Turn 顺序和 `inspectToolAudit` 完整性仍会 fail-closed 验证。

## 二、报告语义

| status | 典型组合 | 报告判定 |
| --- | --- | --- |
| `verified` | Host succeeded/failed 与 Kernel Receipt/Result 的名称、状态、内容一致 | 已有双方一致证据；**不能据此再次执行** |
| `intent_without_host` | Kernel 有 Intent，Host 表无该 Call ID | 未观察到开始，**不是未执行的证明** |
| `host_started` | Host 记录 STARTED，Kernel 无可信最终一致证明 | 可能执行过，必须对账 |
| `host_finished_without_receipt` | Host succeeded/failed，Kernel Receipt 缺失 | Host 与 Kernel 确认断点，必须对账 |
| `kernel_receipt_without_host` | Kernel 有 Receipt，但没有 Host 行（例如旧的进程内工具） | Kernel 自身状态已记录，但无独立 Host 证明 |
| `kernel_outcome_unknown` | Kernel 明确记录 outcome_unknown | 即使 Host 记录 succeeded，也不能自动修复或重跑 |
| `mismatch` | Host 与 Kernel 名称、状态、内容不一致 | 怀疑数据损坏或错误映射，保守审计 |
| `orphan_host` | Host 有执行行，Kernel 没有对应 Intent | 不应发生；可能是数据库不一致或越权写入 |

`requiresManualReview` 为 true 的条目包括所有非 verified 条目，以及任何未结束的 Turn。整个 Session 的 `fullyVerified=true` 仅表示**此只读比较没有发现未决状态**，并非 `AgentKernel.openSession()` 或任意工具重新执行的授权。调用方不得把 `fullyVerified` 或 `verified` 当成执行权限。**无论状态为何，自动 replay 一律不在本实现功能范围。**

审计数据刻意不返回工具原始参数、Receipt 内容、日志中的用户文本；可返回 ToolCall ID / 工具名 / token / Seq 等业务关联字段，仍需在正式控制台做租户级权限保护与脱敏。

## 三、工具日志完整性强化

本轮还强化 `packages/tool-audit/src/index.ts`：

- `tool.receipt` 必须有对应 `tool.result`。
- 两者 Seq **必须相邻**，因为当前 Kernel 在同一次 `EventStore.append` 事务批次里写入这两个事件。
- Receipt 与 Result 的身份、结果及内容必须一致。
- 孤立收据、非原子相邻结果、重复 Intent/Receipt 等异常返回 `CORRUPT_EVENT_LOG`，不把它们判为已成功执行。

这项检查同时用于 `AgentKernel.openSession()`，因此是对现有恢复防线的加固，并不是一个仅供报表使用的校验。

## 四、验证

`tests/tool-reconciliation.test.ts` 通过真实 SQLite + 独立 ProcessToolHost、内存事件日志构造及只读快照，覆盖：

1. 真正由独立 Host 执行并经 Kernel Receipt 确认后，Status 为 verified；
2. Intent 有、Host 从未观察到执行（包括旧 DB 没有 Host 表），仍不能推断可以重试；
3. Host STARTED 但没有 Receipt；
4. Host 已完成但 Kernel Receipt 未落库；
5. Host 与 Kernel 返回内容发生冲突，即使 Turn 已 terminal 也需核查；
6. 旧 Kernel 进程内工具有 Receipt 而无 Host，不能声称 Host attestation；
7. Explicit outcome_unknown 即便 Host succeeded 仍不能自动解除；
8. Orphan Host 执行行的审计拒绝；
9. 缺失 Session、损坏 Turn 流 fail-closed；
10. 只读观察前后数据库行、租约 Token、Host 表不发生变化；
11. 单独 Receipt 缺少 Result 被识别为损坏；
12. Receipt/Result 之间混入其它事件时拒绝作为原子对。

原有 Host/Kernel 的 SIGKILL、超时、租约被接管测试仍由历史测试覆盖。GitHub Actions 测试目标：Node 22.16.0 与 22.x，严格 TS TypeCheck + `npm test`。上一阶段 65 项，本轮新增 12 项，目标累计 **77 项**；最终数量和通过结果以对应最新 GitHub Actions 为准。

## 五、仍待落实

1. **可信人工审批与修复协议**：在验证 Host 身份/审计证据、用户授权、未决 Turn 生命周期后，才可能有受控追加的恢复事件。不能仅凭只读对账表自动补 Receipt 或触发重复 ToolCall。
2. **OS 强制隔离与数据库访问权限**：目前子进程与父进程同 OS 用户，对本地 SQLite 有原始写权限，恶意同权限进程能够伪造双账本；对账也不构成鉴权或防篡改证明。
3. **完整 Host 幂等/副作用执行协议**：外部副作用工具仍禁止，不能由只读演示工具的状态记录推断出 exactly-once。
4. **持续并发/恢复压测**：多进程长时间 crash、耗时工作负载、工作线程与大规模事件流、备份迁移等需要后续测试。
