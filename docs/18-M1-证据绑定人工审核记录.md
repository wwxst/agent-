# 18 · M1 人工复核记录：证据版本绑定、不可变审计与禁止自动重试

> 范围：**可信调用方提交人工复核批注**，不提供审批凭证、权限升级、Turn 恢复、收据修复、Tool 重放或 OS 沙箱。当前 `reviewerId` 是调用者声明的字段；必须由未来经过鉴权的服务端生成，**本模块自己并不验证身份或签名**。

## 目标与新模块

前一阶段 `SqliteToolReconciler.inspect(sessionId)` 使用同一 SQLite 只读快照对照 Kernel Intent/Receipt 与子进程 Host 的 started/succeeded/failed 台账；结果缺失或存在冲突时会得到 `requiresManualReview: true`。但缺少一个稳定存档人工调查行动的位置。

新增 `packages/recovery-review/src/index.ts` 的 `SqliteRecoveryReviewStore`：

```ts
import { SqliteToolReconciler } from './packages/tool-reconciliation/src/index.js';
import { SqliteRecoveryReviewStore } from './packages/recovery-review/src/index.js';

const observer = new SqliteToolReconciler('./agent.sqlite');
const report = observer.inspect('session-1');
observer.close();
if (report.requiresManualReview) {
  const reviews = new SqliteRecoveryReviewStore('./agent.sqlite');
  try {
    reviews.record({
      sessionId: 'session-1',
      reviewId: 'externally-generated-unique-review-id',
      reviewerId: 'identity-from-trusted-authentication',
      expectedEvidenceHash: report.evidenceHash,
      decision: 'investigate',
      reason: 'Need independent confirmation of the Host execution outcome.',
    });
  } finally {
    reviews.close();
  }
}
```

**不要将 `reviewerId` 直接信任为请求体提供的用户身份。** 在没有生产鉴权的当前项目里，示例仅供本地可信调用者测试，不能直接开放为 HTTP 写入 API。

## 事务性证据版本绑定

`ReconciliationReport` 新增 `evidenceHash`：

- 将 Kernel Session 全量事件（含 sequence、ID、类型、数据和时间）及 Host 全量执行状态按确定性顺序序列化并计算 **SHA-256**。
- 摘要用于检测审查起点的数据版本是否过时，**不是加密签名、不可抵赖证据或防恶意 DB 管理员篡改的凭证**。
- ReviewStore 在一次 **`BEGIN IMMEDIATE` 事务**内重新读取两个账本并校验 `expectedEvidenceHash`，随后插入不可变审核记录。任何 Kernel Event/Host state 更新会使旧 Hash 失效，抛出 `STALE_REVIEW_EVIDENCE`。
- ReviewStore 不修改 `kernel_events`、`host_tool_executions`、租约/Token，也不调用 `openSession()` 或 `runTurn()`。

**注意**：两次对账之间没有物理安全上的权限保证。拥有相同 SQLite 写权限的恶意进程可以修改数据库数据，本协议防止的是**正常可信进程的意外陈旧审核**，不是防篡改。

## 严格的审核合同

`ReviewRequest` 包含：`sessionId`、`reviewId`、`reviewerId`、`expectedEvidenceHash`、`decision`、`reason`。审核状态只有：

- `investigate`：需要继续调查，未作结果确认；
- `evidence_noted`：人工记录已查看部分证据，但**不授予恢复、补收据或重试权限**。

没有 `approved`、`allow_replay`、`resolved`、`execute` 等具有操作权限的状态或回调。**不会因为留下审核记录，就让 `AgentKernel.openSession()` 的 `RECOVERY_REQUIRED` 消失。**

表 `recovery_reviews`：

- `(session_id, review_seq)` 主键，`(session_id, review_id)` 唯一；同 Session 的 Review 按数据库写锁序列化，序号严格递增；
- 每条记录包含审核身份、Hash、决定类型、长度受限的原因及数据库时间戳；
- `record()` 只执行 INSERT，不开放 UPDATE/DELETE；同一 ID 重复提交 `DUPLICATE_REVIEW_ID`；
- `list(sessionId)` 只展示保留的审核历史，不表示 Session 已经能够重开；
- 已没有任何未决证据的会话，拒绝新增恢复审核并返回 `NO_REVIEW_REQUIRED`。

审核内容不可用来写入隐私或密钥；原因字段当前以明文存储，最长 2048 字符；正式服务需要鉴权、最小化存储、审计保留期、加密与脱敏。

## 同步修复：Tool Host 冷启动建库顺序

在既有 Host IPC 集成测试中，Node 22 曾偶发出现未决执行判定。上一版 READY 握手已存在，但父进程第一次创建 Lease/EventStore Schema 与子进程 Host Ledger 的 `PRAGMA journal_mode/WAL` 初始化可能并发。

`ProcessToolHost` 构造阶段现在先顺序初始化并关闭：

1. `SqliteWriterLeaseStore`
2. `SqliteEventStore`
3. `HostExecutionLedger`

然后才调用 `fork()`，由子进程继续独立校验 Fencing Token 和持久 Intent。这是数据库**结构的启动预热**，不是 ToolCall 准入，也不代替 Worker 的服务端验证。测试补充连续 10 次全新 SQLite 文件、先启动 Host 再启动 Session 的实际 IPC 冷启动路径，并在失败时采集 Host 状态/事件类型供诊断。**不能仅因单次通过便宣称跨平台竞态被数学证明根除。**

## 验证矩阵

`tests/recovery-review.test.ts` 新增 10 项：

- 审核可重开保留且不改动双账本、两个独立审核者序号连续；
- Kernel 日志追加或 Host STARTED/FINISHED 导致旧 Hash 失效；
- 相同 Review ID、空审核者身份、无效操作枚举及理由被拒绝；
- `evidence_noted` 不允许 Kernel 重开未决 Turn，不允许执行工具；
- 完整终态 Session 无需恢复复核，不能生成伪造恢复许可；
- 子进程在成功写入审核后遭 `SIGKILL`，重启仍能读取持久记录；
- 在序列号不变的情况下修改事件内容，Hash 会变化。

`tests/process-tool-host.test.ts` 新增 1 项冷启动压力测试（10 次 Host/Runner/SQLite 初始化）。

两版本 GitHub Actions 执行 `npm run check` + `npm test`。前一阶段为 77 项，本轮新增 11 项，合计目标 **88 项**；具体成功结果以 CI 为准。
