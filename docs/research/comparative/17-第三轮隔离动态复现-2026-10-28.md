## 1. 隔离动态实证：3 个测试

| 实验 | 真实观测 | 合同判定 | 限制 |
|---|---|---|---|
| **T02 反序并发** | 工具声明 `[a,b]`，返回数组 `[a,b]`；B 先完成时 Receipt 和投影均 `[b,a]`；A 先完成时均 `[a,b]` | **模型可见顺序受执行时序影响**，与建议的确定性声明顺序不符 | 调度器原代码 + Context 摘录；尚未运行完整 AgentKernel+FakeProvider 的探针 |
| **T-EX 独占上下文** | parallel 得到 `sessionId/turnId/callId`，exclusive 得到 `undefined` | **调用合同不一致**；可影响要求执行身份的独占工具 | 注册的独占工具为人工设计的只读测试工具 |
| **T-PREFLIGHT 写工具禁用** | 声明 `risk:write` 的工具被拒绝；实际执行次数 `0` | **当前调度器的只读策略符合预期** | 不等于证明所有 Host/OS 隔离路径都安全 |

三个 Node 测试全部通过；含义是**测试成功复现了观测行为**，不是三个架构目标全部通过。`isolated-test-output.tap` 保存了原始输出。

### 为什么 T02 是架构问题，但不该被夸大

`executeBatch()` 先按模型顺序返回结果数组，但 `onResult` 为每个并发工具在完成时单独持久化收据。`AgentKernel.projectContext()` 按事件发生顺序附加 `tool.result`。因此相同模型输出可因异步工具完成先后而形成不同下一轮模型输入。

需要区分：

- **执行事实排序**：应保留实际完成顺序，方便审计和恢复。
- **Provider 结果投影排序**：建议按照模型声明的 ToolCall 及其 ID 进行确定性关联和排序。

此现象**不必然违反**所有模型 API 的工具结果规范，因为结果保留了 Call ID；不能凭此推断真实任务必定失败。它证明的是当前投影没有独立的确定性顺序合同。

### 为什么 T-EX 是具体可修复问题

`tool-scheduler/src/index.ts` 并发路径调用 `invoke(item, signal, assertLease, context)`，独占路径调用 `invoke(item, signal, assertLease)`。两者是同一工具接口，后者缺少 context。

如果未来注册具有真实主机身份验证的独占工具，它可能因缺少 Session/Turn/Call 身份而拒绝执行或产生错误结果。建议将这一合同纳入所有调度分支的回归测试。

## 2. 与 Pi 的直接交叉核对

Pi 当前 `agent-loop.ts` 的 `executeToolCallsParallel`：先按模型给出的 ToolCall 顺序 `prepareToolCall`；将执行回调存储为数组；`await Promise.all(...)` 得到按原始数组对应位置的 `orderedFinalizedCalls`；最后顺序 `createToolResultMessage()` 和 `emitToolResultMessage()`。

**这支持一个机制级借鉴：异步完成事件与模型历史回填是两件事。** 不需要因此采用 Pi 的全部运行时，也不能因此认为 Pi 的外部副作用恢复更强。

- 源码：https://github.com/earendil-works/pi/blob/a92283056d915c758799fcd904948ff0cb42628c/packages/agent/src/agent-loop.ts#L595-L670

## 3. 与 Codex 的直接交叉核对

Codex 的 `StepContext` 对当前模型采样绑定一个 `ResolvedStepSettings` 快照、Token Budget、执行环境和最终工具计划；`ToolRouter` 在 `ToolInvocation` 中传入该 StepContext。`tools/orchestrator.rs` 负责执行审批、环境选择和受限制的沙箱重试。

这些静态事实说明我们应当对每次执行建立**统一版本化的采样与执行合同**，而不仅是 `toolSetVersion`。但本轮未完成特定 Feature Gate 下全部审批顺序的动态验证，暂不建议照搬 Codex 的重试流程。

## 4. 与 Claude 的直接交叉核对

用户提供的 5,201 项 ZIP 样本记录了 Win32-x64 CLI 2.1.304，`cli_executed:false`；Desktop/SDK 是独立的双向控制与生命周期宿主。证据材料定位了 `tool_use` → StreamingToolExecutor → Permission → ToolHost/tool_result 链；SDK `resultReceived` 不与回调 drain 或 `idle` 完全等价。

本轮**只核对证据内容与版本标识**，没有运行 CLI、进程级权限模拟或 Windows 沙箱，因此不能给 Claude 的副作用恢复能力下动态通过结论。不要用 SDK `result` 当作“所有子任务、外部工具与权限请求已完全结束”的证明。

## 6. 暂不决定的事项

这轮证据支持**先记录待修复缺陷与验收合同**，不支持立刻决定：

- 更换 TypeScript/Rust 或整套 Agent Loop；
- 删除 SQLite Journal、Intent/Receipt 和 Fencing；
- 直接把 Pi 或 Codex 实现当自己的强依赖；
- 放开真实 Shell / 写工具而不审查 Trusted Host；
- 宣称三家中任一家“绝对领先”或我们整体架构已经更好。

### 最小、可证伪的技术假设

**H1**：保持现有 Intent/Receipt 不变，只调整模型可见 ToolResult 的稳定投影，有望消除异步完成造成的 Context 顺序漂移。

**H2**：独占工具上下文传递一致化，是在引入文件/Shell 工具前应修复的低成本正确性问题。

**H3**：Pi 的顺序投影、Codex 的 StepContext、Claude 的流式执行都能给我们局部改进证据；最终组合方案仍必须经过 T01–T12 和真实任务对照。
