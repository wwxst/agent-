# 12 · 四内核执行事实与持久化保证：源码证据审计

> 审计日期：2026-10-26。对象：Pi [d5b3de22](https://github.com/earendil-works/pi/tree/d5b3de22d0e24a3e9c38a9410d3329b099717283)、Codex [970111f6](https://github.com/openai/codex/tree/970111f6cb62cc02fe36a82ea7d71b37a2889c97)、DeepSeek [22ddee37](https://github.com/deepseek-ai/deepseek-harness/tree/22ddee3792402c3e70ec5f86a63c3e3e895a2f60)、用户 Claude Code CLI 2.1.304 / Desktop 3.1623.1 发布包及 2.1.88 提取源码。

**原则：本篇区分“代码存在”“逻辑保证”“进程崩溃”“操作系统掉电”“外部副作用”五层证据。未执行动态故障注入。不能声称任何参考项目已实现任意外部操作的 exactly-once。**

## 1. 先建立不可混淆的事实层

| 层 | 含义 | 不能据此推出 |
| --- | --- | --- |
| 模型消息 | Provider 发出 assistant/tool_use/tool_result | 对外执行一定发生或成功 |
| 内存 Event/Transcript | 本进程已观察到并更新状态 | 磁盘历史一定存在 |
| 文件写入/Flush | 应用等待文件 I/O/缓存完成 | 断电后一定保留；与 fsync 是不同操作 |
| 稳定存储提交 | 明确完成 fsync / fdatasync 或 DB 的持久事务合同 | 另一个系统的网络调用也已持久成功 |
| Host Receipt | 可信执行宿主记录开始/结束与幂等标识 | 任意外部系统均恰好执行一次 |
| 模型可见结果 | 可由 Tool Adapter/Hook/摘要加工的表述 | 可以覆盖 Host Receipt 的原始事实 |

用于自研的四条根本要求：**先持久接受命令才回复 Accepted；副作用执行前持久记录意图；模型可见结果与 Host Receipt 不同对象；非幂等结果未知时暂停协调，不重放执行。**

## 2. Pi：真正的产品级历史机制与写盘语义

直接源码：[SessionManager](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/session-manager.ts#L987-L1210)。

- `fileEntries/byId/leafId` 形成会话树，`branch()` 移动叶指针；原节点保持不变。[L1529–1675](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/session-manager.ts#L1529-L1675)。
- `_appendEntry()` **先更新内存**的 `fileEntries/byId/leafId`，再调用 `_persist()`；文件首次用 `openSync('wx')`，后续调用 `appendFileSync`。[L1140–1202](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/session-manager.ts#L1140-L1202)。
- 此调用片段中没有显式 `fsyncSync` 或回滚内存更新的事务；**不能据 `appendFileSync` 推出断电耐久或 ToolCall Intent 原子性**。这不是声称整个项目永不做 fsync，只是本已审计路径没有该保证。
- `appendContextEdit()` 单独记录针对活动路径消息的修改；可供模型历史投影，但不应作为重写审批/Host 收据的能力。

### 需要借鉴的不是“JSONL 最好”

Pi 的会话树、分支与压缩历史非常值得借鉴；然而 **Coding Agent 历史记录** 与 **可靠作业事件日志** 是两个用途，不能把可重放聊天树直接作为副作用事务。

## 3. Codex：canonical Rollout 和 SQLite Index 的确分层，但 flush ≠ fsync

直接源码：[Local Writer](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/thread-store/src/local/live_writer.rs#L414-L470)：

1. 按 Thread 获得 live writer lock；
2. `RolloutWriteOp::AppendItems` 调 `record_canonical_items`，随后等待 `recorder.flush()`；
3. 成功后尝试 `materialize_to_sqlite`；
4. SQLite 物化失败仅记录警告，Rollout 仍被视作 canonical source，可重建投影。

继续追 [RolloutRecorder::flush](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/rollout/src/recorder.rs#L1079-L1135)：

- `record_canonical_items` 是发送 `RolloutCmd::AddItems` 到后台 writer；
- `flush()` 发送带 ACK 的 `RolloutCmd::Flush` 并等待 Writer 结果；
- Writer `write_pending_with_recovery` 有错误后关闭并重开文件、保留未写后缀、再试一次机制。[L1828–1960](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/rollout/src/recorder.rs#L1828-L1960)；
- 本次直接检查的 `write_pending_once` 使用 `writer.file.flush().await`；[JsonlWriter::write_line](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/rollout/src/recorder.rs#L2140-L2162) 同样使用 `File.flush()`。

**关键修正**：上面证明排空了 Rust 文件写入缓冲并处理写入错误，但没有在这条代码路径找到 `sync_all()/sync_data()`。所以不能把它写成**物理掉电保证**，也不能因 “Codex 使用 Rust/SQLite” 就认为外部副作用 exactly-once。

> 自研判断：**canonical log 与可重建索引分离**是优秀设计；但是具体落盘屏障必须由自己的 SQLite 同步设置、事务和故障测试定义，不能照抄 `flush` 名称。

## 4. DeepSeek：必须把两个不同的 append 路径分清楚

源码：

- [SessionPersistence JSONL Handle](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/session/session-persistence-jsonl/src/storage.ts#L183-L355)
- [存储后端 persistBatch](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/session/session-persistence-jsonl/src/index.ts#L905-L942)
- [跨进程写锁](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/session/session-persistence-jsonl/src/lease.ts#L70-L135)

这套项目存在**两种名字都叫 append、持久承诺不同的操作**：

1. **进程内 Session.append(...)**：先更新实时 Session 事实；持久化服务订阅 live event 后可能先放入 `buffered`，通过定时批处理 `drainLive()` 写入。根进程关闭的时序可能导致某些最终 Session 事件尚未持久保存，项目 README 也说明了这一限制。
2. **显式 SessionHandle.append(events)**：在 `storage.ts` 中将参数先校验/快照，再排队执行 `persistContiguous(batch)`；后者调用底层 `persistBatch`，完成后才推进 Cursor，代码注释和 API 语义明确它是一次已完成的后端持久追加。对已 materialized 的 Handle，`flush()` 可直接返回，因为其追加完成本身已有后端持久合同。

因此，早前“DeepSeek 只有 flush 才真正持久化”这句话对**显式 Handle.append** 不准确。真正缺口是：实时 Session 事件流**可能没有等待显式 Handle 追加完成**，它会有缓冲和关闭窗口。

另外：

- [单写 Lease](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/session/session-persistence-jsonl/src/lease.ts#L70-L135) 在 POSIX 使用文件锁、核对 inode/dev，Windows 使用原生锁句柄，防止另一个进程并发取得写权限；
- [generation.ts L714–842](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/session/session-persistence-jsonl/src/generation.ts#L714-L842) 的**迁移发布路径**使用 `FileHandle.sync()`、独占临时文件、发布和目录同步；注意这证明的是迁移路径，不意味着我们已经审计了所有普通 append 的底层写盘行为；
- [恢复](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/core/agent-loop/src/index.ts#L765-L813) 先获取 write handle、读物理有效日志，再用 `interruptedTurnClosers` 补齐缺失的 ToolResult/Step/Turn 终态；**补齐历史不是证明外部工具没执行**。

## 6. 对自研 EventStore 的可执行决策依据

由以上事实支持以下规则（不是在宣称四家都做到）：

1. **存储阶段明确**：Accepted/IntentCommitted 必须有真实持久事务提交，不得使用 UI / Session 内存 append 充当 ACK。
2. **两个独立对象**：`AgentHistoryProjection` 用于模型，`ToolExecutionReceipt` 用于副作用追踪；允许模型结果被扩展改写，但不允许修改原始执行事实。
3. **写单元与提交顺序**：一条写事务先提交 Tool Intent 和参数/审批摘要，Tool Host 再启动真实副作用；回执通过带版本的事件另行提交。
4. **重放默认不执行工具**：重放只恢复事件投影；需要继续外部执行须通过明确的幂等等级/收据协调。
5. **数据库落盘设置需实测**：本项目若选择 SQLite，本地安全配置与断电模拟另做独立验证；单一组件的 `flush` 函数名不能代替持久性测试。
