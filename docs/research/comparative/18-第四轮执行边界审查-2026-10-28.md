## 1. 本轮 6 项新增动态观察

| ID | 使用精确调度器源码的动态结果 | 解读 / 限制 |
|---|---|---|
| B01 | 声明 `risk:'read'`、并行的工具写入了临时文件，返回 succeeded | `risk` 是注册元数据；**只验证了进程内工具路径**，未突破独立 Host 的 OS 沙箱 |
| B02 | `assertLease()` 在 Tool Body 启动前验证一次；执行中将模拟 lease 改为无效，工具仍可返回 succeeded | 调度器没有内建执行中强制冻结；完整 Kernel 和受信 Host 存在额外校验，不能一概否认 |
| B03 | 在工具已启动时调用 `AbortController.abort()`；工具忽略 signal 后依然返回 succeeded | 协作取消≠强制停止；这里只是 Scheduler Receipt，不代表最终 `turn.completed` |
| B04 | ToolRegistry snapshot 后新增工具，新工具在旧 snapshot 中不可见 | 保留既有模型 Step 工具身份冻结的有效部分；冻结对象不等于冻结闭包或 OS 状态 |
| B05 | 并发 Tool A 的 onResult 写入回调报错，A 与 B 的工具体及 B 的回调均运行；批次最终抛出原始错误 | 维持错误传播和并发排空，但不能将失败返回当成“没执行过任何工具” |
| **B06** | `risk:'read'` 工具的 `parse()` 写入文件后抛异常，`execute()` 从未调用；结果为 `INVALID_TOOL_ARGUMENTS` | **在 Preflight 阶段也运行受信 JS**，接口注释无法强制参数解析纯函数；插件来源必须视作执行信任边界 |

原有 3 个隔离复现同样在本轮重新运行：T02 模型投影的完成顺序依赖并发时序；T-EX 独占工具丢失 execution context；T-PREFLIGHT 声明 `risk:'write'` 的工具被拒绝执行。**合计 9/9 观察测试通过**，详见 `fourth-round-test-output.tap`。

### 需要特别避免的误读

- B01、B06 中的 `execute()` / `parse()` 是由本地**可信调用方主动注册**的函数。模型发一个普通 JSON 工具请求，**不会自动赋予其任意 JavaScript 执行能力**。问题是将来引入不完全可信的第三方插件或适配器时，是否仍能将这些函数直接放进 Kernel 进程。
- 这不是 `startEnforcedToolHost()`、Bubblewrap、seccomp 或 cgroup 的绕过测试。受信 Host 当前只开放 `read.echo/read.sleep` 演示白名单，需要独立进行 Host 入场及拒绝路径验证。
- B02 在 `assertLease()` 首次成功后通过手动改变模拟租约状态构造边界窗口。真正 Host Ledger 可能额外核查 Fencing Token；而已运行的外部副作用也不能靠重复 lease-check 回滚。
- B03 的 succeeded 是工具确实执行完后返回的 Scheduler 观察值。如果上层 Turn 收到 Cancel，仍应单独处理最终 Turn 状态；不能从这一条测试推出整个 Kernel 错误提交了已取消 Turn。

## 2. 与三家参考内核的直接对照

### Pi Agent：Hook 是扩展机制，不是任意插件的 OS 权限限制

`packages/agent/src/agent-loop.ts` 的 `prepareToolCall()` 先选择工具、运行 `prepareToolCallArguments()` 与 `validateToolArguments()`，然后调用 `beforeToolCall`。只有无立即错误时才交给 `executePreparedToolCall()`。并发模式用 `Promise.all` 收敛最终结果后按模型原序生成工具结果消息。

因此，Pi 的核心适合学习 **明确的 ToolCall 准备/执行/结果阶段**，但其 `beforeToolCall` 不是 OS 沙箱。工具自身的 `prepareArguments` / `execute` 函数是否纯净仍依赖来源信任和宿主隔离。

Pi Coding Agent 的 `session-manager.ts` 还有一个应避免误读的持久化区别：`_appendEntry` 可在文件写入抛错时撤销内存中的追加；但 `_rewriteFile()` 使用 `openSync(path,'w')` 直接截断旧文件并逐行写回。该代码可以静态确认**覆盖写入不是显式原子替换**，但本轮没有运行 Pi 崩溃实验，不能断言实际出现了用户数据损坏。

### Codex：把安全权限放进执行过程，而非工具元数据

当前 `step_context.rs` 的 `StepContext` 包含固定模型设置、MCP binding、ToolRouter、环境及授权相关快照。`tools/orchestrator.rs` 明确区分 `ExecApprovalRequirement::Skip / Forbidden / NeedsApproval`，先处理审批，再构造 SandboxAttempt 并执行。遭遇沙箱拒绝后的处理受 `escalate_on_failure`、审批和部署环境限制，不意味着任意命令都会无条件提权重试。

对我们最有价值的是 **ToolCall 身份 + Step/Policy 快照 + Host 实施权限** 三者统一，而不仅是复制一个 approval enum。

需要继续针对 Codex 运行的动态反例：沙箱执行已产生部分本地/网络副作用后被 Denied，后续更高权限重试如何防止重复效果。静态源不足以证明一般性的 exactly-once。

### Claude Code：权限、控制协议与真实 ToolResult 分层

直接复核了用户提供的逆向 ZIP 中 `evidence/local-agent-verification.json` 的 8 个源码锚点，全部在 CLI/桌面 JS 模块**精确字符偏移处匹配**（脚本和结果在本证据包）。其中含 Agent Loop、Claude Messages 创建、工具执行、`can_use_tool`、`control_response` 及 Desktop SDK 输入输出协议。

用户提供的资料显示 SDK 与 CLI 通过带 request_id 的双向 JSONL 控制请求通信；`tool_use_id` 是独立身份。宿主 UI 的批准不是模型运行时全部权限决策，CLI 还有校验和拒绝流程。`resultReceived` 与 `sessionState=idle` 也是不同的生命周期事实。

静态锚点校验**不代表**真实 API、审批 UI、OS sandbox 或崩溃恢复已经运行测试。CLI 2.1.304 为 Windows 可执行文件，当前 Linux Node 环境不能直接完成其产品级动态复核。

## 3. 本轮形成的候选架构硬门槛（不是架构定案）

1. **可信代码边界**：第三方插件的参数 `prepare/parse`、beforeHook、execute 都不得默认拥有 Kernel 的文件/网络/凭据访问权限；如果需要在 Kernel 进程运行，必须标为完全可信并接受审计。
2. **授权与执行同源**：危险工具必须由同一可信 Policy Root 评估原始参数、上下文和目标资源；最终 Host 针对同一身份/参数摘要/权限版本实施限制，不能仅相信工具 `risk` 标签。
3. **取消不伪称撤销**：分别记录 cancel requested、process terminated、execution settled 与外部副作用 unknown；不要将它们压成一个 boolean。
4. **执行事实与模型历史分离**：Host Receipt 可以按完成顺序提交；模型可见 ToolResult 应按明示的稳定调用身份及顺序投影，不改写原始 Journal。
5. **失败不盲目重试**：审批升级、沙箱拒绝、进程退出、回执丢失均需核对副作用状态；未知状态必须阻断可能重复副作用的自动恢复。
6. **冻结 Step 能力而不是只冻结工具名**：绑定工具实现版本、环境、Policy、MCP 列表、允许的资源边界，并定义热更新时的影响范围。
7. **可验证完整执行**：上面每条要求须有真实 Tool Host 和真实场景的功能/拒绝/故障注入测试，而不只是类型声明。

## 5. 阶段性判断

这轮**没有决定重构哪一个 package，更没有宣布自研比三家更安全**。实证可以支持的判断更窄但更重要：

- 现有 `ToolScheduler` 的并发排空、`risk:write` 拒绝、工具目录快照具备合理基础。
- 现有进程内 `ToolDefinition` 是 **trusted-code API**，并非 untrusted plugin sandbox；若将它误当策略强制边界，就会在 `parse` / `execute` 阶段形成事实漏洞。
- 必须把“任何插件在什么权限下执行”纳入所有候选架构的正式审核；Codex 的 Step + Policy + Sandbox、Pi 的阶段化工具模型、Claude 的跨进程控制是三个互补参考。

**严格区分已证实与待测，最终架构继续暂缓决定。**
