# 11 · 四内核跨项目一致性不变量与最终架构评审门槛

> 研究迭代 2026-10-25；**候选约束而非最终 ADR**。来源为固定 Git 提交和 Claude Code 2.1.304 JS 实证。测试状态：`NOT RUN`，无任何外部 Agent 运行结果。

## 1. 各项目“有 Session/Event”仍然有本质差别

| 参考内核 | 核心状态来源 | 落盘边界 | 易误解的地方 |
| --- | --- | --- | --- |
| Pi Agent Core | `Agent` 的进程内 Messages/Event | 上层 `SessionManager` 通过 JSONL 文件持久化产品会话树 | 低层 Core 没有持久任务日志 ≠ 整个 Pi 产品没有历史持久化；文件同步追加也不等于副作用事务 |
| Codex | Rust Session、StepContext、Thread Store | LocalWriter 的 AppendItems 调 Recorder.flush，随后尝试物化 SQLite 索引 | SQLite 不是 Rollout 的唯一权威；flush 函数不等于已做掉电/OS 测试 |
| Claude Code | 本地 Agent Loop、ToolResult、Transcript 与 SDK/Host 控制 | 有保存与 Resume 路径，最新版崩溃语义未全审计 | 补齐孤立 ToolResult 不能证明外部 Shell 没有执行 |
| DeepSeek Harness | Session append-only Event + Inbox/History Projection | SessionHandle `append` 可缓冲，只有 `flush` 声明明确持久性屏障 | Event Append ≠ 磁盘提交；Root 关闭时最后 Turn End 可能没保存 |

**我们的候选规则**：只有 Journal 确认的事件才是 Kernel 的可恢复事实。模型上下文和 UI Snapshot 只是投影；Tool Host 是物理副作用状态来源。所有将 `event` 命名为 `durable` 的地方都必须能说明准确屏障。

## 2. 从源码抽取必须维持的十二条执行不变量

| ID | 不变量 | 源码启发 | 必需实验 |
| --- | --- | --- | --- |
| I01 | 同一 Session/Turn 的控制变更有单调版本与明确目标 | Codex `expectedTurnId`；DeepSeek 独立 Inbox | 重复/迟到 Steer 不能误投 |
| I02 | Step 用统一版本的 Model/Context/ToolSet/Policy | Codex StepContext；DeepSeek ToolSet resolve | 并发热更新不改变已批准调用 |
| I03 | 完整解析的 ToolCall 才可通过 Schema/Policy 准入 | Pi StopReason=length；Claude StreamingToolExecutor | 半个 JSON/截断参数执行 0 次 |
| I04 | 工具实际调度符合冲突关系和资源预算 | Pi 全批串/并行；DS 独占屏障；Claude 并发安全 | 读/写/跨目录/后台竞争 |
| I05 | 每个 ToolCall 在模型历史中恰有一个规范结果 | 四套均有不同补齐逻辑 | Unknown/Abort/拒绝时不孤立 |
| I06 | 模型可见结果可以经 Hook 变换，但不能改物理执行事实 | Pi Extension `tool_result` 修改；DS PTC result shaping | Hook 改 `isError` 不改变 HostReceipt |
| I07 | 只要工具权限变大或参数变化，旧审批不再有效 | Codex 审批 CacheKey；Claude 权限链；DS Guard | 输入摘要不匹配被拒 |
| I08 | 沙箱是否生效只由 Tool Host/OS 证据确认 | Codex Sandbox；Claude Windows argv；DS partial enforcement | 不支持的隔离能力 fail-closed |
| I09 | 权威日志先于向客户端声明持久状态的 ACK | Codex Rollout / DS append–flush 差异；Claude Bridge ACK 风险 | commit/广播/崩溃交错 |
| I10 | 恢复工具调用按收据区分成功、失败、未知结果 | Claude 后台 Shell、DS interruptedClosers | 非幂等 ToolCall 结果未知不重执行 |
| I11 | 压缩只影响模型 Context Projection，不删除任务事实 | Pi CutPoint/SplitTurn；Codex compact；Claude compact | 缩短 Context 不改变审批/工具状态 |
| I12 | Child/Background 具有独立身份、减权、预算和退出清理 | Claude ChildAgent；DS Scope/Agent Team | 父子取消、Crash、Host 换绑 |

以上是**我们的设计目标**，不是四套参考内核都完全满足的认证结果。

## 3. 三种 Tool Scheduler 方案应该用数据取舍

| 方案 | 参考来源 | 长处 | 潜在代价 |
| --- | --- | --- | --- |
| S1 整批串行/并行 | Pi Agent Core | 最清晰，易测 | 一个独占工具可使整批失去并行机会 |
| S2 同组并发 + 独占屏障 | DeepSeek Harness、Claude 部分路径 | 平衡性能和因果有序 | 安全分类通常是一元布尔，不识别资源交叉 |
| S3 明确资源读写集 + 冲突图 | 我们自己的候选增强 | 可并发独立写目标，避免冲突 | 资源集合提取、符号链接与跨进程锁都难实现 |

**决策门槛**：先在 M1 用 S2 保守实现，复杂文件/网络副作用默认独占；只有 K02/K03/K07/K17 等测试通过，并能准确识别跨 Host 冲突时才引入 S3。不要因为理论上可并行，就引入不可验证的安全模型。

## 4. 单一审批原则与多层 Hook 的关系

从实际源码看：

- Pi `beforeToolCall` / `tool_call` 可 block，扩展允许改变 ToolResult；
- Codex `request_approval` 先考虑部分 policy 拒绝，再请求 Hook，最终 Reviewer/Guardian 参与；
- Claude Code SDK 与 Hook 在特定 ask 分支可能有竞争，需要处理迟到响应；
- DeepSeek 工具 `pre-execute` 可请求 approval，再经过 Guard 这一安全否决层。

**可执行候选合同**：

```ts
type ApprovalContext = {
  sessionId: string;
  turnId: string;
  toolCallId: string;
  canonicalArgsHash: string;
  toolVersion: string;
  policyVersion: string;
  hostIdentity: string;
  expiry: number;
}
```

模型、Hook、用户 UI 可以提出请求和提供决策输入，**只有可信 Policy/Approval Root 的事务提交可以生成 Authorize Token**；ToolHost 必须核查 Token 与实际参数、路径和隔离版本匹配。任何“允许型 Hook 先返回”都不构成绕过不可变 Deny 规则的依据。

## 5. 用户发“停止”，到底是哪一种操作？

| 状态转移 | 不同项目中的可见机制 | 自研定义 |
| --- | --- | --- |
| Steer | Pi 队列、Codex `expectedTurnId`、DS next-step | 新输入插入下个安全 Step，不默认终止工具 |
| Interrupt | Codex `turn_interrupt` 可能等待 TurnAborted；Claude Shell 的旧版 `interrupt` 可继续后台运行 | 中断交互/当前 Model Step，结果要观察 |
| Cancel | Tool Signal 传播、进程 kill 尝试、合成 ToolResult | 请求取消，不保证外部副作用被撤销 |
| Background | Claude 长时 Tool、DS 子任务/程序环境 | 明确独立 Task ID、可查询状态与限额 |
| Timeout | Shell、PTC Runtime、Provider | 受预算强制截止，终态可能是 Unknown |

因此客户端不能只暴露一个无法解释的 `stop` 并假设远端资源完全释放。

## 6. 做最终技术选型之前必须通过的评审

### GATE A：基础事实（静态研究）

- 四套方案的最小执行/工具/Context/Session 路径有源码与固定版本。
- 严格区分 Core 与产品宿主；避免把 Pi Core 的缺失推断为产品不存在。
- 能复核 Compaction 和 Subagent 的输入来源与保留事实。
- 所有“沙箱生效”“持久成功”“取消完成”都标明具体事实等级。

### GATE B：自己的 M0 可执行不变量测试

- FakeProvider/FakeHost 下 ToolCall ID、状态转移、断流、时间预算、重复命令按 I01–I12 通过；
- 模型可见 ToolResult 与 HostReceipt 分离；
- 任何插件无法直接覆写可信 Kernel 的决策状态；
- 单写、版本锁、重复 ID、错误 Context Projection 可离线复现。

### GATE C：Host/数据库/平台故障注入

- Kill/Crash 在 `intent-commit / tool-start / tool-complete / flush / event-broadcast` 各点发生时语义清楚；
- Linux/macOS/Windows 任意不支持的沙箱能力不得被静默模拟；
- 可检索日志里保留真实失效原因和不确定状态；
- 并发与取消测试证明没有重复危险副作用。

### GATE D：对照实验后冻结 ADR

- 将至少 S1/S2 两个 Scheduler 在相同 Mock 和隔离真实工具环境下比较；
- 将 JSONL/SQLite/其他事件存储方案做一致性/延迟对照；
- 测量 Context Compaction 保真度与失败成本；
- 最终技术选型写独立 ADR，先由维护者审阅，不把研究结论自动升级为 Accepted。

## 7. 当前实现和研究状态

**四套源码“主干已查”；细分功能全分支和端到端故障测试“未完成”。** 用户请求的是长期可靠的自主 Agent 内核，所以研究文档不应因篇数多而宣布完成。当前可以做候选接口评审，但仍不建议“凭印象”冻结数据库、OS Host、插件运行时或工具调度策略。
