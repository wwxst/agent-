## 2. 精确分层：哪些经过了完整 Kernel？

| 测试 | CI 观察结果 | 运行覆盖范围 | 合同判断 |
| --- | --- | --- | --- |
| T02 | 模型申明 A→B，但 B 先产生 Receipt 后，下一次 FakeProvider 收到 B→A 的 ToolResult | **完整 AgentKernel + EventStore + ToolScheduler + FakeProvider** | 模型结果投影与真实完成时序耦合，模型可见上下文在相同调用声明下可能不同 |
| T-EX | 独占调度路径 `execute()` 收到 `undefined` context | **真实 ToolScheduler**，非整条模型调用链 | 与并行工具执行上下文合同不一致 |
| T-OBS | `onDelta` 抛异常，`runTurn()` 返回 `status=failed`, `errorCode=KERNEL_OR_PROVIDER_ERROR` | **完整 AgentKernel + FakeProvider + EventStore** | 展示/监听异常可以改变 Turn 终态；需定义是否隔离 |
| B01 | 登记 `risk=read` 的进程内工具写入临时文件仍成功 | **真实 ToolScheduler** | 元数据声明不构成 OS 沙箱强制边界 |
| B06 | `parse()` 写文件后抛错；执行体未运行，但文件已修改 | **真实 ToolScheduler** | untrusted `parse` / extension 在获得执行授权前运行的风险边界必须清晰 |

这里的 `PASS` 是“观测行为符合测试断言”而非“安全要求通过”。这些测试证明**具体代码路径的事实**，不证明外部恶意调用能控制受信任的 `execute` 或 `parse` 函数，也不证明独立 Linux Tool Host 存在逃逸。

## 3. 何时属于已证实，何时仍是未知

- **已动态证实**：固定提交的 T02 与 T-OBS 完整 Kernel 路径；T-EX、B01、B06 的真实 ToolScheduler 运行路径；Node 22.16.0 和 22.23.3 下重复出现。
- **尚未动态证实**：生产 Provider/HTTP 流、独立 Process Tool Host、Linux Sandbox/Namespace/Seccomp、SQLite WAL 断电安全、外部 API 副作用恢复、Subagent、Codex/Pi/Claude 的同条件执行。以上不得当作“已通过”。
- **不建议直接将临时观察测试合并进 `main/tests/`**：它们是在断言现有不理想行为，修复后本来就应该改变。长效回归应改成规范性断言（例如模型结果固定原 ToolCall 声明顺序、工具 Context 始终完整）。
- **对比边界**：Pi 的有序模型结果回填目前是锁定源码级事实，不是本次动态横向基准；Codex 的 `StepContext`/审批与 Claude 的权限/SDK 路径仍是静态分析。
