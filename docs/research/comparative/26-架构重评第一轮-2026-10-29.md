# 26 · 架构重评第一轮：先验证参考方案，再决定自研方案

> 日期：2026-10-29。基线：`main@cf9374c9234bff9407c2d293a83530943e0b796a`。性质：**静态源码与现有实现的第一轮重评，不是最终架构裁决**。本报告没有运行 Pi/Codex/Claude/DeepSeek 四套产品的同条件基准；凡未运行者均不得标记为动态通过。

## 0. 结论先行

用户已经明确：项目的目标是做出更好的 Agent Kernel，而不是维护既有实现。因而第 14 号报告中的技术推荐不能因已写成文档、代码或已合并而自动成为事实标准。

当前自研内核**尚未证明整体优于任何一个参考内核**。我们已实现一些值得保留的工程基础，但当前工作重心有偏移：持久化、审计、Lease、Workspace 文件提交和收据补记不断增加，完整的模型工具执行与 Coding 工作流却还没有接成一个端到端产品内核。下一步应先比较、测量、重新取舍，不再继续扩大 Workspace 双账本/人工补记链。

这不表示前几轮代码“全错了”。它们提供了可复用的实验、测试与安全边界；但是否继续保留每个设计，必须重新举证。

## 2. 当前实现的第一轮核对

### 2.1 Loop：循环已存在，但职责集中

`packages/kernel-core/src/index.ts` 中的 `AgentKernel.runTurn()` 同时承担 Turn Admission、Steering 消费、工具集快照、上下文准备/压缩、Provider 流处理、Token 预算、工具 Intent/Receipt/Result 写入、取消、Lease Fencing 和终态处理。它是一个约 26 KB 的核心源码文件。

这让关键不变量集中、容易沿调用链审查；代价是 Loop、Step 组装、持久化协调和生命周期逻辑耦合较深。**不能仅为了“模块化”就拆成更多包**，但应先把可独立测试的 Step 执行合同写清楚，再判断是否需要拆分。

Pi 的 `agent-loop.ts` 将外层 Follow-up 与内层工具/Steering 循环分开，接口较容易读懂。第一轮建议：借鉴它清晰的循环语义；不要复制其产品层会话存储，也不要预设 Pi 的整体可靠性胜过当前实现。

### 2.2 StepContext：已有工具快照，但还不是完整的执行快照

当前内核在每个模型 Step 调用 `tools.snapshot()`，并将 `stepId/toolSetVersion/tools` 传给 Provider。这是正确的起点，能避免同一 Step 中工具注册表变更导致模型看到的工具集与实际执行工具不一致。

与 Codex 的 StepContext 思路对照，当前对象还没有统一固定 Provider/模型配置版本、Policy/Approval 版本、Context/Checkpoint 身份和预算预留。由于当前 M0 仍拒绝写工具，这不应被误报为已绕过审批；但在开放写工具之前，必须明确哪些值是一次 Step 的不可变输入，哪些允许在 Step 间变化。

**暂定决定：借鉴 Codex 的快照原则；先定义最小合同与竞态测试，再决定字段，不照抄 Codex 的 Rust 结构。**

### 2.3 工具调度：安全基线保守，结果顺序合同需要明确

当前 `ToolRegistry.modelSpecs()` 只把 `risk === 'read'` 的工具暴露给模型；`preflight()` 对其他风险级别拒绝执行。这意味着当前 Kernel 是只读工具循环，**还不是可自主编辑代码的 Coding Agent**。这是明确的安全边界，不是可用性完成。

`executeBatch()` 对普通工具并发执行、对 `exclusive` 工具设置屏障，并按输入下标构造最终返回数组。但并发任务各自完成时就调用持久化 `onResult`，因此事件日志中的 `tool.receipt/tool.result` 顺序可能是**实际完成顺序**，而不是模型原始调用顺序；返回数组则保留输入顺序。两种顺序不应被混为一谈。

这未必是错误：日志可以记录真实完成时序，模型上下文也可以按稳定规则重排。但现有候选设计强调确定性上下文顺序，二者的合同必须明确，并以 T02 反序并发测试检查实际下一轮 Provider 输入。

**暂定决定：先保留简单的“并发组 + 独占屏障”，不提前引入资源冲突图 S3；先测定事件顺序、模型消息顺序与性能。**

### 2.4 持久化与恢复：有真实边界，但修复链已开始变复杂

当前 SQLite EventStore 使用事务、WAL 与 `synchronous=FULL`，并可在写事务中校验 Lease；Tool Host 另有执行状态记录。Kernel 事件与 Host 副作用状态即使共用 SQLite 文件，也属于不同事实合同，而文件系统变更不能与 SQLite 提交组成单一原子事务。

第 23–25 号实验逐步增加了 Stage、可信文件提交、Host Ledger、Kernel 收据补记与人工审查。这些研究揭示了真实故障窗口；同时也说明当前路径尚未形成完整的生产执行链，并产生了相当多的恢复分支与维护负担。

Codex 的 Rollout/ThreadStore + SQLite 查询投影、Pi 的 Session JSONL、DeepSeek 的 append/flush 合同是不同取舍，不能仅凭文件格式就判定哪种更安全或更简单。必须对比：崩溃后重建、事实重复、日志损坏、外部副作用未知、迁移和调试成本。

**暂定决定：暂停扩展收据补记与审批适配器；保留现有代码与测试作为实验资产，但不认定双账本/补记方案已是最终设计。先做故障矩阵和最小端到端对照。**

### 2.5 Context：字符预算不是 Token 预算

当前 `admitContext()` 计算序列化消息与工具 Schema 的字符数，并明确不是 Tokenizer。Turn 的 Token 上限则依赖 Provider 返回的 usage。Checkpoint 只允许基于连续完成的历史前缀，且不将摘要作为授权或执行事实来源；这是值得保留的安全约束。

但字符数上限只能作为序列化体积上限，不能当成模型窗口预算。Pi、Codex、Claude 的压缩触发与失败处理并不完全相同。本轮不建议再加更多摘要逻辑，而是先为目标 Provider 定义 token 估算、窗口余量、工具 Schema 成本和压缩失败策略，并用小窗口任务验证。

### 2.6 Coding 工作流：各个安全部件尚未成为一个可用闭环

当前可验证的 Stage、Patch 预览、文件提交与收据补记是分阶段实验。它们还没有作为一个生产 Tool Host 流程与同一个 Kernel Turn、持久审批、实际测试命令和最终差异审查完整接通；模型工具目录也仍然只读。

因此目前不应以“写入安全控制器已实现”推导“Coding Agent 内核已完成”。更不应为了完成已有控制器而默认继续其架构。

**暂定决定：下一阶段只设计和验证最小垂直切片：提出 Patch → 在隔离副本运行测试 → 生成 Diff → 可信审批 → 版本复验并提交 → 对账结果。是否继续现有实现，由端到端证据决定。**

## 3. 四个参考内核可借鉴的内容（非排名）

| 参考项目 | 值得验证的机制 | 不应直接复制的部分 | 当前建议 |
|---|---|---|---|
| Pi Agent Core / Coding Agent | 小型双层 Loop、截断 ToolCall 不执行、Steering/Follow-up 分开、会话分支与 Context CutPoint | 把进程内 Messages 当外部副作用真相；把 Core 与 Coding 产品层混为一谈 | 先用它定义最小 Loop 基准 |
| Codex | StepContext 快照、ToolRouter、审批与沙箱策略分离、Rollout 与查询投影分工 | 直接复制庞大的 Rust 结构或把 flush 视为已验证掉电保证 | 重点对照 Step/Approval/Storage 合同 |
| Claude Code | 流式 Tool Executor、并发安全分类、长任务/后台 Shell/Subagent 生命周期、控制请求竞态 | 从压缩打包符号推断全部产品语义；把 Interrupt 当作外部副作用已停止 | 重点验证流式延迟、取消与结果关联 |
| DeepSeek Harness | Scope/Registry 组合、Session Event 与历史投影分离、并发批次屏障、明确 append/flush 语义 | 在核心合同未稳定时让所有组件热替换；把语义补齐等同于副作用确认 | 仅在需要扩展生命周期时引入 Scope |

以上是研究假设，不是效果排序。源代码有某个分支，也不代表产品在当前环境一定走该分支。

## 5. 下一轮先做的实验

1. **T02 顺序合同**：构造慢 A、快 B；同时记录 Host 完成顺序、事件日志顺序、返回数组顺序、下一轮模型上下文顺序。明确唯一规范并添加断言。
2. **E0 最小 Loop 基准**：使用固定 FakeProvider 流覆盖普通文本、多个 ToolCall、截断、工具错误、Steering、取消与 Follow-up；统计状态转移、真实工具启动次数与事件序列。
3. **存储故障矩阵**：分别在命令接受、Tool Intent 提交、外部文件替换、Host 成功记录、Kernel Receipt 写入点注入进程崩溃；比较恢复结果与人工介入步骤。
4. **Coding 垂直切片**：在临时隔离副本中完成固定失败测试的修复任务，审查 Diff，再提交；没有完成真实权限审批、Host 隔离和崩溃对账之前，保持模型写工具关闭。
5. **参考实现动态运行**：能运行的 Pi/Codex/DeepSeek 版本使用固定版本与同一任务；Claude ZIP 当前仅有静态打包代码复核，不把未运行的 Desktop/CLI 记成 PASS。无法等价运行的能力标为 `UNSUPPORTED/NOT RUN`。

## 6. 本轮裁决

**不再以“把当前架构补完整”为默认目标。** 当前只读 Kernel 和安全实验作为可复用基线保留；Workspace 写入/恢复链暂缓扩展。下一步先完成 T02 与最小 Loop 基准，再决定是否重构 Loop、StepContext、存储与 Coding Host。
