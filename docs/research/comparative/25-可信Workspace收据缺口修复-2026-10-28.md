## 2. 复用既有恢复系统，不另建独立真相源

仓库已有 `SqliteToolReconciler`：对 Kernel EventStore 与 Host Ledger 进行**同一 SQLite 快照**的只读分类，识别 `host_started`、`host_finished_without_receipt`、`mismatch` 等状态。也已有 `SqliteRecoveryReviewStore`：允许受信调用方记录不可变的、绑定 `evidenceHash` 的 `evidence_noted` 审查记录，但审查记录**不授予工具执行/重放权**。

本轮新增 [`manual-workspace-receipt.ts`](../../../packages/tool-reconciliation/src/manual-workspace-receipt.ts)，导出 `SqliteWorkspaceReceiptRepair`。它不是 HTTP 接口、不是 Agent Tool、不是自动后台修复器；它必须由具有当前授权的**受信任恢复控制端**显式调用。

## 3. 受限的成功结果补记条件

新控制端在一个 `BEGIN IMMEDIATE` 写事务内必须同时满足：

1. 调用请求包含有效的 `sessionId/turnId/callId`、当前有效且已持久登记的 Writer Lease、审查身份/记录 ID 及预期的双账本 `evidenceHash`。
2. 受信调用方提供独立的、可复查当前权限的同步 `authorize(request)`；执行前和 SQLite 写锁内都调用。**仅凭审查备注不能通过授权。**
3. `SqliteToolReconciler` 的双账本快照与预期哈希完全一致，目标 Turn 仍处于**未完成**状态，唯一目标调用为 `workspace.patch` 且 `status=host_finished_without_receipt`。
4. Host 记录必须是 `state=succeeded`、结果为小写 64 位 SHA-256 摘要；恢复者的 Fence Token **严格大于**原 Host 执行时的 Token，确保不能由原在途执行者补写。
5. 已有一条审查记录匹配 session、reviewId、reviewerId、**同一个快照哈希**及 `decision=evidence_noted`。没有审查表、没有匹配记录或未获独立授权时均拒绝。

仅在这些条件全部满足后，将与 Host `succeeded` 内容完全一致的 `tool.receipt` 与 `tool.result` **相邻、原子写入** Kernel EventStore。再用同一事务快照验证调用已变成 `verified` 且 Turn 依然未完成，才提交这次补记。

## 5. 仍然缺失的链路

- **模型提案 → 正式审批**：现有 `authorize()` 是受信回调，并未建立持久化的 Workspace Patch 审批表与有效期/撤销/版本绑定。不得由模型直接决定批准。
- **独立 Stage 测试 → 同一批准的提交**：第 23–24 号报告分别验证了 Stage 隔离与受信提交，但还没有将它们连接成一次完整受信 `Tool Host` 调用。
- **收据补记 ≠ Turn 恢复**：当前仅对`已由 Host 证明成功`的单个工具补齐审计事件对；Turn 仍未结束、Kernel 仍拒绝恢复和模型继续执行。实际恢复状态机和治理审批需要独立设计与验证。
- **物理文件当前状态不可由结果摘要代替**：Host 的成功摘要说明那次提交的结果，不能证明补记时仓库内容仍是该版本；本轮没有重新检查文件，也没有给出新的写权限。
- **强对抗环境**：恶意并发文件系统更名、ACL/xattr、断电持久性、真实 OS cgroup + Seccomp + Workspace 组合、跨平台、远程多租户权限体系和 Codex/Pi/Claude 同条件动态测试仍未验收。

## 6. 后续优先级
