## 三、必须回答的关键问题

### G1：模型事件与工具调用

- 模型刚输出半个 ToolCall JSON，流就断了：实际执行次数是否为 0？
- 多个 ToolCall 并行返回，若结果完成顺序与 ToolCall 顺序不同，历史如何关联？
- 模型 Output `length`、ToolCall ID 重复、模型回退、更换 Provider，状态是否一致？
- 真实工具执行后 Provider 返回错误，重试模型请求会否重复工具执行？

### G2：审批与权限

- Hook、用户审批、组织策略、Tool Host 之间谁的决定最高优先级？
- Hook 改写工具输入后，原审批是否自动失效？
- 命令路径/符号链接/挂载点导致文件系统能力漂移时，谁最终阻断？
- 多 Agent、远程 Worker 的权限是否严格受父任务/操作者约束？
- 沙箱不可用时，是 fail-closed、明确提权再执行，还是静默无沙箱？

### G3：持久化与重启

- Session Event append 成功但尚未 flush 即掉电，是否允许丢失？
- 网络已 ACK 但 Turn 尚未持久接受就断电，能否恢复？
- ToolCall 已发给 Host/实际执行但结果回执丢失，是否会被重试？
- Turn End 已播给客户端但持久化失败，重连后会出现什么？
- 修复“孤立工具调用”与确认“外部副作用未执行”是否被正确分离？

### G4：上下文与多 Agent

- 摘要后的历史是否还能恢复未完成工具、审批和用户目标？
- 压缩模型失败、超预算、缩短历史时是否有熔断与保底？
- 父 Agent 取消后异步子 Agent 是否真正停止或被显式后台化？
- Fork 是否复制父 Context 的多媒体/工具状态？是否出现重复 ToolCall ID？
- Worktree 丢失时是否会错误回退到其他目录执行危险命令？

## 五、计划如何补全证据（不是后台承诺）

按优先级完成时，每项要提交：

1. 版本/平台/Feature Gate 清单；
2. 核心函数完整调用图，包含异常、取消、恢复；
3. 最小复现实验脚本和测试项目；
4. 命令、环境、退出码、结果文件与输出脱敏摘要；
5. 结果是否通过及无法排除的局限；
6. 对自研内核的设计决策或反例测试；
7. 受影响的 ADR 与协议版本更新。

### P0：Claude Code 2.1.304 原生/桌面剩余调用图

从 Desktop 真实 UI 控件或消息事件起点，追到 Electron IPC `senderFrame` 校验、Agent SDK 调用、ProcessTransport 的 `spawnLocalProcess`，直到 CLI `su/iu`；对完整 approve/cancel/resume 回程建立引用。需检查 Windows 沙箱执行返回的 argv/env 处理和 Host 强制实施的边界，不只搜索字符串。

### P0：Codex 的真实 App Server 与事件/执行收据路径

阅读 v2 协议与 Rust 任务处理、Session 终态、Tool Runtime、rollout recorder/flush 的实际关系；完成审批缓存与 OS 沙箱流程的测试，避免把设计文档当绝对保证。

### P1：Pi 的上层 Coding Agent

`packages/coding-agent`（以固定提交实际目录为准）：会话树、压缩、扩展生命周期、OS 工具、资源清理、Provider 切换和重试。这是之前只研究 `packages/agent` 低层核心的主要缺口。

### P1：DeepSeek 的 Sandbox/Approval/Session Persistence

继续追踪默认 Bundle 中真实装配的存储/沙箱/权限组件，并做 kill/flush/restore 验证，尤其修复根关闭 `turn/end` 未落盘和后台工具副作用未知的问题。

### P2：同条件四向基准

- 固定**同一模型**或至少对不同 Provider 做独立对照，不把模型质量混入 Harness 设计；
- 统一工具集、工作区快照、风险策略、上下文预算、测试任务和网络环境；
- 比较可解释指标：成功率、错误工具执行率、恢复正确率、审批安全、Token、Wall Time、P95 延迟与最大资源；
- 重复足够次数并记录置信区间；不由单次演示决定架构。

## 六、何时可以作最终架构决定？

**必须先达成以下门槛**：

- CC、Pi、Codex、DS 的关键执行状态有可复核的正常/异常/取消路径。
- 每个项目至少完成工具调用、权限/沙箱、Context 和 Session 恢复的代表性动态测试；不能运行的领域明确写成无法验证。
- 完成一版自己最小 Loop + DurableEventStore + FakeHost，并运行 K01–K18 中所有适用的离线/隔离测试。
- 关键架构决定具有至少两套方案的实验对照，知道代价与失败模式。
- 所有 ADR 的 `Proposed` 明确由维护者审阅接受后再升级为 `Accepted`。

**当前结论：研究已有足够事实形成高质量的候选架构，但严格标准下尚未全部研究透。建议先验证所有安全/恢复不变量，再冻结 Kernel 接口和最终技术选型。**
