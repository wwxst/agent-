## 1. 需要用户评审的基本设计选择

| 决策 | 默认候选 | 备选方案与代价 | 批准前需确认的事实 |
|---|---|---|---|
| 内核形式 | 小型 Turn/LLM engine + Durable Task/Operation Coordinator + 外置 Tool Host | 完全统一 Task runtime：接口少但所有模型变化必须持久 checkpoint；纯 Core Loop：简单但无崩溃恢复 | 真实业务需要恢复到 Tool/Turn/Task 哪一级？ |
| 主存储 | 单实例 SQLite WAL + 强制 Journal/Outbox/Unique constraints；按 R1/R2 选 sync | Postgres 可多节点 CAS 但部署复杂；JSONL 简单易读但 marker/fsync/索引/并发约束大 | 首期单机还是多机？强断电不丢最后一笔是否硬要求？ |
| 执行所有权 | DB CAS owner epoch + Host execution fence；进程 supervisor 单独维护 OS lock | 只有 OS processLock 易集成但不保护外部/跨主机旧 worker | 是否可能多个进程/机器同时使用同一 Storage？ |
| Tool 效果重试 | unsafe 默认禁止盲目重复；safe 仅在实际支持 idempotency/queryOutcome 时重放 | 所有超时自动 retry：吞吐好但可能重复执行 | 有哪些真实外部工具支持操作键/结果查询？ |
| 权限 | Permission Authority 必经、执行端二次校验、默认明确 ask/deny | 可选 extensions-only gate 更轻但绕行和热更新风险高 | 单用户本机还是多租户/远端 Host？ |
| Context | 不可变 canonical transcript + revisioned projection + summary validity fence | 简单 summary/head 可减少代码但会有 redaction/stale 风险 | 是否需要删除/脱敏、强审计、分支合并？ |
| UI 协议 | Command acceptance + eventual Task receipt；commitSeq snapshot/cursor | stdout-only events 简单但断线重复/丢事件不能对账 | 多端同会话同步是否必须？ |

这些是**独立判断**，不预设旧 Kernel 可保留，不因为 Claude/Pi 某一方案已有源码就直接沿用。

## 2. 状态机关键不变量（最终设计需要形式化验证）

**Invariant 1：Intent-before-effect**。若某 side-effect tool 首次执行，必存在有效、不可被撤回的已提交 Intent，绑定完整 canonical args/hash、host/operation identity、permission decision 和 owner epoch；未提交 Intent 禁止调用外部执行入口。

**Invariant 2：Receipt-atomic-with-ToolResult**。合法 Receipt、tool-result entry、关联 Task transition 在单个 authoritative DB transaction 内提交。若事务失败，不可告诉调用者最终成功；可以发布 provisional progress 但必须可纠正。

**Invariant 3：Unknown-preserving**。已发送而不可证 never-started 的调用，断网/timeout/kill/cancel 不能自动变成 NOT_STARTED；默认标记 OUTCOME_UNKNOWN，需要 Host outcome query 或人工确认。

**Invariant 4：Fencing**。Host 执行前和关键 side-effect checkpoint 比对当前 owner epoch、policy revision 与 approval scope；旧 owner 的迟到 callback/Receipt 在控制面仅记录为审计，不覆盖新 owner 状态。

**Invariant 5：Cancellation is independent**。CancelIntent 可与 Running/Completed/Unknown 并存；标记 cancel 不表示 effect rollback；任务所有权的 foreground/background cancel 规则必须显式。

**Invariant 6：Context provenance**。任何投喂 LLM 的摘要必须追溯 source entry set/head/tail、ContextRevision、redaction/policy epoch；当受影响 edit/revoke 已提交，旧 summary 不可继续代表已授权上下文。

**Invariant 7：Permission last-mile**。所有工具，无论直接模型 tool、MCP、nested、subagent、用户脚本还是 Host forwarded，都经过同一个 mandatory execution gate；可选 extension 不能解除策略下限。

**Invariant 8：UI delivery != truth**。UI 可以接收 provisional tokens，但最终状态必须以 commitSeq/Task/Receipt 为准；重连 snapshot+cursor 能恢复最后已提交事实，并去重 event ID。

**Invariant 9：Task ownership closure**。Task 有 owner，owner terminal 之前必须按 join policy settle foreground children；background escape 必须在 admission 显式声明。恢复时重建 ownership DAG 与等待环检测。

**Invariant 10：Versioned recovery**。Task/checkpoint/tool schema/permission policy 版本在持久存储中可查；无法兼容新版本的任务明确 park/orphan，不调用未知旧工具重放。

## 3. Fault injection 验收矩阵（计划，不是实际实验）

| ID | 故障点 | 必须观测的结果 |
|---|---|---|
| FI-01 | Tool Intent commit 前 kill | 没有 Host effect，重开可生成新 operation |
| FI-02 | Intent commit 后、send 前 kill | Outbox 中仍有可恢复待投递；不重复分配 operationId |
| FI-03 | Host 收到但未实际执行、连接断开 | 只有 Host 证据充分才结算 NOT_STARTED；否则 UNKNOWN |
| FI-04 | 外部 effect 已完成，Host Receipt send 前 kill | queryOutcome/idempotency 工具能 recover receipt；不支持的工具 UNKNOWN |
| FI-05 | Host Receipt 收到、DB commit 前进程退出 | 重新对账后最多一个 terminal Receipt；不重复执行 unsafe |
| FI-06 | Parallel 两个工具，一个 UNKNOWN、一个晚到成功 | source-order transcript 保持配对，不让未知 sibling 触发不安全下一轮 |
| FI-07 | Permission 已显示 UI，Session switch / policy revoke 后才允许 | 旧审批 scope/policy epoch 被拒绝；没有 effect |
| FI-08 | MCP tool call 取消而 server 忽略 | 标注 cancel requested + operation UNKNOWN/RUNNING，不假称 rollback |
| FI-09 | 旧 Host lease 超时、新 Worker claim，旧 Host 再回报结果 | fencing 拒绝旧 owner 的新执行/状态覆盖，审计保留 late result |
| FI-10 | Compaction summarize 进行时删除/脱敏旧消息 | 旧 summary 无法落地或必须重生；新 prompt 不含撤销内容 |
| FI-11 | Provider 生成 summary 后进程丢 response | 标记重复调用/费用不确定，不假装 exactly-once |
| FI-12 | Append/transaction 内中段失败、disk full、断电/kill -9 | Storage contract 对 atomicity / durability tier 的声明真实成立 |
| FI-13 | UI 消费慢、断开、snapshot 重放、事件乱序 | Snapshot/seq 恢复已 commit facts，provisional 与最终事件可区分 |
| FI-14 | Parent child Task wait/abort/close/crash 交错 | Owner DAG/restart count/completing/failFast 正确，aborted child 不残留 |
| FI-15 | Registry/tool schema 热更新，旧 checkpoint 恢复 | migrate/park/orphan 决策有证据与版本，不执行不兼容副作用 |
| FI-16 | 双进程同存储名、不同 OS/process lifecycle | DB CAS + Host fencing 无双 executor effect，失效节点不能抢写 |

验收需同时记录：输入/操作 UUID、owner epoch、host/worker instance、policy revision、Tool args hash、DB commit seq、UI seq、日志与调用结果、实际外部 effect count。只验证文本答案一致是不够的。

## 4. Benchmark 与可维护性要求

- Latency：首 token、每 turn 工具 preflight、permission/UI 交互、commit p50/p99、outbox 到 Host 的 dispatch 延迟、reconnect snapshot 延迟。
- Throughput：并行 1/4/16/64 tools、持续 token streaming、1000+ queued submissions、多个活跃 Conversations。
- Memory/Storage：bounded UI queue、bounded tool stdout/artifacts、长 session context projection、compaction retained history、数据库索引/归档开销。
- Failure metrics：unknown outcome rate、Host stale owner rejections、replayed idempotent operations、orphan/parked tasks、policy revocation race, context invalidations。
- Developer UX：模块边界可单独 fake，但所有 release 前安全属性需要真实工具/数据库/OS 故障测试；observability 必须跨子进程保持 trace/operation identity。

具体性能 SLO、可接受 R1/R2/R3 tier 和预算暂不武断设定，需产品需求和硬件基线后确认。

## 6. 当前仍未解决的设计问题

1. 首发产品单用户本机还是远端多租户？它决定权限强度、Storage/R2 和 Host 隔离级别。
2. 是否必须在硬断电时保留最后一笔已 ACK 的 Tool Intent/Receipt？否则 SQLite NORMAL 等策略即可满足更低 tier。
3. 哪些具体 Tool/MCP provider 支持 idempotency key 和 queryOutcome？没有的 operation 要怎样在人机界面呈现 UNKNOWN？
4. 是否需要跨进程 Worker 并行 claim、抢占和 Lease 续签？如果不用，先设计兼容字段、后置多节点实现。
5. 历史删除/隐私脱敏要求是 prompt-level projection、审计版本保留，还是物理删除并清除所有 derived summaries？
6. 是否需要兼容 Claude Agent SDK/Claude Code 的具体 protocol？若需要，版本和行为 contract 另行钉住；不能从静态源码猜兼容。
7. 既有 Kernel 数据如何迁入新 Conversation/Task/Receipt 体系？需先盘点数据格式与迁移可能性。
8. 关键未测保证：Claude V5 backend、SSH helper、云端 Agent、真实 Pi SQLite/JSONL crash、external effect Ledger。

这些问题不会阻止形成初步架构，但决定最终定案与验收条件。不得在缺少资料时杜撰答案。
