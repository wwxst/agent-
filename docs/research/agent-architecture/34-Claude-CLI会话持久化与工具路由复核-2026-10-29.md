# 34 · Claude CLI 会话持久化与工具路由复核

> 日期：2026-10-29  
> 样本：CLI 2.1.304 发布版 JavaScript。  
> 证据类型：静态源码复核；未运行 CLI，未动态验证磁盘故障、进程崩溃或远程 Host 的真实执行。  
> 本文补充报告 33：把 hook append 与会话 transcript 写入分开，并继续追踪工具路由的 local/remote 分支。

## 1. 先纠正一个术语：`r.appended(v)` 不是通用的持久化提交

报告 33 将 `r.appended(v)` 的底层语义列为未决。进一步追踪后可以明确：

- `chunk-smbjjyps.js` 的 `ha(e,o)`（@28,628）创建的是 query-loop 侧的 session-append hook context。
- 它通过当前 host conversation、`afe(... isHookable ...)`、`Jq(..., {fills:true})` 和 feature gate `L3e() = Ra("session.append")` 管理可供 session.append 扩展钩子读取/补充的消息行。
- `chunk-4b60tdnk.js` 的 `Jq`（@4,757,128）在没有 session hook、context 不可 hook 或 feature gate 关闭时，`fills:true` 路径不会调用 keep callback；有 hook 时才经 `rowsAppendedTo` 处理。
- 同一模块在 @4,757,112 附近注册了 `session.append` handler，最终调用当前 session hook 的 `callAppended`。

所以，`await r.appended(v)` 的确定含义是：等待这条 **session.append hook 路径**完成（若当前条件不适用，则可能是 no-op）。它本身不能作为“Assistant ToolCall 已写入 transcript 文件”的证据。

## 2. 实际 session transcript 写入链

### 2.1 QueryEngine 的 record adapter

`chunk-1vdc3qtt.js` 的 `xR({conversation,messages,persistSession,storageV5})`（@356,593）提供 `record()`、`evict()`、`flushBeforeCompactBoundary()`、`applyCompactBoundary()` 等方法。

`record()` 的关键行为：

1. 以内部 cursor `h` 跟踪已处理的 message rows；
2. 通过 `zZt(...)` 与排序/过滤逻辑选出当前可写的连续前缀；
3. 普通调用会在遇到 `assistant.message.stop_reason === null` 时停止，不把仍未收束的 assistant row 当作完整 transcript row；
4. 通过 `qk(...)` 写入缺失的 message chain，并更新 cursor。

`chunk-4b60tdnk.js` 的 `qk(e,n,r,s,h)`（@387,527）会读取 `dd().sessionMessages(sessionId, storageV5)`，跳过已存在 UUID 的消息，再调用 `ga().insertMessageChain(...)` 写入缺失的链。它还维护 parent UUID、session ID、storage version 以及 bridge/sidechain 相关信息。

### 2.2 Message chain 如何进入 transcript writer

`chunk-4b60tdnk.js` 中：

- `hCt.insertMessageChain`（@373,801）在 `trackWrite` 内处理消息链，必要时先 materialize 当前 session file，再为每条消息建立 transcript entry（parentUuid、agentId、sidechain、version、branch 等元数据）。
- `hCt.appendEntry`（@379,108）按 entry type 的写入策略分流。transcript 行会进入 `enqueueWrite` 队列；写入队列由 `scheduleDrain` 定时触发，`drainQueuesOnce` 最终调用 `appendToFile`。
- `hCt.flush()`（@362,968）会停止待执行 timer、等待当前 drain、执行 drain，并等待 pending write 计数归零；若 writer 已进入 storeFence 状态则抛错。
- `Qc()`（@403,725）封装 `await ga().flush()`。

重要区别：`insertMessageChain` 等待其 enqueue/append 处理流程，并不等同于在该函数返回时已经完成所有 transcript 文件写入。dedup-transcript 分支调用 `enqueueWrite` 后会继续返回；实际写入由后续 drain 执行。需要显式 flush 时，源码有独立的 `flush()` 路径。

### 2.3 Assistant、User 与 Turn 终态的不同等待方式

`chunk-1vdc3qtt.js` 的交互/SDK Turn 驱动在 @392,568 等位置处理 query 输出：

- **Assistant row**：先加入内存消息数组，再在 `persistSession` 开启时调用 `Ue.record()`，但这个调用点没有 `await`；随后保留/吸收消息并做后处理。
- **stream_event / message_delta**：更新 stop_reason 与 usage 后，再调用 `Ue.record()`，同样没有 `await`。
- **User row**：加入数组后使用 `await Ue.record()`，然后保留/吸收该消息。
- **Turn result**：终态分支使用 `await Ue.record(true)`；若 `nn` 为真（由 `CLAUDE_CODE_EAGER_FLUSH` 或 `CLAUDE_CODE_IS_COWORK` 影响），还会执行 `await Qc()`，显式 drain transcript writer。

由于普通 `record()` 会暂缓 `stop_reason === null` 的 Assistant row，ToolCall 所在的 content-block-stop 事件到达时，最初的 record 尝试可能不会写入该未完成 assistant row。后续 message_delta 会触发新的 record 尝试，但该调用点没有 await；Turn result 则会强制记录并 await record，且在 eager-flush/Cowork 条件下进一步 flush。

### 2.4 由源码能得出的结论边界

**源码事实：** query loop 中 `await r.appended(v)` 是 hook 路径；transcript 由另一套 `xR → qk → insertMessageChain → appendEntry/enqueueWrite` 路径处理。ToolCall block 完整后，query loop 会在整个 API message 结束前提交给 StreamingToolExecutor；会话驱动对 Assistant row 的普通 record 调用并不显式 await，且记录器会跳过 stop_reason 为空的 row。

**尚不能断言：** 不能仅凭这些事实断言一定丢失 transcript、工具一定在磁盘写入前产生副作用，或恢复一定失败。实际队列可能在后续事件/Turn 结束前完成写入，Host/MCP 执行层也可能有额外记录。必须继续查明写入队列的时序、flush/exit 路径，以及每种工具执行目标的执行事实记录。

## 3. 工具路由的完整分层（当前版本）

### 3.1 `wG` 入口

`chunk-4b60tdnk.js` 的 `wG`（@3,957,580）是当前版本工具路由器。源码可见的顺序包括：

1. 必要时等待 pending MCP/tool discovery 状态；若工具尚未进入池，会等待并刷新工具定义后重试路由。
2. 处理别名；若仍无工具定义，生成带原 tool_use_id 的合成错误 tool_result。
3. 检查工具是否可用/已加载，以及相关 isolation latch；失败时返回错误 tool_result。
4. 解析当前 MCP connection 与 server 信息，并进行路由前的等待/状态检查。
5. 调用 `uVt` 获取 local/remote dispatch 结果，再由 `gLs` 做路由后校验。
6. `where === "refused"` 生成拒绝结果；`where === "elsewhere"` 调用 `hosts.runToolUse(...)`；`where === "here"` 进入本地 `vYr` 执行路径。
7. 本地执行路径进入 `AYr`（@3,967,595）等 helper，进行输入校验、PreToolUse/工具调用 hooks、权限决策和实际工具调用，最后把结果映射为原 tool_use_id 对应的 tool_result。

### 3.2 Local / remote 选择不是简单的工具名判断

`uVt`（@1,347,132）调用 `Nqo`；`Nqo`（@1,347,666）先检查 session 是否已把该工具指定给另一个 host、已有 remote-call/host 决策，以及 remote host router 是否适用。若没有适用的 remote router，通常返回 `where:"here"`；若 router 适用，则调用 `remote.route(tool,input,context,signal)`，根据结果返回 local/here 或 elsewhere。

此外，`gLs` 位于 `chunk-77n97phr.js`（@16,123），会检查 route refusal / route target，并对本地 route input 重新做 schema/coerce 与额外策略检查。不能把“被路由到 remote”理解为无条件信任远端改写后的输入。

### 3.3 Host 路由证据的边界

`hosts.runToolUse` 接收 tool、toolUse、route、assistantMessage、toolUseContext、canUseTool 和 clock/now 等上下文。这证明 Host 路由是工具执行的一条正式路径，且权限 callback 被传入该边界；但本轮还没有证明每一种 remote host 都会如何持久化 STARTED/terminal receipt、如何处理连接断开、如何去重或如何在结果未知时恢复。

## 5. 本轮结论、未知项与下一步

### 已证实

- `r.appended(v)` 是 `session.append` hook integration，不是通用 transcript commit。
- Transcript 有独立的 message-chain writer 和异步 write queue；`record()`、`flush()` 是不同层次。
- 普通 Assistant record 调用与 User record 调用的 await 方式不同；Turn result 有强制 record，部分模式再显式 flush。
- 工具路由先处理 discovery/alias/isolation，再判定 local/remote，remote route 之后仍有输入校验，host path 与本地 path 分开。
- Host path 接收 `canUseTool` 和执行上下文，但其具体执行账本/恢复语义尚未核验。

### 未知

1. `enqueueWrite` 的实际文件写入与 `flush()` 在 crash/exit/shutdown 各分支中的先后关系。
2. Assistant ToolCall row 的 write queue 何时完成，与工具执行开始的真实并行时序；不能把没有 await 直接升级为“必然丢失”。
3. remote `hosts.runToolUse` 的各 host 实现如何记录执行事实、做权限复验、处理超时/取消/断连和 UNKNOWN。
4. pending MCP tool discovery、MCP 工具路由、remote route 与本地 `AYr` 的权限路径是否完全一致。
5. model stream fallback/abort/tombstone 时，已启动工具是否会被等待、取消、补写结果或留待后续恢复。

### 下一步

1. 追踪 write queue 的 `drainQueuesOnce`、`appendToFile`、`flush` 和 exit/shutdown flush 路径，标明“record 已排队 / writer 已 drain / 是否有 fsync 证据”三种不同状态。
2. 追踪 `hosts.runToolUse` 的实际 host router/执行实现与 MCP host 分支。
3. 再追踪 streaming fallback、refusal fallback、abort 和 tombstone 对正在执行工具的影响。
4. 本轮仍是静态源码研究，不作目标架构裁决，不开始开发。
