## 1. 威胁模型：五种“许可”不是同一许可

| 层次 | 保护对象 | 正确的 authority | 失败样式 |
|---|---|---|---|
| Project Trust | 是否载入项目扩展、MCP、settings、system prompt 等 | Workspace trust policy | 信任配置不能限制工具访问已暴露的文件/网络 |
| Identity / tenancy | 谁发请求、可操作哪个 workspace/secret/Host | 用户认证 + Principal/Scope | User A 通过 Agent 对 User B 的 Host 提权 |
| Model Tool Exposure | LLM 本次看见哪些 tool schema，间接/直接调用 | Tool Registry / Context projector | 未曝光工具仍可能由脚本/nested call 间接执行 |
| Tool Authorization | 某个具体 operation 参数和资源是否允许 | Mandatory Permission Authority + Host pre-execute check | UI approval callback 迟到；热更新后旧 approval 漏过 |
| Execution Isolation | 获准 shell/extension 能实际读取/写入/连接什么 | OS sandbox/container/VM/network/credential boundaries | shell 运行时任意访问进程账户可见资源，不受模型 tool hook 逐效果拦截 |

Pi Coding 官方 docs/security.md（固定 tag v1.4.0）明确：工具以 OS 用户权限运行，不默认逐 tool call 求批准；Project Trust 决定资源加载不是 sandbox；extensions 和 child processes 如果未隔离使用相同权限。Coding Agent session.ts L645–705 的 tool_call 是 ExtensionRunner 上的可选 handler；runner.ts L1249–1266 返回第一个 block。MCP 默认 indirect codemode/deferred/direct/hidden 只是模型曝光和发现策略，所有真正执行必须另有安全约束。

Claude Desktop/SDK 报告 47/48/50 展示集中权限 broker + callback/request identity 的价值，但 UI request/approval、Host permission gate、MCP URL elicitation 并不等于 OS 资源隔离；SDK Host callback 的“允许”也不能回滚已启动外部工具。

## 2. 强制授权的 Proposed OperationGrant 合同

OperationGrant（**设计对象，非上游 API**）必须绑定：

- principalId、tenantId、userSessionId / trusted caller identity、delegation chain；
- toolId + version/schema hash、Host capability identity、sandbox profile；
- canonicalized args hash、目标资源 scope（可枚举 path/endpoint/namespace 等）、是否允许 network/process spawn；
- permissionDecisionId、policyRevision、expiry/deadline、单次 operationId、budget/quotas；
- 明确的 effect mode 与是否自动 retry；
- 审计 traceId、approver/approval kind、approval timestamp 与来源；
- 不得由模型或不可信扩展任意修改的签名 / Host 内验证属性（具体实现可用可信本地 IPC，而非必须公开签名）。

授权流程：

1. Tool preflight 做 schema、资源解析，生成 canonical effect plan；不允许 extensions 在获得用户批准后偷偷修改 args。
2. Policy evaluate：allow/deny/ask；ask 作为可恢复 Approval Task，在审计存储绑定工具版本、参数哈希、scope、deadline。
3. Approval 返回后再次查询当前 policy revision；需要重新授权的权限变更不允许用旧审批票据。
4. Tool Intent commit 之前或同一受控事务内保存准入事实；Host execute 前校验 grant/epoch/policy，身份/权限不可达时 fail-closed。
5. 运行结束 Receipt 记录实际执行版本/Host/sandbox/argsHash；审批通过不是效果已经产生。

**TOCTOU 上限**：高层 Tool Permission 只能判定“允许启动这个命令/API 调用”。被批准的任意 shell 脚本仍可能在调用中产生任意文件写入/网络副作用，不能声称每个内部系统调用都被 Permission Authority 逐项验证。对不可信 shell/extension，必须借助 sandbox 限制可见资源、网络与凭证。

## 3. 扩展、Nested/MCP、Subagent 的不可绕过边界

- 所有间接 invocation（模型 ToolCall、nested executeTool、codemode、MCP、Subagent、后台任务、用户脚本）进入 Host Gateway 时都需 OperationGrant；禁止“已批准父工具”自动使所有子调用免审。
- Delegated scope 默认不能大于 parent scope；Subagent/后台任务需要显式 lease/owner/policy downgrade，不能因为 detach background 逃避撤销。
- 可选 extension hooks 用于提示/数据转换/安全加强；mandatory policy 必须在 hooks 后、真实执行前再次检查最终参数和资源。
- 信任分层：trusted in-process plugin 拥有宿主进程能力，因此只能加载审计过的代码；untrusted extension 必须走独立进程/容器和 capability-limited IPC；不能在一个 Node VM 里仅靠 TypeScript interface 假装权限隔离。
- MCP server 自身也是 effect authority。OAuth token/scope 是服务端身份能力；MCP exposure/codemode 仅减少模型上下文噪声；MCP Elicitation 同意访问 URL 与授权工具操作属于不同 consent。
- CredentialBroker 为操作发短期、最小权限 token；不能把全局 provider keys 透传给 sandbox 或整个 extension ecosystem。

## 4. 撤销时序的可承诺行为

| Revoke 落点 | 可给用户的真实保证 | 仍未知 |
|---|---|---|
| 还未生成 Intent | 后续授权请求失败，Operation 不派发 | 已有其他操作不受影响 |
| Intent 已 commit，Host 尚未接收 | outbox 取消 + policy revision 复查；新执行拒绝 | 已在传输中的请求是否已经到达 |
| Host prepare 已登记，execute 前 | 若 Host 在线且 fail-closed 检查到新版本，则拒绝执行 | 网络分区/离线 Host 只有本地旧缓存时的窗口 |
| Host execute 已开始 | 提交 cancel/revoke intent，阻止新操作；可尝试杀本地进程或 MCP cancel | HTTP/文件/远端副作用未必可撤销 |
| Host 完成，Receipt 未到 | 尝试 queryOutcome/回收 late receipt；状态可为 UNKNOWN | 不支持幂等/账本的外部系统无法精确对账 |

必须明确 Host 在策略服务不可达时是 **fail-closed**（不启动尚未开始的危险操作）；运行中阻断能力以 sandbox/OS/process/network enforcement 为上限，不得宣称时间上绝对即时撤销。

## 5. Context/Compaction 的数据安全设计

### 5.1 数据分类

把四种内容分离：Canonical Entry（原始历史）、ContextProjection（对模型的授权视图）、DerivedSummary（可过期派生物）、External Provider Copy/Backup（已离开本地控制域）。这四类的删除保证完全不同。

- ContextRevision：消息投影变化（edit/omit/head/branch）导致更新。
- SecurityRevision/RedactionEpoch：涉及隐私/权限/资源所有权的变更；必须改变 summary validity。
- Summary 来源绑定 input transcript set/hash、ContextRevision、SecurityRevision、firstKept、tail、model/prompt version。
- Summary 完成必须通过同一个权威事务验证其输入仍有权成为当前模型上下文，否则丢弃内容而非 placement；如果 input 仅有非安全无关 append，可按明确规则允许复用。
- ToolResult/Attachment/Artifact 被脱敏时，摘要与索引/search embeddings、缓存、导出/备份引用都可能衍生敏感数据，必须纳入 invalidation lineage。
- 如果产品要求**物理删除**，不可变 append-only raw history 与“永远保留审计记录”存在冲突：需选择加密后可销毁数据密钥、按保留期安全清除外置 blob/备份/派生索引，或针对受监管数据使用可实际擦除的存储策略；不能仅把 active model projection 设为 omit 就宣称删除原始数据。
- 已发送至 Provider/远端 MCP 的内容不能由本地 ContextRevision 收回；外部保留/删除需要单独约定，并坦诚披露。

## 6. 三种独立架构备选与选择依据

### A. Core Loop + Session/Journal wrappers

结构：沿用轻量内存 loop（可自研或参考 Pi Core），由外层 wrapper 监听 events 写入 Task/Journal，Tool proxy 强制进入 Host Gateway。

优势：低学习/研发成本、能快速复用流式工具生态和现有 CLI；适用于本地 R0/部分 R1、无复杂后台任务和远端 effects。

核心风险：Loop 里 already executing tool 时 wrapper 的 listener/Journal 事务是否 truly before-effect；模型流 retry/Tool batch/Host operations 的状态可能一分为二，重启需要额外重放 Loop 内部不可见状态。**不能以 session.subscribe 自动获得 durable ToolTask。**

### B. 统一 Durable Task Engine（Model/Tool/Compaction 都是 Task）

结构：参考 pi-durable 但独立实现，模型请求、工具执行、压缩、审批、子任务均是统一 versioned checkpoint Task。

优势：状态机清晰、所有任务可审计/恢复，owner/wait DAG 与 UI commit publication 一致；适合高级 Agent、长时间运行、复杂并行和远程 Host。

风险：引擎复杂、状态迁移严格、开发与验证成本最高；模型 streaming/parallel tool/动态插件会扩大 Task schema 版本空间；仍不能免除外部 effect unknown，也不能照搬 Durable compaction/edit 缺口。

### C. 分层 Hybrid：轻量 Turn Engine + Durable Control/Task/Operation Plane + 强制 Host（推荐继续评审）

结构：Turn Engine 只负责模型流与 planning；**一切具有外部副作用的操作交由 Durable Coordinator 生成/审核 Intent，由 Host 执行并收敛 Receipt**；长时间等待/子任务/审批/压缩作为持久 Task，由 Coordinator 决定重启后的执行入口。UI 只从 commit-derived EventHub 获取权威事实，provisional stream 明确标注。

优势：保持 Core Loop 的性能/调试可理解性，隔离 Durable/Host/Permission，扩展长期任务与插件；可以单机一个进程承载所有逻辑模块，后续逐步拆分多进程，逻辑边界不依赖部署形式。

代价：跨 TurnEngine 与 TaskCoordinator 的 admission/pause/resume interface 必须严格定义；不能让 Loop 的 internal auto tool dispatch 绕过 journal。恢复到哪一层需要显式作 checkpoint，不得以“外层可观察”假装复活内部 Promise。

**建议：C 作为当前默认设计方向，但以两个 hard-gate 评估**：
- 若 TurnEngine 无法在任何 effect 前 await durable admission，必须改造为 Task-driven execution / 采用 B，不能用非 awaited event stream 冒充屏障。
- 若产品要求所有 in-flight model/tool 的精确 phase 恢复、极长跨进程 Graph，B 可能比 C 的 wrapper 分层更简单可靠。

这不是“已有成熟内核就能直接集成”的结论；需用 FI-01–16 之类的 contract tests 验证。

## 7. 设计决策记录候选（仍未获批准）

| ADR | 设计候选 | 撤销/替换触发条件 |
|---|---|---|
| ADR-01 | Hybrid C 为默认研究基线，核心状态由 Durable Coordinator 持有 | 若 Loop 无 await-before-effect 控制点，改 Task-native B |
| ADR-02 | Tool Execution 必经 PermissionAuthority → Intent Ledger → Host execution boundary | 若 shell 被赋予全局 OS 权限，即使有审批也不声明资源级隔离 |
| ADR-03 | Unsafe/unknown 不自动 replay；Capability-driven reconciliation | Host/Provider 有真实原生幂等/查询并通过 crash 验证才升级 |
| ADR-04 | Context projection 与 summary 使用 SecurityRevision fence | 如果要求物理删除，则另立 data erasure/crypto/backup 合同 |
| ADR-05 | Local SQLite 作为可评估的首期 Store，但保证等级按 sync+验证决定 | 若首发多节点，则需 Postgres/等价 CAS store & fencing |
| ADR-06 | 所有 UI 只从 committed event sequence 得到终态 | 如需纯 stdout CLI，可让 stdout 订阅 EventHub，而不直接充当真相源 |

## 8. 未决与后续审阅问题

- 第一版要支持任意 shell/extension 的程度，决定最小 sandbox：OS 账号隔离、容器、VM、网络策略/凭证 broker。
- 历史删除是模型上下文修订还是物理数据擦除，是否涉及备份/provider 外发？
- 是否必须在单用户本地环境仍逐工具审批，还是允许明确的用户级 policy preset？
- 首发单机或多主机决定谁是 authority、外部 Host 是否能在网络分区期间运行。
- 是否接受已发出外部效果但结果未知时 Run 进入待人工确认状态？
- EventHub/Model streaming 需要哪些交互/性能 SLO？长时间 Agent 的 Task checkpoint granularities 如何选择？
