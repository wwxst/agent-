## 0. 本轮结论

本轮把报告 36 中的 abandonAttempt、远程 session transport 的取消协议、Host 端 serveSessionToolCall、实际工具执行状态、Host call ledger，以及 caller 的 late-outcome correction 接成一条链。

**已证实的机制：**

1. 模型流 fallback 对执行中工具发出 per-tool AbortSignal；若工具路由到远程机器，信号经 session protocol 转为 control_cancel_request，Host 端撤销对应 request 并 abort 实际 serving pipeline。
2. Host 的执行上下文会区分“权限/审批阶段尚未允许执行，什么都没跑”与“已经允许并进入执行，取消时可能部分执行”。结果状态含 ranNothing。
3. Host 另有按 call_id 管理的 call ledger：内存保存状态和有限期结果；独立 JSONL summary log 在进程重启后恢复部分状态；outcome_of 查询可返回迟到结果或“已到达但结果不再保留”的防重放答复。
4. Caller 端的 m_e 会对 delivery_unknown、timed_out 等 open 状态安排 outcome query，并把结果作为 tool_hosts_correction 注入后续模型上下文。

**本轮发现的重要不对称：**

- 普通 dropped/timed-out 路径会产生 outcome.open，进入 caller 的 given-up/correction ledger。
- 直接 AbortSignal cancellation 被映射成 interrupted，没有 open；Lr 因此调用 forget(callId)。
- Host 的 us wrapper 在 signal 已 aborted 时会抑制 response，即使 serving handler 已经返回。于是 Host 可能知道最终 outcome，Caller 却没有为该 call 排定 outcome query。
- abandonAttempt 的 sweep helper 会计算 startedToolUseIds，但该调用点只取 removes，没有把 started IDs 交给 late-outcome ledger。

这构成一个**静态源码可见的 outcome-accounting 风险点**，尤其值得检查“stream fallback 中远程工具已经开始、取消后模型又发出新的 tool_use”这一场景。它目前是风险/未决问题，**不是经过动态复现的 Claude 缺陷结论**。实际 Shell/MCP 工具是否及时响应 abort、是否留下副作用，仍须按工具实现分别验证。

## 1. 先区分四种 ID / epoch

| 字段 | 归属与作用 |
|---|---|
| call_id | 等于本次模型 tool_use_id；Host 端 run-at-most-once key，在审批 legs、redelivery 和 outcome query 间保持不变 |
| request_id | 每个 session control request / leg 独立；用于请求去重与 control_cancel_request 撤销 |
| instance_id / host_epoch | 远程机器 announce 实例及该机器 Claude 进程 epoch；用于识别机器重启/重新绑定 |
| worker_epoch | 发起远程调用的 cloud worker life；Host 的 retry-join 逻辑用它区分跨 worker epoch 的同一请求重试 |

Protocol schema 说明：call_id 是 serving side 的 run-at-most-once key，覆盖 legs、redeliveries 和 queries；request_id 是 per-leg。旧请求的服务端存储延迟超过 service-clock deadline 时以 stale 拒绝；协议还明确 durable catch-up 到新 client 时不能执行过期旧调用。

## 2. 从模型 fallback 到 Host 端执行取消

    StreamingToolExecutor.discardAndAbortInFlight
      └─ abort per-tool AbortController (reason: streaming_fallback)
          └─ wG(... toolUseContext.abortController = per-tool controller)
              └─ hosts.runToolUse → remote route → no / qt
                  └─ session transport.call(signal)
                      └─ sendRequest abort listener
                          └─ enqueue control_cancel_request(request_id)
                              └─ RemoteSessionManager.handleMessage
                                  └─ retireServedRequest(request_id)
                                      └─ abort pending served request
                                          └─ Mo/us combines and forwards signal
                                              └─ serveSessionToolCall
                                                  └─ s8r(... signal ...)
                                                      └─ Rn links leg abort to execution controller
                                                          └─ co / permission + tool pipeline

### 2.1 Caller 发起取消

- StreamingToolExecutor.discardAndAbortInFlight（chunk-smbjjyps.js @52,200）先将 executor 标为 discarded；对 executing 工具 abort per-tool controller；queued 工具只计入 queuedNeverStarted，不像 executing 一样 abort；已完成但已开始的调用也会被计入 started IDs。
- per-tool controller 是 Cg(this.toolUseContext.abortController) 创建的子 controller，并通过 wG 传入工具上下文（chunk-smbjjyps.js @58,000 附近；chunk-4b60tdnk.js 的 wG @3,957,580）。
- abandonAttempt（chunk-smbjjyps.js @121,677）先 tombstone 旧 assistant messages 和 tool results，再调用 gn sweep，最后 rebuild executor。值得注意：它只解构 gn(...) 返回的 removes，没有消费返回的 startedToolUseIds。

### 2.2 Session transport 发出 cancel

- sendServedCallRequest（chunk-g9306b3w.js @38,368）为本 leg 创建 request_id，把 signal 与自身 AbortController 合并后调用 sendRequest。
- sendRequest（@31,738）在 signal abort 时调用 enqueueCancelRequest(request_id)，并撤销本地 pending request；因此 cancellation 是协议消息，不只是本地 Promise reject。
- transport wrapper _e（chunk-vjg7hgts.js @19,509）把 signal abort 映射为 kind:"cancelled"。该结果不包含 Host 端最终工具 outcome。

### 2.3 Host 接收取消并抑制 response

- RemoteSessionManager.handleMessage（chunk-8f3361cb.js @47,756）识别 control_cancel_request，先处理相关待处理控制请求，再调用 retireServedRequest。
- retireServedRequest（@74,476）从 pendingServedRequests 删除 request，并 abort 该请求的 AbortController。
- served channel 的 Mo/us（chunk-6qrznqa7.js @140,612 / @141,114）将请求 signal 与 serving-lifetime signal 合并，调用 serveSessionToolCall；handler 完成后若 e.signal.aborted，直接 return，不再调用 respondToServedChannelRequest。
- serveSessionToolCall（chunk-we991ne4.js @27,398）通过 F.answer(request_id,...) 做同一 request leg 的 in-flight Promise 去重，然后把 signal 传给 s8r。该去重 map 在 finally 后删除；跨 legs 的 call_id 去重由另一套 call ledger 负责。

因此，取消若先于 response 发送，caller 收到的是 cancelled transport outcome；Host handler 的执行状态不会作为该 leg 的正常 response 送回。

## 3. Host 的实际执行状态如何区分“未运行”和“可能部分运行”

- Rn（chunk-s6d90kk9.js @11,267）把 leg signal abort 映射到内部 controller 的 remote-cancel；Host serving lifetime 结束则映射为 shutdown。
- co（@40,551）把内部 controller/clock 交给权限和工具执行管线。
- ze（@27,458）根据 permissionOutcome 判断是否已获准：
  - 尚未 allowed/approved_by_session：返回 cancelled 或 timed_out，带 ranNothing:true，说明 hook/approval 阶段结束前命令未运行；
  - 已允许执行：返回“取消时可能已部分运行”的 cancelled/timed_out，不带 ranNothing，并明确提示不要盲目重试非幂等命令。
- yo（@61,638）把最终状态写为 leg summary，包含 state、code、ended_as、ran_nothing、is_error 等字段。

这证明 abort signal 已进入 Host 工具执行管线；**不证明所有 Shell/MCP 子进程或外部系统都已停止，更不证明副作用可回滚**。工具是否响应 signal、何时终止进程、是否有已提交的外部写入，必须继续追各工具 executor。

## 4. Host 端 call ledger：内存结果与重启 summary 是两层

### 4.1 内存 call store

VAs（chunk-ns649tzz.js @396,010）有以下默认上限：

- 最多 1,024 个 call records；
- 最多 64 个缓存结果、总结果缓存最多 8 MiB；
- 单个结果 TTL 30 分钟；
- 结果过期/被淘汰后，call summary 仍可留存，但完整 result 不一定还在。

Re（chunk-s6d90kk9.js @11,976）按 call_id 处理重复请求：已完成/失败则返回已有结果或 duplicate_call summary；received/running/asked 则返回 in-progress/approval 状态。它不会因为同一 call_id 的 redelivery 就再次执行工具。

### 4.2 跨 worker epoch 的 retry join

- Oe(tool,input,startDir)（chunk-s6d90kk9.js @39,660）用工具名、startDir 和 deciding input 构造 retryKey；LX（chunk-c4am3cy2.js @1,017）对规范化对象做稳定 hash。
- VAs.retryOf（chunk-ns649tzz.js @398,488）只查找**同 retryKey 且旧 workerEpoch 小于当前 workerEpoch**的请求，并要求旧 call 仍在进行，或其结束时间晚于新请求接收时间；旧 call 已在新请求到达前终结时，不会无条件 join。
- 对 execution.mode === "in_process" 且工具 isReadOnly(input) 为 true 的调用，yt（chunk-s6d90kk9.js @59,904）会跳过 retry join。

这不是“相同命令永远只执行一次”的全局幂等键。它主要处理 worker epoch 变化时重叠的同一请求。**同一 worker epoch 内模型重新生成一个新 tool_use_id/call_id，不会仅凭 retryKey 自动被这条规则合并。**

### 4.3 独立的 served-call summary log

- 默认目录：~/.claude/state/served-calls（chunk-ns649tzz.js 的 xj）。
- 记录类型：started、disowned、leg。started 在权限已允许、工具执行即将开始时记；leg 记最终 summary。
- qAs.note（@402,230）将 append 排入 Promise chain，但不返回/等待该 append Promise；写入失败只记录 warning/telemetry。
- 默认 Lzr.append（chunk-3en886nm.js @17,812）使用 fs/promises.appendFile；本层没有显式 fsync。
- Xir（chunk-s6d90kk9.js @79,069）注册 exit flush，与 1,000 ms timer race；它是尽力收尾，不是 side effect 与 journal 的原子事务。
- loadPrior 最多读最近 6 个 segment、每段最多取 4 MiB tail，最多 20,000 个 call IDs、每 caller 保留最近 256 条；load timeout 默认 2,000 ms，超时先以空 Map 继续并记 load_timeout。
- 持久化恢复只重建 summary，不重建完整 result，也不重建 retryKey/workerEpoch。

重启映射（VU @403,718）：
- started 或 received/running：lost_in_restart，提示可能部分运行；
- completed：只恢复完成状态和 is_error，不恢复结果 body；
- failed：恢复 code、ended_as、ran_nothing；
- asked：映射为 host_stopped/withdrawn；
- disowned：恢复为 disowned tombstone。

### 4.4 disowned tombstone 防止晚到的旧 call 执行

An（chunk-s6d90kk9.js @12,433）在 outcome_of 查询发现 call_id 无记录时，如果 caller session 仍存在且 call store 没有忘记过记录，会：

1. 先在内存 call store 写入 failed/disowned；
2. 将 disowned 事件排入 call log；
3. 返回 unknown_call。

如果同一 call_id 的旧请求之后才到达，Re 会识别 disowned 并返回 g8r（chunk-88eey5ab.js @11,779）生成的“session 已被告知未收到、该 call 未运行”答复，而不是执行它。这是一个明确的 late-delivery tombstone。

但 tombstone append 同样是异步 best-effort；若 call store 已忘记记录、日志写入失败或 prior log 未及时加载，跨进程保护边界仍需验证。

## 5. Caller 端 outcome query 与 correction

- N4r（chunk-nteqxgw3.js @6,922）发送 outcome_of(call_id)，可重复 check-in，区分 answer、still_running、not_received、host_restarted、unknown、unreachable、cancelled。
- Zwn（@10,901）把 unknown_call 与 host_epoch 对比：同 epoch → not_received；epoch 改变 → host_restarted；缺 epoch → unknown。
- m_e.gaveUp（@12,108）只保留带 outcome.open 的调用；dueForQuery 每轮最多取 4 个待查询调用。
- JXo（@74,238）将 late outcome 转成 tool_hosts_correction；prompt context builder 会在后续模型上下文中消费它。它会告诉模型：已运行、未运行、仍运行、可能部分运行、Host 已重启或结果丢失等。
- correction 对 host_restarted、cancelled/timed_out 等情况会要求先用只读方式检查 Host 上的效果，再决定是否重复。

### 5.1 取消路径与未知投递路径不一致

| transport outcome | dRe 的 caller outcome | Lr 后续行为 |
|---|---|---|
| dropped | error + open:"delivery_unknown" | 写入 m_e.gaveUp，之后可 outcome query |
| timed_out | error + open:"timed_out" | 写入 m_e.gaveUp |
| stalled（请求已发出且未撤回） | error + open:"stalled" | 写入 m_e.gaveUp |
| cancelled | akt(host) → error interrupted，无 open | Lr 调用 m_e.forget(callId) |

no（chunk-nejdcwfh.js @41,235）在 signal aborted 时把本次 forwarding outcome 设为 interrupted，并在 finally 中调用 Lr（@42,375）；Lr 对无 open 的结果直接 forget。相反，Hr 的恢复检查若被取消，会用 akt(host,{askLater:true})，产生 open:"interrupted"，因此仍会保留待核对记录。

**因此：首次远程 call 在执行中被 fallback/user abort 的路径，与恢复阶段被取消的路径，caller 端 accounting 不同。** 前者没有进入 m_e 的 late-outcome query 队列。

## 6. 风险判断：事实、推断与未知

### 源码事实

- fallback 会 abort executing tool 的 per-tool signal，并 tombstone 该 attempt 的消息。
- 远程 session transport 会发 control_cancel_request；Host 收到后 abort serving request。
- Host 执行管线可记录 cancelled/timed_out 与 ranNothing；已获准执行的调用可能部分运行。
- Host 在 signal aborted 时抑制 response。
- Caller 对直接 cancelled transport outcome 不建立 m_e given-up record，而是 forget call_id。
- Host call log/内存 ledger 具有恢复能力，但有容量、TTL、异步 append 和 flush timeout 限制。

### 推断 / 风险（未动态验证）

- 若远程工具已开始产生副作用，fallback abort 后 Host 可能只留下 cancelled/partial 或 completed 的 call summary，而 caller 不一定会主动 query。
- 如果 fallback 后模型发出新的 tool_use_id（即新的 call_id），同 worker epoch 的 retryKey 不会自动 join 旧 call；存在重复执行风险。
- 这不证明 Claude 一定会重复执行：工具可能及时响应 abort、模型也可能不重复同一操作；需要按工具和时序验证。

### 未知

1. Bash/Read/Write/Edit 的 Host executor 如何处理 AbortSignal、子进程组、SIGTERM/SIGKILL、收尾 hook 和已提交副作用。
2. MCP passthrough 工具对 AbortSignal 的真实传递与服务器端取消语义。
3. streaming fallback 发生在 remote call 不同阶段（排队、请求已发送、Host receive、审批、工具运行、工具完成但 response 未发）时，是否存在其他补偿/通知路径。
4. direct-cancel 后是否有未由 m_e 管理的其他 outcome query 机制；本轮检索的 Lr / m_e 路径未发现。
5. served-call log 的 load_timeout、append_failed 和跨重启 disowned tombstone 是否会在真实环境中造成 late-delivery 窗口。

## 7. 对后续架构比较的启示（不是架构决策）

- 对话 transcript、工具执行账本、工具结果存储应作为不同职责建模。
- operation_id/call_id 与 delivery_request_id 必须分离；取消某一 delivery leg 不等于 operation 已终结。
- cancel_requested、cancelled_before_start、cancelled_after_start/outcome_unknown、completed_but_reply_lost 应是不同状态。
- 在副作用开始前记录执行意图，且 journal write 的成功语义必须明确；仅排队 append 或 Promise resolve 不足以证明持久化。
- abort 后保留 operation ID 和 reconciliation obligation；不能因为 attempt tombstone 就丢弃执行状态。
- 大结果可存 artifact/reference，但 summary journal 至少保留终态、ranNothing、result reference/hash、执行目标和 epoch。
- retry/idempotency 的作用域要明确覆盖 model retry、worker restart、delivery redelivery，而不是只处理其中一种。
