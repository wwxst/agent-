## 0. 核心结论

取消不是一个原子动作，而是一组跨层状态转换。Claude 2.1.304 对不同工具路径的取消和结果回收能力不一致：

- Bash foreground：本地进程终止尝试；无统一 operation ledger。
- Bash background：解除原 tool-use signal，转由 task registry / output file / TaskStop 管理。
- MCP ordinary auto-background：解除原 signal，靠进程内 Promise/registry；Session 退出不恢复。
- MCP SEP-2663：request cancellation 与 server task cancellation 是两件事；拿到 task handle 后可发送 tasks/cancel，任务 sidecar 支持 resume。
- Remote Host tool：request_id cancel、call_id ledger、outcome_of/correction 分层存在，但 direct cancelled 分支没有进入 caller 的 open outcome queue。

**最重要的设计证据：原 tool_use/attempt 结束，不代表 operation 已结束；transport request 取消，不代表 server task 已取消；本地状态标记 killed，不代表远端副作用停止。**

## 1. 取消时序矩阵

### 1.1 Bash / Shell

| 时序点 | Caller / ToolUse | 执行端 | 可持久化信息 | 取消与恢复结论 |
|---|---|---|---|---|
| spawn 前已 abort | per-tool signal 已 aborted | 返回 killed / “Command aborted before execution”，不创建 child | 通常没有 local_bash task record；可能有调用 transcript | 可确定没有启动此 Shell child；不能推断 hook/调用前其他副作用 |
| spawn 后、仍 foreground | abort signal 仍连接 LFe | streaming_fallback 不属于 turn-abort 豁免；进入 kill，先 SIGTERM，约 1.5s 后尝试 SIGKILL process group；Windows taskkill /T /F | output writer/file；若任务已超过注册阈值则 Engine State task record | 是进程终止尝试，不是事务回滚；已提交文件/API/DB 副作用不撤销 |
| 已自动/手动 background | 原 AbortSignal listener 已被 background() 移除 | child 继续运行，输出继续写文件；TaskStop 可经 registry 调用 shellCommand.kill | Engine State task record + session-scoped output file | 后续 attempt abort 不再停止它；同 session 中 TaskStop 可控制；跨 CLI process reattach 未证实 |
| child 已完成、结果尚未回填 | child 已 exit，LFe 已清 listener，task/result 已生成 | 后续 abort 不会撤销已完成操作 | 可能有 task terminal event/output file；快速命令可能没有 task record | 结果可能随 abandoned attempt tombstone 被撤回；没有 Bash 版统一 outcome_of ledger |
| caller final response / session exit | 取决于 backgroundEndsWithFinalResponse、remote keepalive 等 | 某些同步 subagent/headless task 在 final response 终止；普通 background task可继续；process exit/crash 行为未动态验证 | output file 可能仍在 | final response、session exit、process crash 是不同边界；不能互相推断 |

证据锚点：\`chunk-4b60tdnk.js\` 的 LFe constructor/abort @253,035–253,733、kill @256,121、background @256,916、detach @257,147、ShellCommandManager ENn @251,208、\`sNn\` @190,594、Bash runner \`uRs\` @4,857,980、task registration/background \`ETr/e1n/z6n\` @4,774,576/@4,775,997/@4,777,403；TaskStop 的 \`Kq\` @2,391,915 与 \`chunk-45j5sbzt.js:eAe\` @23,080；TaskOutput 路径见报告 40。

### 1.2 MCP ordinary call 与 auto-background

| 时序点 | Caller / ToolUse | MCP Client / Server | 可持久化信息 | 取消与恢复结论 |
|---|---|---|---|---|
| 普通 request 尚未 auto-background | parent AbortSignal 与 MCP request controller 关联 | abort 后 Client 发 notifications/cancelled(requestId, reason)；Server SDK 将其映射为 handler AbortController.abort | 普通 task sidecar 不存在 | server handler 可协作取消；第三方 server 是否尊重 signal 未知 |
| auto-background threshold 到达 / 用户消息提前到达 | wrapper 解除 parent signal 与 request controller 的关联 | 原 MCP Promise 继续运行 | 只有进程内 task registry/Promise | 原 attempt abort 不再取消它；它明确不 survive session exit |
| auto-background 后 TaskStop | TaskStop 找到进程内 mcp_task record | MCP_TASK.kill abort request controller，普通 MCP cancellation notification 继续发送 | 无 SEP-2663 metadata sidecar | 依赖当前 CLI 进程；无 server task ID，不走 tasks/cancel |
| session exit / crash | process-local Promise 消失 | server 可能已停止、仍运行或已完成 | 无可供该路径恢复的 sidecar | 结果和执行状态不可由此 task registry 恢复；server side effect 状态未知 |

证据锚点：\`chunk-0h73ch0n.js:Re\` @15,686；MCP SDK request cancellation 见报告 39；auto-background 返回文本明确写明不 survive session exit。

### 1.3 MCP SEP-2663 Protocol Task

| 时序点 | Caller / ToolUse | Server task | Sidecar / 恢复 | 结论 |
|---|---|---|---|---|
| 原 tools/call request 发送后、task handle 尚未返回 | per-tool signal 仍属于原 request | Server 可能正在创建 task | 尚无已知 mcpTaskId，metadata 未登记 | 可发 notifications/cancelled；若 server 已创建 task但 handle 未返回，client 暂时无法按 taskId 发送 tasks/cancel |
| task handle 返回时，原 signal 已 aborted | wrapper 检查 Xe.signal.aborted | 已取得 server taskId | 此分支直接 best-effort 发 tasks/cancel，返回原响应，不进入常规 task registry/sidecar 驱动 | 有专门补偿，但取消请求失败被 catch；没有持久恢复义务 |
| handle 正常返回并注册 | registerOrAdoptSep2663Task | server task 继续运行 | 写 mcp-tasks metadata；写入失败只 telemetry/warning，task registry 仍继续 | metadata 失败会形成 restart reattach 缺口 |
| background drive 运行中 / server 暂时断连 | 原 tool-use attempt 已结束 | watcher reconnect + tasks/get polling | metadata 保留 server/task ID、protocol、transportFingerprint、TTL 等 | 可恢复轮询，不重新执行原 tools/call；身份变化会阻止错误 server 操作 |
| Session shutdown | watcher 收到 shutdown/park 路径 | server task 可能继续 | 任务被 parked，metadata 保留 | 设计上可在同 session resume 后重新 drive |
| resume | 新 CLI session 恢复相同 conversation/session | restore 读取 metadata、重建 registry、reconnect/poll | outcome sidecar 先 replay；metadata 后 restore | 比 ordinary auto-background 有明确恢复路径，但受 feature/runtime guard 和 sidecar 写入成功影响 |
| TaskStop | 本地 drive/request controller abort | 仅 server connected 且 transportFingerprint 匹配时发送 tasks/cancel | 本地仍标记 killed 并删除 metadata，不等待 server ack | server offline/mismatch 时可能仍执行，且本地 reattach record 被删除 |
| server terminal outcome、通知尚未进入 transcript | task drive 得到完成结果 | Server task terminal | outcome sidecar 采用 atomic 写入语义；resume helper 可补发通知 | 若 outcome write 失败且 CLI 在通知被读取前 crash，源码明确承认 ending 可能丢失 |

新增 handle-abort 证据：\`chunk-je35d7v1.js\` @184,666 检查 \`Xe.signal.aborted\` 后调用 tasks/cancel；malformed handle 分支尽力解析 taskId 并取消，若无法确认会提示 server 可能仍在运行；正常注册调用 \`registerOrAdoptSep2663Task\` @185,762。其余证据见报告 40。

### 1.4 Remote Host 工具

| 时序点 | Caller | Remote Host | Caller outcome recovery |
|---|---|---|---|
| send 前/发送中 abort | transport 发 control_cancel_request(request_id)；本地 pending request 取消 | 若 Host 尚未收到 request，是否会收到 cancel 与消息时序相关 | direct cancelled 映射为 interrupted，无 open；caller forget(call_id) |
| Host 收到、尚未 permission allow | caller transport 可能已取消 | Host retireServedRequest abort request；工具 pipeline 可返回 ranNothing:true，但 aborted wrapper 可抑制 response | caller direct-cancel 路径没有进入 m_e given-up queue |
| Host 已 allow / tool started | caller transport 取消 | Host execution controller 收到 remote-cancel；结果可能部分运行 | Host ledger 可记 started/leg summary；caller 未必 query |
| Host tool completed、response 尚未发送 | caller transport 取消 | wrapper 在 signal aborted 时 suppress response；call ledger 可能已知完成 | caller direct-cancel 仍可能 forget；结果未必回到模型 |
| dropped/timed_out/stalled（非 direct cancel） | caller 记录 outcome.open | Host 可能仍执行或稍后完成 | m_e 安排 outcome_of，tool_hosts_correction 注入后续上下文 |

证据见报告 35、38；本表不重复其 call ledger 细节。

## 2. 横向发现：三种“取消成功”不能混为一谈

| 语义 | 含义 | 不代表什么 |
|---|---|---|
| request_cancelled | 客户端停止等待并发送取消协议 | 不代表 server handler 已停止 |
| task_cancel_requested | 已向 server taskId 发送 tasks/cancel | 不代表 server 已确认或底层 executor 已停止 |
| process_kill_sent | 本地进程收到 SIGTERM/SIGKILL 尝试 | 不代表子进程/外部副作用全部消失 |
| local_task_marked_killed | CLI registry/UI 标记 terminal | 不代表远端 task 已停止 |
| outcome_recorded | ledger/sidecar 记录某个结果 | 不代表 transcript 已包含该结果或模型已消费它 |
| result_delivered | task notification / tool_result 到达对话 | 不代表副作用可安全重试 |

## 3. 风险与未知

### 源码事实
- Bash foreground/background、MCP ordinary auto-background、SEP-2663 task、Remote Host tool 有不同 signal 与恢复路径。
- SEP-2663 的 task handle 迟到分支有专门 tasks/cancel；普通 MCP auto-background 无 task sidecar。
- Remote Host direct cancelled 与 dropped/timed_out 的 caller accounting 不同。
- Sidecar metadata/outcome 的写入纪律不同；Storage V5 backend 物理 durability 仍未知。

### 推断 / 风险
- 新模型 attempt 可能与旧后台 operation 并存；如果只按 tool_use_id 或 request_id 管理，可能丢失 operation 的执行责任。
- stop/cancel 没有确认时删除本地 registry/metadata，会把“取消未确认”错误折叠为“本地已停止”。
- result notification 被 tombstone 或未消费时，如果没有可恢复的 operation outcome，模型可能在未知状态下重复非幂等操作。

### 未知
1. Local Bash 在真实 CLI process crash 后的存活与重接管。
2. Bash descendant process、后台进程组和 PostToolUse hooks 的完整终止/收尾顺序。
3. MCP server 对 notifications/cancelled 与 tasks/cancel 的真实响应行为。
4. SEP-2663 server task 的持久性、TTL 与 terminal outcome 查询保证。
5. Storage V5 sidecar 在 power loss/crash 下的原子性和耐久性。
6. Remote Host direct-cancel 是否存在 m_e 之外的通知/查询补偿路径。
