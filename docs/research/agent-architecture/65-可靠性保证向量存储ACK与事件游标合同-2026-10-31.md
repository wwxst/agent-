## 1. 关键修订：R0–R4 不是一条可比较的可靠性等级轴

报告 60 的 R0–R4 实际混合了五种彼此独立的能力：
- R1：本地进程崩溃后恢复已提交状态；
- R2：主机断电后持久；
- R3：多进程/多主机执行所有权；
- R4：特定 Tool 的外部 effect dedup/outcome query；
- EventHub 的 replayable delivery 并未被这些等级单独覆盖。

因此不能用 reliabilityLevel=R4 这种单值对整个 Run 或整个产品做承诺。一个多主机系统可能有很强的数据库提交保证，但某个 Bash Tool 仍只能给 OUTCOME_UNKNOWN；单机 SQLite FULL 也可能提供本地断电后数据保证，却不具备多主机 worker ownership。

**建议将 R0–R4 改成 capability vector / guarantee profile**，按每个运行实例和每个 operation 报告实际能力：

| 维度 | 建议级别 | 精确定义 | 典型候选 |
|---|---|---|---|
| commitAck | A0 volatile | 只在进程内存确认 | Memory |
|  | A1 process-recoverable | commit atomic；应用进程崩溃后可 reopen，未承诺掉电保留最近 ACK | SQLite WAL NORMAL；须依实际 Storage 实现 |
|  | A2 local-fsync | ACK 前本地 WAL/marker 已按合同同步；依赖 OS/FS/device 如实执行 flush | SQLite WAL FULL；Postgres fsync=on + synchronous_commit=on（local） |
|  | A3 sync-replicated | ACK 等待配置的同步副本将 commit WAL 持久化；failover/promote 仍需独立 fencing/运维协议 | Postgres synchronous standby + synchronous_commit=on；read-after-failover 可能需要 remote_apply |
| writerAuthority | W0 single-process | 单个 Coordinator 实例内串行 | memory/session queue |
|  | W1 single-host multi-process | 同主机多进程共享本地存储，具有数据库 CAS/owner lease；SQLite WAL 不放 network FS | SQLite local disk + task owner CAS；OS lock 只能作额外防线 |
|  | W2 multi-host | 中央数据库条件写/lease epoch + Host side fencing；旧 owner 不能启动新 effect | Postgres/等价中心化协调 Store |
| eventDelivery | E0 ephemeral | token/event 尽力推送，不保证断线重放 | provisional stream |
|  | E1 transactional outbox | state + outbox 同一事务；投递至少一次，允许 duplicate | DB outbox + idempotent consumer |
|  | E2 replayable stream | E1 + stream cursor、ordered replay、snapshot barrier、retention reset | conversation-local event log/cursor |
| effectEvidence | X0 unknown-capable | 外部操作可能已经发出；无强去重/查询时必须保留 UNKNOWN | shell/MCP/HTTP without idempotency |
|  | X1 replay-safe | 纯计算/只读或经验证的可重复操作；重试不会产生新业务效果 | pure local tool |
|  | X2 host-deduplicated | Host 对稳定 operationId/argsHash 有持久唯一登记；能 join 已有运行或 receipt | Host ledger，但若外部 provider 非原子，effect crash gap 仍可能 UNKNOWN |
|  | X3 provider-idempotent | 外部 provider 对同 effectKey 原子去重，并提供保留期内可靠 outcome query/receipt | provider native idempotency contract |
|  | X4 shared-transaction | effect 与 receipt 真正在同一权威 DB 事务内 | 仅适用于副作用确实由同一 DB 承担的受限工具 |

这些字母/级别是**建议的产品能力描述**，不是行业标准，也不意味着 A3 自动包含 W2/E2/X3。工具的 effectEvidence 必须 per operation 计算，不能按系统最高等级冒充。

示例：
- 本地强耐久单机：A2/W1/E2/X0(shell)。
- 多节点 Agent SaaS：A3/W2/E2/X3(payment-api)，但对无幂等键的 Bash 仍为 X0。
- 纯内存演示：A0/W0/E0/X1(pure-calculation)。
- 无论 A2/A3 如何，数据库提交 ACK 不能替代外部业务 API 的 effect receipt。

## 2. Pi v1.4.0 Storage 源码事实复核

固定 earendil-works/pi@v1.4.0，具体证据见报告 55：

### 2.1 Node SQLite

packages/chord/src/sqlite/node.ts blob b156477e8749c5b0315f0444396e82b8ee79a5bf：
- 使用 Node DatabaseSync，SerialOperationQueue 把同一 adapter instance 的事务/查询按 call order 串行；
- transaction() 执行 BEGIN IMMEDIATE，callback 使用 transaction handle，正常后 COMMIT，异常尝试 ROLLBACK；
- open 固定 journal_mode=WAL、synchronous=NORMAL、wal_autocheckpoint=1000、busy timeout 5000ms；
- close 尝试 wal_checkpoint(TRUNCATE) 后关闭连接。

packages/durable/src/storage/sqlite/storage.ts blob 7dc5903828740fe278fdc692ef9f40dbf68982c7：
- records、documents/revisions、next_id、next_seq 在同一个 SQLite transaction 更新；
- mintId() 先使用 storage instance 本地 nextId，commit 时才把 metadata next_id 更新到 max(candidate)；多个独立 Storage 实例并发打开同文件并不自动成为一个 TaskScheduler owner，也不能由本地计数器证明多进程 ID 分配安全；
- SQL transaction 提供批次原子性，但不提供上层执行 lease 或外部副作用幂等。

**外部机制佐证**：SQLite 官方说明 WAL + NORMAL 在 application crash 后提交数据仍可恢复，但 system crash/power loss 后最新事务可能回滚；WAL + FULL 每次 commit 增加 WAL sync，官方把 WAL + FULL 列为 ACID。见 [SQLite PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragmasynchronous) 与 [SQLite WAL](https://www.sqlite.org/wal.html)。WAL 要求所有进程在同一主机，不能在 network filesystem 上共享；见 [SQLite WAL limitations](https://www.sqlite.org/wal.html)。

因此，Pi 的 Node SQLite adapter 只能按 A1（process-recoverable）描述，不能因为它使用 WAL 就宣称 A2。要达到 A2，目标实现需明确使用 WAL + FULL 并验证 Node/OS/VFS/硬件 flush 行为。

### 2.2 JSONL

packages/durable/src/storage/jsonl/storage.ts blob 4b03fd5beff465841ec3dc069d32fd90241604eb：
- fsync=true 时先 flush affected sidecars，再 append main.jsonl marker；
- marker append 成功后才 apply memory state；
- 主文件 flush 仅在 sidecar reclaim path 尝试，不是每次 commit 都执行；
- 因而 fsync=true 仍不能声明每条 commit marker 已完成同步落盘。普通 entry-only commit 可能只有 appendFile(main.jsonl)。
- append 返回错误时，marker 可能已经被 OS 接收，重开 scan/reconcile 才能确定 commit 是否存在；不应直接重做外部副作用。

**判断**：现有 adapter 不满足 A2 的目标 ACK 合同；除非重新设计 main marker sync、文件创建/rename 的目录项同步、write-after-error reconcile 和跨进程 single-writer。它仍可作为低成本单机/导出/恢复格式，但不能只靠 fsync=true 配置升级成 A2。

### 2.3 IndexedDB / Cloudflare DO

- IndexedDB adapter 的事务 Promise 等待 IDBTransaction.complete，源码上有 all-stores readwrite batch；但上游测试用 fake-indexeddb，真实 browser eviction/quota/tab owner/power failure 未验证。
- Cloudflare DO adapter 依赖平台 ctx.storage.transaction，并通过同一个 storage object wrapper 的 queue 串行；绕过 facade 的 raw storage access 不受该 queue 控制。真实平台 eviction/restart 与事务语义未在本轮验证。
- 两者不能只按 TypeScript 接口与 SQLite 等同评级；需要各自平台 contract test。

## 3. SQLite 与 PostgreSQL 的条件化选择

### 3.1 首发若为单用户本机 / 单主机

候选 SQLite：
- 单一权威 Store，所有 Task/Submission/Operation/Entry/Outbox 在同一数据库事务；
- WAL + FULL 作为 A2 候选；如果性能预算不允许，可明确退回 A1，而不是继续显示“强持久”；
- W1 只允许本机文件系统，多进程协调必须另有 Task owner CAS/lease，且所有 worker 都遵循；BEGIN IMMEDIATE 只串行化写事务，不自动串行化整个 Agent operation；
- 不得把 SQLite WAL 放到 NFS/SMB 等网络文件系统；WAL 共享内存要求同一 host；
- 备份/复制不能只复制主 .db 文件而忽略 WAL 一致性；必须使用 SQLite online backup/受控 checkpoint/关闭流程并测试恢复。
- 可信 Tool Host 若独立进程，也要以 operationId/epoch/grant 与 Coordinator 对账，不得把 process lock 当 effect ledger。

### 3.2 首发若为多主机 / 多租户

候选 PostgreSQL 或等价中央事务 Store：
- 本地 fsync=on，关键事务 synchronous_commit=on；官方文档说明非 off 的本地行为等待 WAL flush；
- 配置同步 standby 后，synchronous_commit=on 等待 standby flush 到 durable storage；remote_apply 进一步等待 standby replay 并可见，代价更高；remote_write 仅确认 standby file system write，不等于 standby OS crash 后仍持久；
- synchronous_standby_names 为空时，remote_apply/remote_write/local 与 on 都只提供相同 local sync level；
- 同步复制也不自动解决 split-brain/failover leader ownership；Promotion controller、旧 primary fencing、连接路由和恢复决策必须单独验证。

见 [PostgreSQL 18 WAL configuration](https://www.postgresql.org/docs/18/runtime-config-wal.html)（fsync、synchronous_commit 与同步副本语义）。

### 3.3 不把 PostgreSQL Sequence 当作 Event Cursor

PostgreSQL 官方明确 nextval()：
- 多会话原子分配不同值；
- transaction abort 后不回收，允许 holes；
- sequence 变更不是事务回滚的一部分；
- crash around uncommitted nextval/setval 时 sequence state 也可能不确定。

见 [PostgreSQL 18 Sequence Manipulation Functions](https://www.postgresql.org/docs/18/functions-sequence.html)。

因此，BIGSERIAL/identity/sequence 是唯一 ID 的好工具，但不能作为连续的 per-stream commit order。也不能推断 ID 小的一定先 commit。

**建议的 PostgreSQL per-stream cursor：**

在 stream_cursors(stream_id PRIMARY KEY, next_seq) 中，为每个 conversation/stream 维护一个事务性计数器：

1. 开启事务；
2. 对 stream cursor row UPDATE ... SET next_seq = next_seq + event_count ... RETURNING old/new range，获取该行锁；
3. 在同一事务插入具有这些 event_seq 的 outbox rows，并写入业务 projection；
4. commit 释放 row lock；
5. 同一 stream 的下一事务只能在前一个事务 commit/rollback 后获得 cursor row，并基于已提交的 next_seq 分配下一段。

这个方案让同一 stream 的分配顺序由事务锁定/提交控制，而不是依赖 sequence。它会让一个 conversation stream 的并发 commit 串行化；不同 conversation 的 cursor row 仍可并行。事务 abort 会回滚 cursor update，因而不会产生由该事务留下的 cursor 空洞（除非业务有意发 tombstone/skip marker）。

这是**目标实现方案**，需要针对 PostgreSQL isolation、row lock、死锁与事务重试做并发测试。

## 4. Snapshot + Cursor 必须来自同一视图

PostgreSQL Read Committed 下，事务内的连续 SELECT 可以看到不同的 committed snapshots；官方文档对此有明确说明。Repeatable Read 在事务开始后的第一个非事务控制语句建立 snapshot，后续 SELECT 看到同一视图，但写入冲突可能产生 serialization failure，需要重试。见 [PostgreSQL 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)。

目标 EventHub：
- GET snapshot 必须原子读取 projection snapshot + lastEventSeq，要么一个 SQL statement，要么同一个 Repeatable Read read-only transaction；
- 不得先读取最新 UI state，之后另一个 transaction 再读取 cursor；二者之间并发 commit 会造成客户端从错误 cursor 继续，丢事件；
- cursor 至少包含 {streamId, eventSeq, itemIndex} 或等价 tuple；如果一个 commit 含多条 event，itemIndex 在同一个 eventSeq 下定序；
- cursor 不是全局数据库 LSN，也不是 wall-clock timestamp；跨 stream 不承诺总序。

## 5. Transactional Outbox：只解决 DB 与事件生成的双写，不提供 exactly-once delivery

AWS Prescriptive Guidance 的 Transactional Outbox 说明：
- 业务状态与 outbox row 在同一 DB transaction 提交，避免业务 commit 与 publish 双写分裂；
- dispatcher 仍可能重复发送；consumer 应用 event ID 做幂等；
- event notification 必须按业务更新顺序发送；若服务间需要跨 DB 事务，则应设计 saga，而非伪装单事务。

见 [AWS transactional outbox pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。Debezium Outbox Router 用 aggregate key 作为 Kafka key，帮助维持 partition 内 ordering；见 [Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)。

### 5.1 Dispatcher 必须按 stream 保序

错误做法：所有 pending outbox rows 被多个 worker 任意 SKIP LOCKED，然后按可用行并发发送。若 stream seq=10 被慢 worker 锁住，另一个 worker 可能跳过它并发送 seq=11，造成客户端观察到倒序。

建议：
- 按 stream partition dispatcher；每条 stream 同时只有一个有效 dispatch lease；
- 只 dispatch 当前 stream 最早未完成的 event；后续 event 等待前序完成/重试；
- 多条 stream 可以并行；
- 每个 event 有稳定 eventId，每次发送 deliveryAttemptId；
- publish 成功但 dispatcher 未提交 delivered marker 时允许重复投递，client 以 eventId/cursor 去重；
- outbox delivered marker 是“至少一次交付的推进证据”，不是 consumer 已经应用的证明；
- 若 dispatcher 在 send/ack 之间网络中断，保留 pending 并重投；不得宣称 exactly-once transport。

### 5.2 Client cursor 与应用状态更新

- Client 只能在完整 apply event 后推进 applied cursor；
- 若 client 在 apply 后、持久化 cursor 前 crash，恢复后可能重复收到同一 event，因此 event reducer 必须幂等；
- 若先持久化 cursor 再 apply，crash 会跳过未应用的事件，禁止此顺序；
- 如果 UI state 和 cursor 能放同一 client-side transaction，则一起提交；否则服务端 replay 设计必须容忍重复；
- cursor 超过 retention window、stream reset 或 snapshot version 不兼容时返回 snapshot_required，不能静默把 cursor 拉到 latest；
- snapshot 与 cursor 同步读取；client 用 snapshot cursor 开始拉取其后事件，避免 snapshot/live event gap。

### 5.3 Provisional streams 与 durable events

Model token delta、tool stdout、typing/status 可走 E0 ephemeral channel，标记 runId + attemptId + chunkSeq；retry/abort/fallback 时发 invalidate/supersede。最终 assistant/tool messages 必须由 committed Entry 生成 E1/E2 事件。UI reconnect 不要求重播每个 token，但必须能从 snapshot 重建最终事实。

## 6. API 与审计合同建议

### 6.1 Submission acceptance

submit() 返回值应区分：
- accepted：Submission + Run/Task 已经 commit 到当前 Store；
- ackProfile：A0/A1/A2/A3 中实际达到的提交保证；
- submissionId、clientRequestId、streamCursor；
- 如果只进入内存队列，不得返回与 durable accepted 相同的状态。

客户端重试必须使用稳定 clientRequestId。数据库建立 unique key (tenantId, conversationId, clientRequestId) 并存 payloadHash：
- 同 key + 同 payloadHash：返回已受理/已完成的相同 Submission；
- 同 key + 不同 payloadHash：返回 idempotency_conflict，绝不能默默覆盖；
- 服务端在提交 ACK 发送前断线，客户端重试同 key 查询已存在提交，不创建第二个 Run。

### 6.2 Commit result unknown

DB transaction commit 成功后网络断开，调用端可能只知道“没有收到 ACK”，不代表数据库 rollback。必须：
- 用稳定 commandId/operationId 在重连后查 journal；
- 查到 committed record 则继续，不再重复副作用；
- 查不到且 Store authority 明确提供最终一致/线性一致查询后才可重新 admit；
- authority 本身不可达时返回 submission_outcome_unknown，不凭客户端超时推断未提交。

### 6.3 Operation / Provider Usage

每次 Provider request 和 Tool operation 独立有 stable ID 与 attempt IDs。Provider timeout 可能已经产生 tokens/费用；如果 Provider 不提供原生 idempotency 或 usage query，则保存 usage_unknown，不能自动创建一个“同样的”新请求并声称没有重复计费。

## 7. 条件化技术选型结论

| 产品约束 | Store 候选 | 默认 ACK profile | 不包含的保证 |
|---|---|---|---|
| 本地单用户、单机、进程崩溃恢复优先 | SQLite WAL NORMAL | A1 | 最近 ACK 的断电持久性 |
| 本地单用户、用户提交/Tool Intent 断电不丢优先 | SQLite WAL FULL | A2 候选，需设备/FS 实测 | 多主机 writer、外部 effect exactly-once |
| 多进程同主机、本地 SSD | SQLite WAL FULL + transactional owner rows/leases | A2/W1 | network FS、多主机 failover |
| 多主机/多租户协调 | PostgreSQL + row-CAS/lease | A2/W2；HA 配同步副本可 A3 | tool effect dedup；split brain 仍需 fencing |
| 浏览器离线本地缓存 | IndexedDB | 真实浏览器测试后声明 A1/A2 | 服务端 authority、多 tab owner、quota 不丢 |
| JSONL appendable archive / export | 适合作为辅助恢复/导出 | 现有 Pi adapter 不能声明 A2 | per-commit main marker fsync、multi-process writer |
| Memory | 测试与瞬时执行 | A0 | crash recovery |

**当前没有足够产品需求来最终决定 SQLite 还是 PostgreSQL。** 推荐条件化而非强行定案：若首发明确单用户本机，优先 SQLite FULL；若多租户/跨主机，优先 PostgreSQL；避免把 JSONL 作为强 ACK 权威 Store。

## 8. 需新增的验收门槛（研究计划，未执行）

1. A1/A2：分别对 SQLite NORMAL/FULL 在 process kill、OS crash、虚拟磁盘断电模拟下验证 ACK 数据恢复；记录 SQLite/Node/OS/filesystem/device 型号与测试次数。
2. A2 JSONL：主 marker append 后、marker fsync 前、sidecar flush 前/后、rename/reclaim 前/后 crash；确认恢复后只显示完整 commit 或可检测 unknown。
3. A3：Postgres 本地 WAL flush、同步 standby on 与 remote_apply，在 primary/standby crash 与 failover 交错下验证已 ACK 数据保留；同步副本配置与 failover fencing 需明确。
4. W1/W2：多个 Scheduler 同时 claim 同一 Task、lease 到期旧 worker 发新命令、主机暂停后恢复；验证只有一个有效 owner 可发起新 effect。
5. E1/E2：outbox publish ack 丢失、dispatcher crash、duplicate delivery、seq=10 慢/seq=11 快、client apply 后 cursor 保存前 crash、cursor retention 过期；验证去重/保序/snapshot reset。
6. PostgreSQL stream cursor：两事务竞争同一个 cursor row，commit/rollback/serialization failure；验证同 stream 顺序、事务回滚不消耗 eventSeq、不同 stream 并行。
7. API acceptance：DB commit 完成后丢 ACK；client 用同 clientRequestId 重试，确保同 Submission 被返回；不同 payloadHash 冲突。
8. X0–X4：对真实 Shell、MCP、provider API 逐个 crash injection，记录 effect count/receipt/idempotency TTL/query semantics，不能用 fake host 代替。

## 9. 本轮结论与未知

### 直接源码 / 官方文档事实
- Pi Node SQLite adapter 默认 WAL/NORMAL，事务使用 BEGIN IMMEDIATE / COMMIT；Pi SqliteStorage 把记录、documents、next_seq 放同一 SQLite transaction；来源见报告 55 与上述固定 blob SHA。
- Pi JSONL 的 fsync 选项 flush sidecars，但 main marker 并非每个 commit 都 flush；来源 jsonl/storage.ts blob 4b03fd5beff465841ec3dc069d32fd90241604eb。
- SQLite 官方文档定义 WAL NORMAL/FULL 与 power-loss durability 区别；WAL 不支持 network filesystem。
- PostgreSQL 官方文档定义 fsync/synchronous_commit/local/synchronous standby 语义；Sequence nextval 不回滚；Read Committed successive statements 可见不同 snapshots，Repeatable Read 保持事务 snapshot。
- AWS outbox 指南明确消费者可能收到重复消息，需要幂等处理，并要求按业务更新顺序发布。

### 架构推断
- R0–R4 必须拆成 capability vector；否则一个工具的 X0 UNKNOWN 会被一个数据库的 A3 淹没。
- 同 stream 事务性 row counter 能比非事务 sequence 更直接地表达提交顺序，但要接受每 stream 的 row-level serialization。
- Outbox dispatcher 的并行策略必须按 stream 保序，不能只依赖数据库查询排序。
- UI snapshot/cursor 与 client applied cursor 必须一起建模；transport ack 不等于 event apply。
