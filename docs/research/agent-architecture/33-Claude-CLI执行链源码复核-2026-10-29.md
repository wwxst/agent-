## 1. 从 CLI 入口到 Agent Loop

### 1.1 CLI 启动入口

`modules/cli` 的 `Ve()` 是发布版入口函数。静态可见的阶段包括：

1. 设置运行环境并执行启动/策略检查；
2. 处理 `--version`、后台 worker、MCP server、remote-control 等专用分支；
3. 解析 cwd、CLI flags、配置与 session 类型；
4. 对普通交互路径动态导入 `chunk-9b0nx8jt.js` 的 `main`，最后调用 `await Ce(s)`。

因此 CLI 入口不是“直接调用模型”。它先分流大量命令和运行模式，普通交互、非交互打印、SDK 子进程和后台任务会经过不同启动路径。

### 1.2 main 与交互会话驱动

`chunk-9b0nx8jt.js` 中：

- `Ru`（@39,908）是 main 函数，建立主程序/退出处理并进入 `Ji`；
- `Ji`（@40,838）构建 CLI program，注册命令和解析参数；它把 `or` 作为 `runInteractiveSession` 回调传给会话/渲染入口；
- `or`（@57,919）是交互会话路径的一部分。

`chunk-1vdc3qtt.js` 为交互/SDK 会话路径提供会话驱动：其上下文中显式注入 `runQuery: YL`。驱动先把用户输入放入队列，再从一个独立的 engine iterator 逐条消费事件（`De.next()`），按类型处理 assistant/user/progress/attachment/system/result。遇到 `result` 时，驱动结束该 Turn、汇总 usage、permission denials 和终态信息。

**观察：** 会话/显示/会话记录驱动与底层 Agent Query Loop 是分层的。前者消费事件流并更新会话状态，后者负责模型与工具编排。该层次是源码事实；实际某次 Desktop 会话选择哪个入口分支仍未动态验证。

## 2. Query Loop 的状态与每轮执行

### 2.1 `YL` 外层包装

`chunk-smbjjyps.js` 的 `YL`（@135,116）是异步生成器。它会：

- 为本次 query 建立会话/消息相关的资源包装；
- 预处理工具定义；
- 根据 `QOn()` 选择普通 `su` Loop 或带额外观察器的 `Jm` 包装；两条路径仍会进入 `su`；
- 在退出时运行清理、命令生命周期收束和终态记录。

因此，`YL` 不是单一模型请求函数，而是 query 生命周期外壳。

### 2.2 `su` 与 `iu`

`su`（@137,532）初始化 query 的 messages、工具上下文、依赖和 guard state。状态包括消息历史、`toolUseContext`、压缩跟踪、终止/重试 guard、turnCount 和 transition。内部 `iu`（@141,376）负责一次模型请求轮次，外层以 `next_turn` sentinel 反复调用它，直到返回终态。

每轮可确认的顺序：

1. 检查 `shouldStopBeforeNextApiCall` 等停止条件，建立 query chain/depth/round 时间信息。
2. 合并当前历史和队列中到达的消息。
3. 构建 context、system prompt、tool list 与模型事实。
4. 请求前运行 autocompact。压缩结果可能重建 messages/context；快速重复压缩会触发 breaker，而不是无限循环。
5. 调用依赖中的 `callModel`，消费流式事件。
6. 收束/排空工具结果，运行相关 hooks，更新 messages 与 context。
7. 若允许继续，则设置 `transition:{reason:"next_turn"}`，下一轮输入为旧消息、assistant 响应和工具结果的组合；否则返回 completed/error/aborted/max-turns 等终态。

默认依赖 `Td()` 注入 `callModel:zIt`、`autocompact:rkr`、UUID 和时间函数；Loop 同时允许使用 `e.deps` 覆盖默认依赖。**这是内部依赖注入点的源码事实，不代表公开稳定 API。**

## 3. 模型请求与流式消息构造

### 3.1 请求构造

`zIt`（`chunk-4b60tdnk.js` @2,690,290）进入模型请求/流式包装链；下游 `Xmn` 构建请求参数。源码中的请求体 `Hc` 包含 model、messages、system、tools、tool_choice、max_tokens、thinking，以及按条件添加的 metadata、context management、safeguards 等字段。

客户端由 `JH` 按当前 model/provider、credentials、storage、fetch override、abort signal 等创建。实际发送点在 @2,780,615：

- 调用 `beta.messages.create(..., stream:true)`；
- 传入 abort signal 和按需附加的 headers；
- 获取 response stream 并消费其事件。

这确认 CLI 自己构造并发起模型 API 请求，而不是只把用户消息交给 Desktop/SDK 让宿主完成模型调用。

### 3.2 从原始 SSE 事件到内部消息

流解析逻辑维护当前 message、content block、usage、stop reason 和已完成 block。关键行为：

- `message_start`：建立当前 API message；
- `content_block_start`：初始化 text/thinking/tool_use 等 block；
- `content_block_delta`：累积 text、thinking 或 `input_json_delta.partial_json`；
- **`content_block_stop`：解析已完成 block，构造内部 `type:"assistant"` 消息行并 yield；**
- `message_delta`：更新 usage、stop reason 和 context-management 信息；
- `message_stop`：关闭 message envelope，标记 stream 完成；
- 原始事件还会作为 `stream_event` 发给上层会话驱动。

当 stream 结束时仍有未关闭 block、缺少必要终态、没有 message_start/已完成内容等情况，解析器会记录错误并抛出特定异常，供更高层 retry/fallback 逻辑处理。该路径具有 byte/message idle watchdog、stall 记录和非流式 fallback 机制；完整错误分类与重试矩阵仍需下一轮逐支核验。

## 4. 工具执行：完整 ToolCall block、流式调度与结果回填

### 4.1 工具何时进入执行队列

在 `su` 的模型事件消费循环中（约 @181,931）：

1. 收到内部 `assistant` 消息后，找出其中的 `tool_use` blocks；
2. 若包含 ToolCall，先 `await r.appended(v)`；
3. 将该 assistant 消息与各个 tool_use 交给 `streamingToolExecutor.addTool`；
4. 继续消费流并通过 `In()` 排出已完成结果/进度。

流解析器在 `content_block_stop` 才把完整 block 变成 assistant row；在此之前，tool input JSON 仍在累积。因此，源码支持的准确表述是：**工具可在完整 ToolCall block 已结束、输入已形成后启动，但不必等待整个 API message 的 `message_stop`。** 不能将其描述为“模型只输出了部分 JSON 就开始执行”。

这里的 `r.appended(v)` 是 query 提供的 append 回调。它发生在 `addTool` 前，但本轮尚未追完 `ha()` 与底层 append 实现，因此不把它直接等同于 fsync、事务提交或独立 durable Intent。

### 4.2 `StreamingToolExecutor` 的并发合同

`chunk-smbjjyps.js` 的 `class vs`（@52,975）维护每个工具的 queued/executing/completed/yielded 状态，并保留进度、桥接事件、结果和 context layers。

- 添加工具时先查工具/别名；若不存在，会生成带原 tool_use_id 的合成错误 tool_result。
- 已知工具先对 input schema 做 `safeParse`，再调用 `isConcurrencySafe(parsedInput)`；schema 失败或判断抛错时按非并发安全处理。
- 若当前没有执行中的工具，可以启动队首工具；若已有执行中工具，只有“新工具安全且所有执行中工具也安全”时才允许并发。非安全工具会等待已有执行结束，且会阻断其后的队列推进。
- `executeTool` 异步运行 `wG`，持续收集消息、progress、bridge events 和 context layers。
- `getCompletedResults()` 按工具收到的顺序遍历已完成结果；执行中的非安全工具会挡住后续结果的发出。
- `getRemainingResults()` 在响应流结束后关闭 responseOpen，反复推进队列、发出完成结果/进度，并等待仍在运行的调用收敛。

流消费层 `nl` 会在“下一条模型流事件”与“工具执行器变为可排出状态”之间竞速；工具进度/完成后可触发 `tool_drain_tick`，由 Query Loop 在模型流仍在消费时排出工具更新。这是流式并发优化的实际机制，而不只是按最终 ToolCall 数组调用一次 `Promise.all`。

### 4.3 工具路由、权限与结果

`chunk-4b60tdnk.js` 的 `wG`（@3,957,580）是实际工具路由器。源码路径包括：

1. 等待必要的 pending MCP/tool discovery 状态；
2. 根据名称/alias 查找工具，处理缺失工具与工具动态可用性；
3. 在 `AYr`（@3,967,595）等路径验证 JSON/schema、工具输入和 PreToolUse hooks；
4. 由权限决策 helper 计算 allow/deny/ask；ask 可通过传入的 `canUseTool` 交给宿主/用户审批；
5. 拒绝或验证失败会生成与原 tool_use_id 配对的错误 `tool_result`；
6. allow 路径调用工具实现，并将结果通过 `mapToolResultToToolResultBlockParam` 等映射为模型可消费的 tool_result；
7. 路由中存在 `hosts.runToolUse` 的跨 Host 分支，所以不能假定每个工具都在 CLI 进程本地执行。

工具结果和进度由 Query Loop 收集；`Gr` 等逻辑将其规范化后加入本轮结果集合。之后会排空剩余工具、运行 PostToolBatch/Stop 等 hooks，并依据工具是否请求结束 Turn、maxTurns、abort 和其他 guard 决定终态或下一轮。

## 5. 失败、取消与上下文：本轮已经看到的边界

- Query Loop 的 `Hr` 错误收束路径会尝试排出已经完成的工具结果，并处理 assistant/tool_result 配对后再输出错误终态；工具执行错误不能简单等同于“整个工具批次完全没有发生”。
- `discardAndAbortInFlight` 会区分已经完成、尚未启动和正在执行的调用，对执行中的工具发 abort，并返回工具 ID/启动状态供上层清理。上层 fallback 分支会 tombstone 被丢弃的消息并重建 executor。
- autocompact 在请求前运行；prompt-too-long 还存在 reactive compact/retry 路径。重试状态由 guard/transition 记录，不是简单地无限重发同一个请求。
- Loop 有 abort、background requested、max turns、stop hook、model/API error、prompt too long、image error 等多个终止原因。

这些代码证明 CLI 内部存在复杂的错误恢复与流式工具清理逻辑；但本轮尚未逐一验证每个 fallback/cancel 分支中已产生的外部副作用如何被协调，也没有动态运行证明其最终行为。

## 6. 版本漂移警告：旧版 TypeScript 不能直接代表 2.1.304

旧版参考包 `reference-2.1.88/restored-src/src/services/tools/StreamingToolExecutor.ts` 有可读的同名类，但其字段和取消策略与 2.1.304 的提取类结构不相同。例如 2.1.88 明确包含 `hasErrored`、`erroredToolDescription` 和 `siblingAbortController`，并在 Bash 工具错误时取消 sibling；2.1.304 的 `class vs` 则以 `responseOpen`、`drainGeneration`、`pendingBridgeEvents`、`contextLayers` 等状态为显著结构，且有独立的 `discardAndAbortInFlight`。

这至少证明不能把 2.1.88 的注释或错误策略直接写成 2.1.304 的事实。下一步应继续逐项对照版本差异，而不是把旧 TS 当成新版原始源码。

## 7. 证据等级与待确认问题

### 已由当前版本静态源码证实

- CLI 入口将普通会话交给 main/session 驱动；会话路径把 `YL` 作为 `runQuery` 注入。
- `YL → su → iu` 是主要 query Loop 结构；`next_turn` 驱动同一 query 中的下一轮。
- CLI 自己构建 Messages API 请求并以 stream 模式消费响应。
- 完整 content block 在 `content_block_stop` 后可被转换为内部 assistant row。
- Query Loop 收到带 tool_use 的 assistant row 后会先 await append callback，再将 ToolCall 放入流式执行器。
- 工具并发由 `isConcurrencySafe` 和正在执行工具的状态控制；执行器会在流结束后 drain。
- 工具路由包含 schema/PreToolUse/权限/Host 路由/结果映射路径。
- context compaction、retry/fallback、abort 与多个终止状态在主 Loop 中均有实现分支。

### 推断（不是独立验证事实）

- 流式提前启动工具的目的之一是减少模型响应延迟；代价是执行器、流事件、fallback、tombstone 和取消的状态协调更复杂。
- CLI 的会话驱动与 query loop 分层，有助于让交互 UI、SDK/非交互入口复用同一套核心 query 机制。

### 未知 / 下一步必须查证

1. `r.appended(v)` 的确切持久化语义、写入顺序、崩溃恢复行为，以及它与工具启动之间是否存在独立调用账本。
2. `wG` 的本地执行、MCP、宿主转发分支在每类工具下的选择条件和可信边界。
3. stream retry、non-streaming fallback、model fallback 和 refusal fallback 的完整状态转移；哪些分支会取消已启动工具、保留/丢弃哪些消息。
4. 用户 interrupt、turn abort、shutdown、后台接管与工具的 interruptBehavior 如何互动；取消是否意味着底层副作用已停止。
5. subagent 的父子消息、预算、权限、取消、后台运行与恢复路径。
6. 上述分支没有在本轮动态执行，静态可达路径不等于某个 feature gate 下的实际运行行为。

## 8. 本轮结论与下一步

**本轮结论仅限于：Claude Code CLI 2.1.304 内有完整的 Agent Query Loop；它通过流式 API 解析、工具执行器、权限/工具路由与消息回填完成多轮 Agent 执行。其工具执行器可在完整 ToolCall block 完成后、整个 message 结束前启动安全工具，并与模型流交错排出结果。**

这不是最终架构推荐，也不代表要复刻这套实现。

下一轮仍留在 Claude CLI 研究阶段，按顺序追踪：

1. `r.appended` / query resource / transcript/session persistence 的真实实现；
2. `wG` 的 host/MCP 路由与权限判定完整链；
3. streaming failure、retry、fallback、abort 和 tombstone 的状态机；
4. 然后再研究 subagent、context compaction 的完整状态变化。

在 Claude CLI 的关键执行与失败路径研究完成前，不进入目标架构定案或开发。
