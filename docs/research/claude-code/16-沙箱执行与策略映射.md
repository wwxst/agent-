# 16 · Claude Code 沙箱执行与权限规则映射：源代码级追踪

> 研究日期：2026-10-24  
> 本文直接验证范围：**用户旧仓库的 Claude Code CLI 2.1.88 Source Map 提取源码**。本轮未能再次读取 ZIP 中 2.1.304 的原始模块，因此不能将下述条件分支、默认值或平台能力归属于 2.1.304。未执行实际系统调用、沙箱探测或安全渗透测试。

## 一、核心判断

旧版并没有一个全局 `sandbox=true` 就必然沙箱执行的逻辑。真实决策涉及：

1. Sandbox 设置启用、平台支持、运行依赖；
2. 用户/管理策略设置；
3. 工具调用参数（例如是否显式禁用沙箱）；
4. 命令是否命中排除规则；
5. 转换成 OS 沙箱运行时配置；
6. Bash 实际执行入口传递 `shouldUseSandbox`；
7. 由外部 `@anthropic-ai/sandbox-runtime` 负责部分系统级封装。

**这条链必须区分“允许不使用沙箱”与“系统级限制已经生效”。** 旧版应用逻辑明确允许存在不使用沙箱的命令及配置；是否可执行还可能另受权限提示和管理策略控制。

## 三、真正决定是否沙箱执行的旧版条件

### 3.1 默认值与能力

`sandbox-adapter.ts` 中可以直接读到：

- `sandbox.enabled ?? false`：旧版的一般设置缺失时不默认启用。
- `autoAllowBashIfSandboxed ?? true`：已沙箱化 Bash 可自动授权的另一个设置，与“能否启动沙箱”不同。
- `allowUnsandboxedCommands ?? true`：允许无沙箱命令的另一设置；并不代表所有无沙箱命令无须权限审批。
- `failIfUnavailable ?? false` 参与 `isSandboxRequired` 的判定；此函数是否对每条执行路径有最终拦截作用，必须继续追踪其调用者。
- 平台支持检查在适配器注释中列为 macOS、Linux、WSL2+，WSL1 不支持；还需要底层运行时提供必要依赖。

**全部仅是 2.1.88 样本中的直接源码默认值**，不是产品通用承诺，更不是 2.1.304 的默认值。

### 3.2 特定命令排除

[shouldUseSandbox.ts L18–126](https://github.com/wwxst/-/blob/main/restored-src/src/tools/BashTool/shouldUseSandbox.ts#L18-L126) 的原注释明确指出，`excludedCommands` 是用户便利配置，**不是安全边界**。

旧版处理复合命令、环境变量前缀与包装命令的候选形式，尝试识别排除模式。但是这段文本匹配不能被当成完整 Bash 语言语义解析器或 OS 强制策略。

**自研决策**：被标记为“不可在沙箱内运行”的命令只能触发一条明确的“无沙箱审批/拒绝”路径，不能自动视为已获更高权限。

### 3.3 沙箱不可用与初始化失败

`isSandboxingEnabled` 在以下情况直接返回 false：平台不支持、依赖检查失败、当前平台不在 enabledPlatforms 中、用户未启用沙箱。随后 `getSandboxUnavailableReason` 可生成“用户已要求沙箱但依赖不足”等警告。

[initialize L730–790](https://github.com/wwxst/-/blob/main/restored-src/src/utils/sandbox/sandbox-adapter.ts#L730-L790) 里有值得特别注意的实现取舍：

- 提前设置 initializationPromise，避免其他路径观察到“尚未开始初始化”而继续。
- 底层初始化失败时清空 Promise，并**记录错误但不再向调用者直接抛出**。
- wrapWithSandbox 在 isSandboxingEnabled 为 true 的情况下检查 Promise 是否存在，否则抛初始化错误。

这表明“初始化错误如何传递到实际 ToolHost”需要沿底层运行时进行端到端验证。**仅凭这里的 catch 不能断定会产生无沙箱绕过；也不能断定绝对 fail-closed。**

## 四、系统权限映射并不是“只允许工作区”

[convertToSandboxRuntimeConfig](https://github.com/wwxst/-/blob/main/restored-src/src/utils/sandbox/sandbox-adapter.ts#L170-L380) 有多个具体规则：

- network.allowedDomains、deniedDomains，以及 Unix Socket / 本地监听相关设置。
- 从 WebFetch allow/deny 提取 `domain:` 规则；受管理策略时可以仅使用 policySettings 中的域名。
- 默认 writable 路径包含当前目录与 Claude 临时目录，另有 additionalDirectories、Git Worktree 主仓库路径等扩展。
- 主动限制写入 `settings.json`、管理策略目录和 `.claude/skills`。
- 对某些能够诱导未隔离 Git 进行危险动作的伪造裸仓库文件进行特殊保护和事后清理。
- sandbox.filesystem 规则和普通 PermissionRule 对以 `/` 开头的路径有不同语义，解析时必须保留配置来源。

这说明应用层授权与 OS Sandbox 配置之间存在**跨规则域转换**。转换错误可能导致被批准工具与实际文件/网络范围不一致。

**自研建议**：内部用规范化的 `ResourceCapability` 表达真正可读/可写的路径、网域、Socket 与进程权限，再生成平台专用沙箱策略；未经验证不得在前端显示“已沙箱保护”。

## 五、动态策略更新与竞态

- 初始化时先构建当前运行配置，然后订阅 settingsChangeDetector；
- 设置变化时调用底层 `updateConfig`；
- `refreshConfig()` 在权限更新后同步重建配置，注释明确意在避免 pending requests 使用过期策略；
- 同一 Session 内缓存 Git Worktree 的主目录，以免异步查询导致策略构造竞态。

但 OS 已经启动的进程与新策略之间是否原子生效，本文无法从适配器代码证明。

## 六、对自己的 Tool Host 的约束

自研的 Tool Host 必须采取比“沙箱布尔值”更明确的合同：

```ts
type IsolationRequirement =
  | { mode: 'required'; filesystem: ResourceCapability[]; network: ResourceCapability[] }
  | { mode: 'explicitly_unsandboxed'; approvalId: string; scope: string };

type IsolationReport = {
  mode: 'enforced' | 'unsandboxed_approved' | 'unavailable';
  platform: string;
  policyVersion: string;
  enforcementDetails: Record<string, unknown>;
};
```

- `required` 如果无法完成隔离，就拒绝执行；
- 明确无沙箱必须绑定用户、工具、输入指纹、工作区、过期时间和宿主身份；
- 每次执行持久记录实际使用的隔离版本，而不是只记录“曾经启用”；
- `sandboxUnavailable` 必须作为错误/状态曝光，而不是普通日志；
- 高风险 Shell 要在子进程/容器/OS 安全边界强制实施，并通过故障测试验证。

## 七、对应验收测试

T16-01 用户要求强制沙箱而底层依赖缺失：0 次高风险工具执行。  
T16-02 路径权限允许读、拒绝写：Shell 无法以符号链接/挂载点越权写入。  
T16-03 网络白名单配置变更：后续新 ToolCall 遵守新规则且记录 Policy 版本。  
T16-04 多个工作区/Worktree：不泄露其他工作区路径能力。  
T16-05 被 excludedCommands 匹配的命令：不自动放行，必须按无沙箱路径重新授权。  
T16-06 Sandbox 初始化失败：用户能看到可核验的拒绝/错误，不静默继续危险执行。  
T16-07 运行中更新权限：审批输入版本与执行时检查版本严格对应。  
T16-08 Mac/Linux/Windows/WSL 不支持的能力：明确报告 NotSupported，不假装等效隔离。

### 尚不能确认

2.1.304 的上述默认值、所有 OS 平台分支、实际底层 Sandbox Runtime 系统调用覆盖范围、特定命令实际能否越权。本报告是**旧版沙箱架构研究**，不是安全审计结论。
