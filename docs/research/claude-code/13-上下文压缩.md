# 13 · Context Budget、自动压缩与信息保留

> 证据：旧版 2.1.88 核心压缩模块直接可读；新版 2.1.304 可见主循环和压缩下游函数。不同版本默认阈值和实验开关不得混用。

## 一、压缩并非一个提示词功能

旧版 [query.ts](https://github.com/wwxst/-/blob/main/restored-src/src/query.ts#L365-L380) 在模型请求前整理上下文，并应用工具输出预算；其余分支还有 microcompact、auto compact、错误恢复和任务跟踪。

新版 chunk-smbjjyps.js@144401 在单轮 iu 中调用 I.autocompact，主模型请求点在 @162542。chunk-4b60tdnk.js@2522174 处存在 async generator rkr，负责压缩决策与多个执行分支。这证明压缩是实际的执行阶段，不只是 CLI 中提供的 /compact 命令。

## 二、旧版触发策略：可核对的具体值，仅限 2.1.88

[autoCompact.ts](https://github.com/wwxst/-/blob/main/restored-src/src/services/compact/autoCompact.ts#L48-L90)：

- 使用 getEffectiveContextWindowSize(model)，阈值约为有效窗口减去 AUTOCOMPACT_BUFFER_TOKENS；
- 源文件中可确认缓冲值为 **13,000 tokens**（L62）；warning/error 缓冲均为 **20,000**（L63-64），manual 缓冲为 **3,000**（L65）；
- CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 可以在有效范围内调低测试阈值。
- L160-239 的 shouldAutoCompact 会避免压缩自身及 session_memory 等内部查询递归；先检查功能开关，再计算 Token 估算和是否越过阈值。

**不能将上述数字当作 2.1.304 的固定行为，也不应将其直接复制为自研内核的模型无关常量。**

## 三、失败熔断是值得重点学习的机制

旧版 autoCompact.ts L51-59 定义了 consecutiveFailures；L67-70 将连续压缩失败上限设为 **3**。L253-264 在熔断开启后跳过再次请求；L312-349 在成功时清零、失败时累加。通过这一机制避免持续超限情况下每轮重复浪费模型请求。

自研建议：

1. 把“压缩失败”与“模型请求失败”拆分成不同错误域；
2. 为摘要请求配置独立 Timeout、Token、成本与重试预算；
3. 失败达到上限时停止或切换保守截断策略，不能无限循环；
4. 仅当已确认安装有效上下文检查点时重置失败计数；
5. 恢复进程后熔断状态也必须可持久化，避免重启后重试风暴。

## 四、手动压缩、自动压缩与局部压缩

旧版 [compact.ts](https://github.com/wwxst/-/blob/main/restored-src/src/services/compact/compact.ts#L387-L429) 的 compactConversation 在压缩前执行 PreCompact Hooks；触发方式区分 auto / manual，Hook 可以贡献自定义指令。L772-833 的 partialCompactConversation 支持对选中消息之前或之后进行局部摘要处理，保留其余消息并处理旧的 compact boundary，避免老边界在恢复时覆盖新摘要。

旧版 autoCompact.ts L287-310 还能看到先尝试 session memory 压缩的分支，未处理则进入传统 compactConversation（L312-333）。

这说明“上下文压缩”至少包含：策略判断、摘要生成、消息边界维护、Hook、替换上下文与后续恢复。功能名称相似不代表算法相同。

## 五、信息回填与边界

旧版 compact.ts L1415-1457 的 createPostCompactFileAttachments：

- 检索之前读取过的文件路径与时间；
- 排除保留消息中已经带入的路径；
- 依据最近使用顺序选择有限数量文件；
- 使用额外 Token 限额产生压缩后的文件附件；
- 避免摘要后模型完全失去当前代码工作区的必要背景。

旧版还明确用 [image]、[document] 之类的文本占位处理摘要阶段某些媒体输入，不能假设所有多模态内容都可原样进入压缩模型。此处引用的是处理策略，不等于新版本所有媒体路径相同。

**对自研内核**：文件回填不应盲目复制整个源文件；要考虑权限、路径是否仍有效、内容是否已发生变更、是否保留敏感数据。压缩摘要不能取代 ToolCall 执行事实、审批记录或外部产物的持久依据。

## 六、新版 2.1.304 可确认的额外复杂度

chunk-4b60tdnk.js@2522174 的 rkr 中可看到：

- 基于模型和压缩配置决定路径，存在替代模型处理分支；
- 环境禁用压缩时返回 not_needed；
- consecutiveFailures 达到阈值可触发 failure_breaker_open；
- 依据窗口、已预处理状态和触发类型判定是否压缩；
- 返回区分 compacted、failed、hook_blocked 等状态。

chunk-smbjjyps.js 中同时能定位 autocompact、reactiveCompact、工具结果预算以及主模型调用前的上下文准备。**不能仅凭 rkr 名称推导所有触发条件的时间顺序或默认配置**；需要针对不同模型、开关和异常做动态验证。

## 七、我们自己的 Context Engine 设计要求

- **硬边界**：Provider 发送请求前必须证明 Context 估算低于保守上限，且为输出预留余量；
- **检查点**：把输入消息范围、摘要模型、摘要版本、保留消息列表、预算与来源写成记录；
- **保留事实**：当前用户目标、最近有效约束、ToolCall ID 与结果状态、工作区引用不可凭摘要抹除；
- **低信任标签**：外部文件内容和工具输出在摘要中不能升级为 system 级权限；
- **恢复优先**：压缩不能改变原有批准/拒绝/ToolResult 的持久事件；
- **失败可解释**：超预算、摘要失败、Token 使用量未知时报告清晰原因并给出安全退路；
- **媒体路径**：图片、音视频和超大文件用 Artifact 引用与有限摘录，避免凭摘要虚构内容。
