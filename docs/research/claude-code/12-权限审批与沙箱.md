# 12 · 权限决策、Hooks、工具执行与沙箱边界

> 证据：2.1.88 可读源码 + 2.1.304 打包 JavaScript。静态核对，不是独立渗透测试或操作系统隔离认证。

## 一、必须区分四种不同安全机制

1. **工具定义及参数验证**：工具是否存在、输入是否满足 Schema、命令结构是否合理。
2. **策略授权**：显式 deny / ask / allow 规则、权限模式、工具自身 checkPermissions。
3. **用户与宿主审批**：在 ask 分支调用 UI/SDK permission callback，等待结果，处理拒绝与取消。
4. **操作系统强制执行**：实际 Shell / 文件 / 网络权限边界；这必须在执行器中强制落地，不可仅由模型或 UI 保证。

Claude Code 同时包含这些层次，但并非一个文件中完成。源码中出现 SandboxManager 不等于所有平台、命令、文件系统访问都实际处于同样级别的沙箱内。

## 二、旧版策略链的可复核决策次序

位置：[permissions.ts](https://github.com/wwxst/-/blob/main/restored-src/src/utils/permissions/permissions.ts#L1158-L1319)。

- L1163-1165：执行前检查 abort signal。
- L1169-1179：先判断整个工具是否被显式 deny。
- L1183-1205：查看工具级 ask 规则；对启用了 Sandbox 自动放行的 Bash 有条件性处理，非沙箱命令仍需遵守 ask。
- L1208-1223：通过 inputSchema.parse 验证，并执行 tool.checkPermissions；取消异常向外传播，其他检查异常会被记录。
- L1225-1260：工具自身的 deny、内容敏感 ask、安全检查 ask 在特定条件下优先于模式级放行。
- L1262-1281：重新读取最新 AppState 后决定是否启用 bypassPermissions/相关模式，避免使用旧状态。
- L1283-1297：已有整工具 allow 规则可放行。
- L1299-1319：未决的 passthrough 最终转换为 ask。

这说明**授权不是简单的 allowlist 布尔查询**。尤其“有 bypass 模式”不等于任何危险写入必然绕过安全检查。但这些源代码展示的是该版本的某一权限检查路径，不证明所有平台的实际隔离无漏洞。

### Hook 与权限合成

旧版 [useCanUseTool.tsx](https://github.com/wwxst/-/blob/main/restored-src/src/hooks/useCanUseTool.tsx#L27-L95) 中，函数先处理 abort 和 hasPermissionsToUseTool / forceDecision；allow 可以直接解析并返回规范化输入，deny 返回拒绝；ask 分支可能走自动检查、分类器或互动 UI。L130-168 可见先尝试部分自动检查再显示交互式审批。

新版 chunk-4b60tdnk.js@3927471 的 Svr/XVr 处理 PreToolUse 决策：Hook 可返回 deny、allow 或 ask，以及可能更新后的输入；随后还有安全检查、宿主审批和策略判断的逻辑。@3976664 Svr 的结果进入执行链；@3980050 拒绝被包装为 is_error tool_result，@3985545 才进入 e.call。chunk-451m4237.js@8400-14200 还能定位 SDK/宿主 can_use_tool、批准/拒绝以及规则更新的处理。

**重要限制**：新版本权限链有多个 feature gate、SDK 配置和宿主目标。不能仅看到 PreToolUse allow，就推断在每条代码路径上都会自动跳过更高优先级的拒绝规则；也不能假设所有工具都必定弹出 UI。

## 三、工具与文件路径不是简单字符串匹配

旧版 [filesystem.ts](https://github.com/wwxst/-/blob/main/restored-src/src/utils/permissions/filesystem.ts#L604-L660) 中 checkPathSafetyForAutoEdit 检查原始路径与符号链接解析路径，专门识别 Windows 的特殊路径形式和一些敏感配置文件（如 .git、.claude、shell 启动文件等）。这属于防止权限绕行的“应用层路径安全检查”。

旧版 [FileEditTool.ts](https://github.com/wwxst/-/blob/main/restored-src/src/tools/FileEditTool/FileEditTool.ts#L115-L165) 可看到：工具回填/权限匹配使用扩展后的路径，validateInput 还检查某些敏感内容或不必要修改；call 从 L387 开始进行具体文件改动。

**不应由此推出** getPathsForPermissionCheck 能抵御所有 TOCTOU、硬链接、挂载点、Windows 重解析点和符号链接竞态。自研 Host 必须以受限目录句柄、系统级进程隔离和写入前最终路径验证为准。

## 四、Bash：并发性、命令规则与沙箱使用条件

旧版 [BashTool.tsx](https://github.com/wwxst/-/blob/main/restored-src/src/tools/BashTool/BashTool.tsx#L430-L455)：

- L434-440：isConcurrencySafe 通过 isReadOnly 的结果判定，而非把 Bash 全部判为只读。
- L445-455：准备 Hook 命令匹配时会解析复合命令；解析不确定时选择更保守的匹配，避免复杂命令绕过特定安全 Hook。
- L539-540：checkPermissions 调 bashToolHasPermission。
- L624 起进入 call；Shell 命令的最终运行在后续调用链发生。
- 工具是否受 SandboxManager 限制，需继续结合 shouldUseSandbox、具体 runShellCommand 分支和所选 OS 验证，不等于对 Bash Tool 的所有变体都已证明隔离。

新版本 chunk-4b60tdnk.js 中能找到 Bash 工具本身及 permission/execute 入口，也能找到 SandboxManager 相关依赖。**本轮没有对 Windows 原生进程 / VM / WSL / SSH 的全部隔离路径实施运行测试**。

## 五、对子 Agent 继承权限的额外警告

旧版 [runAgent.ts](https://github.com/wwxst/-/blob/main/restored-src/src/tools/AgentTool/runAgent.ts#L412-L478)：

- 子 Agent 可定义 permissionMode，但父任务的 bypassPermissions、acceptEdits 等状态在特定情况下优先；
- 异步后台 Agent 默认可能不显示审批 UI，另有明确配置允许冒泡或显示；
- 显式传入 allowedTools 时，会替换来自父 Session 的 allow 规则，但保留 SDK 命令行来源的 cliArg 规则。

**因此不能无证据地声称 Claude Code 的子 Agent 权限一定是父 Agent 权限的严格集合。** 对我们的自研内核，仍坚持“默认只减权，不自动继承过宽的交互放行”，这是一项自主设计决策，而不是对 Claude 的行为描述。

## 六、迁移到我们的 Kernel 时应设计什么

| 机制 | 参考价值 | 自研实施约束 |
| --- | --- | --- |
| 显式 deny/ask/allow 和工具级 check | 高 | deny 优先级明确，不允许 Hook 覆盖硬拒绝 |
| PreToolUse 和交互审批 | 高 | 绑定 toolCallId、工具版本、参数哈希、Session、宿主与截止时间 |
| 路径规范化与符号链接检查 | 高 | Tool Host 最终强制实施目录能力，不只依赖 Node 路径字符串 |
| Bash 只读分类 | 中高 | 分类错误必须保守回退为“可能有副作用” |
| 自动审批分类器 | 有研究价值 | 第一版默认关闭，不允许模型自己宣称批准 |
| bypass / acceptEdits | 仅研究 | 如果支持高危快捷模式，需要独立告知、范围、过期和审计 |
| 工具沙箱 | 必需 | 无真正隔离时拒绝高风险 Shell；失败时不能静默降级为无沙箱 |

## 七、必须有的安全验收

T12-01 对所有工具先做 deny 检查；Hook allow 不能覆盖硬拒绝。  
T12-02 Hook 将输入改写后，原有审批失效；新参数重新计算权限。  
T12-03 同一审批 ID 不可跨 Session/ToolCall/Host 重用。  
T12-04 修改权限配置后，长时间运行任务在下一个授权边界读取最新规则。  
T12-05 符号链接与竞态攻击不能逃离受限目录。  
T12-06 Bash 命令解析失败默认保守处理，复合命令不得绕过规则。  
T12-07 没有沙箱或权限服务异常时，不执行高风险工具。  
T12-08 拒绝和取消均形成正确关联的 tool_result，但不伪造“未产生副作用”。

这些是我们必须实现的测试，不是本次已经运行的 Claude Code 安全测试。
