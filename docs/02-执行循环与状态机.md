# 02 · Agent 执行循环与状态机

> 状态：设计草案。以下状态、接口和流程均为 v0.1 目标，不是现有实现。

## 一、术语

- **Session**：持久会话容器，包含多次 Turn、会话配置和事件流。
- **Turn**：一次用户请求及其引发的模型/工具活动；有独立取消和完成状态。
- **Step**：一次模型请求、工具批次、压缩或审批等待的内部步骤。
- **ToolCall**：模型发出的工具执行请求；必须分配全局唯一调用 ID。
- **Provider**：将模型专有协议映射到标准流的适配器。
- **Steering**：在指定活跃 Turn 中加入用户新指令；不是无条件开启新 Turn。

## 二、Turn 状态

```text
queued -> preparing -> running_model
                         │
                         ├─> waiting_approval -> running_tools -> running_model
                         │
                         ├─> running_tools -> running_model
                         │
                         ├─> compacting -> running_model
                         │
                         └─> completed
所有非终态 --(取消)--> cancelling -> cancelled
所有非终态 --(故障)--> failed / interrupted
```

合法终态：completed、cancelled、failed、interrupted。

不变量：

1. 同一 Session 的可变执行活动在 v0.1 至多有一个活跃 Turn；其余 Turn 排队或被明确拒绝。
2. 一个 Turn 终态只写入一次，不可从终态恢复为 running；继续执行需要新 Turn 或明确的恢复尝试记录。
3. 取消请求可重复发送，但最多产生一次有效状态终结。
4. 审批等待时不可执行受保护工具；审批必须绑定精确 ToolCall 参数指纹。
5. 每个模型调用、工具调用、压缩均有明确预算、超时和可观测事件。
6. Prompt 注入内容与工具回显一律视为数据，不具有更新系统指令或授予权限的权力。

## 三、Agent Loop 概念过程

```text
1  接受用户消息，持久化 TurnCreated / UserMessageAccepted
2  构建系统规则、项目指令、历史上下文、技能提示与工具列表
3  检查预算、上下文窗口、取消状态
4  调用 Provider；把增量结果标准化为 Model* 事件
5  模型无工具调用 -> 完成 Turn
6  模型有工具调用 -> 校验名称、参数、工具声明和策略
7  需要授权 -> 生成 ApprovalRequested，等待批准/拒绝/超时
8  已授权 -> 记录 ToolCallPrepared，再由 Host 执行并记录结果
9  把结果纳入 Context，继续步骤 3
10 达到模型/工具/耗时限额 -> 明确结束或提示人工接管
```

需要定义防止无限循环：默认最大模型步数、最大累计工具调用数、最大连续重复调用次数、最长 Turn 耗时、预算上限；实际默认值由配置与测试确认，而非在文档中伪造固定数字。

## 四、暂停、取消和 Steering

### 取消

- 客户端发送 CancelTurn(turnId)。
- 服务端记录 CancelRequested，终止未开始步骤，尽最大可能通知 Provider 与 Host 停止。
- 对已发生的副作用必须等待宿主给出明确结果；不能假设“发送取消 = 命令没有执行”。
- 进入 cancelled 前应清理或标记所有等待的审批与工具调用。

### Steering

- 指定预期 Turn ID，避免新指令注入另一轮任务。
- 新指令从受控入口进入模型上下文；已开始的有副作用工具通常不能无条件撤销。
- 应持久化 SteeringAccepted 或 SteeringRejected 及原因。
- v0.1 可以将 Steering 列为实验能力；核心必须先正确完成取消与顺序执行。

### 超时与中断

- Provider 超时、工具超时、审批超时、Session 关闭属于不同错误域。
- 进程意外退出后未完成的 Turn 标记 interrupted；恢复前对尚未确认的工具副作用进行核对。

## 五、事件顺序和模型输出

- 模型流分片只是增量展示；模型是否真正完成需等 Provider 最终事件。
- 工具调用参数片段必须完整合并并通过 Schema 校验，才可准备执行。
- 多工具调用如果按顺序执行必须固定顺序；如允许并发，要保留独立调用 ID、审批与结果关联，且明确相互依赖的处理规则。
- 模型返回文本与工具调用同批出现时，不可据“已有文本”提前结束 Turn。

## 六、最小测试矩阵

| 场景 | 必须满足 |
| --- | --- |
| 只有文本 | 收到终态、事件唯一、有可回放输出 |
| 多次工具调用 | 每次有唯一调用 ID，结果不会错配 |
| 非法工具或参数 | 不执行，返回标准拒绝/错误 |
| 需要审批且拒绝 | 工具实际执行次数为 0 |
| 批准后执行 | 审批绑定调用 ID 与参数摘要 |
| Provider 流中断 | Turn 明确标记失败或中断，不假装完成 |
| 重复取消 | 状态一致，无二次副作用 |
| 启动时发现悬空 ToolCall | 不直接重复执行高风险工具 |
| 预算耗尽 | 停止循环并产出可解释原因 |
